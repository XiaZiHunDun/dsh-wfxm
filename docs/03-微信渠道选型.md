# 03 — 渠道选型（微信 / 桌面）

> 调研日期 2026-10-15（微信渠道）；**2026-10-28 补桌面通道**。
> 全部结论来自 GitHub REST API + `raw.githubusercontent.com` 源码 + 本地 dsh 源码交叉核对。
> **未采信任何插件目录站/博客的转述。**

## 结论

**用 `xmanrui/dsh-im`，锁 `5.7.0`；运行基线 DSH `0.2.1-rc.2`。**

> **2026-10-28 复核**：5.7.0 已覆盖微信/飞书/企微/钉钉/QQ/Slack/Telegram/Discord/WhatsApp/Matrix。
> 本文下方的候选对比是 10-15 快照，版本号已过期；**选型结论不变**。

```sh
dsh plugin --profile web add -w @xmanrui/dsh-im@5.7.0
```

- **不要自行降级到 4.x** —— 5.7.0 的验证基线是 DSH `0.2.1-rc.2`（Session v4），旧宿主请用对应历史版本
- **不要从 dsh-plugin.org 装** —— issue #124/#133/#297/#298/#302/#354/#356 全是这条路径 install failed

## ClawBot 与 iLink 的关系

**同一件事的两层，不是两个可选方案。**

| 名称 | 是什么 |
|---|---|
| **ClawBot** | 腾讯在微信里的功能入口（我 → 设置 → 插件），用户侧产品形态 |
| **iLink** | 支撑它的底层 API 协议，`ilinkai.weixin.qq.com`，纯 HTTP/JSON 长轮询，无 WebSocket、无官方 SDK |
| **`@tencent-weixin/openclaw-weixin`** | 腾讯开源的该协议参考实现（MIT），各插件 vendor 的就是它 |

**协议与 OpenClaw 框架解耦** —— 只要符合 iLink 协议就能接入，不必用 Claw 应用。
理论上完全可以自己写 iLink 客户端，一个插件都不装。
（且 WFXM 已有非测试 1,228 行实现，见 [04-WFXM-资产盘点](04-WFXM-资产盘点.md)）

## 为什么选 dsh-im

1. **社区规模高一个数量级**（2.0k star / 47 贡献者 / 900 commit / 116 版本），近 11 天 6 个 release，有外部 PR 被合并。
2. **工程安全明显更好**：凭证走 `tokenRef` + Host 凭证服务，出站锁死腾讯域名 + HTTPS + 443，CDN 上传 AES 加密。
3. **多渠道**：微信之外还能接飞书/Slack/Telegram/钉钉/企微/QQ/Discord/WhatsApp —— Butler 现在有 Slack/Telegram 的投入。
4. **自带兼容自检脚本**：`scripts/verify-*.mjs` 可对着本地源码跑。
5. **微信代码隔离干净**：`src/channels/weixin/` 六个文件职责分明，将来要补体验有落点。

## dsh-im 微信渠道的 4 个已知妥协

| # | 妥协 | 判断 |
|---|---|---|
| 1 | 微信看不到 thinking 和工具进度，只有"正在输入"+1800 字分段（**微信是它 9 个渠道里最弱的一档**，飞书有原生 thinking 过程） | 纯体验，可忍 |
| 2 | 审批是**文字/yes-no**，不是可点卡片 | 需 owner 确认能否接受从「`确认`/`👌`/`y`」退成「回个 yes」 |
| 3 | **扫码新建 bot 默认放开入站**（渠道级白名单可调，但默认不安全），任何能联系 bot 的人都能驱动 agent | ⚠️ **必须处理** —— 见下 |
| 4 | 超时补发**不重放审批**（README：恢复文字结果和终态通知，"不重放问题、审批或文件工具调用"） | 边缘场景，可忍 |

### 关于第 3 条

**优先用小号物理隔离**：dsh-im 微信渠道不拦入站，只要确保那个微信号只有 owner 本人使用、
不外传给别人，缺口就被堵住，**不需要改代码**。

若将来要接别人或给团队用，再在 dsh-im 前面挂一层入站过滤 —— 但那不需要重写 iLink。

### 另外两个运维坑

- **同一微信账号只能绑一个 dsh 实例**：`connection-supervisor.mjs` 只有进程内 single-flight 锁，
  **没有跨进程锁**，两个实例会互抢游标。
- **消息 API 无自动 429 重试**：只有文件投递做 429 分类，普通消息没有。

## 腾讯侧账号风控

issue #2 有用户报告：换 5 个新 bot 后 `sendmessage` 一直返回 `ret:0` 但**无 `message_id`、
手机端连会话记录都没有**（服务端接受但不投递）。作者无法复现，判为账号侧风控。

**频繁重新扫码 / 换 bot 可能触发腾讯主动推送风控。**
不要把投递问题当 bug 反复重扫解决。

同时：把 agent 接进个人微信号长时间自动回复，仍可能触发腾讯对机器人行为的滥用判定。
**这是本方案最主要的外部风险，dsh 的任何技术特性都无法缓解。**

## 如果将来要改微信体验

**不要 fork dsh-im**（47 贡献者 / 900 commit 的合并成本只为改一个目录不划算）。

正确做法是**自己写一个渠道插件**，而且**不需要重写 iLink**：

| 要写 | 规模 |
|---|---|
| iLink 协议层 | **0 行** —— WFXM 已有非测试 1,228 行实现，直接复用 |
| 入站：微信消息 → `session.prompt` | 一层映射 |
| 出站：`session/event` → 微信消息 | 反向映射 |
| 审批应答：注册 `approval/request` waterfall，解析中文（`确认`/`👌`/`y`）返回 `allowed-once` | 补回社区插件都缺的体验 |
| 入站白名单 | 补 dsh-im 的安全缺口 |
| 流式推送 | 补 1800 字分段 |

**规模判断**：协议层 0 行，胶水层几百行。比 fork dsh-im 小两个数量级。

## 桌面通道（2026-10-28 补）

> **要解决的问题**：在**另一台电脑**上控制服务器上的 agent。
> **结论**：三条现成路线，**都不需要自研桌面客户端**；需要自己写适配的只有一个自托管 IM 场景，第一版不做。
> 证据级别：dsh-im 5.7.0 渠道清单与 web-app 源码 README 均属 **E2（一手材料，未在本机运行）**；
> 跨 surface 行为**未实测**（见本节末尾）。

### 1) 桌面 IM —— 配置级，零开发

这些渠道**本身就有桌面客户端或网页版**，装一个 dsh-im 后，同一个 bot 同时服务手机和电脑，会话是同一个：

| 渠道 | 桌面形态 | 状态 |
|---|---|---|
| 飞书 | 桌面 App / 网页版 | ✅ 已支持，**推荐** |
| 企业微信 | 桌面 App | ✅ 已支持 |
| 钉钉 | 桌面 App | ✅ 已支持 |
| Slack | 桌面 App / 网页 | ✅ 已支持 |
| Telegram | Desktop / Web | ✅ 已支持 |
| Discord | 桌面 / 网页 | ✅ 已支持 |
| Matrix | Element 桌面 / 网页 | ✅ 已支持（可完全自托管） |
| QQ | 桌面客户端 | ✅ 已支持 |
| 微信 | 桌面客户端 | ⚠️ 与手机同链，仍是 typing + 1800 字分段 |

**推荐飞书**：thinking 与流式过程是 dsh-im 里最好的一档，桌面端与手机端可同时看同一会话。
审批仍是文字 yes/no，不是可点卡片（与微信侧同一限制）。

### 2) 浏览器控制台 —— dsh 自带，零开发

`packages/bundle/web-app` 提供完整的浏览器 GUI：交互式聊天、模型与设置管理、会话历史。

- 启动：`dsh --profile web`；`--host` **只接受一个具体地址，拒绝 wildcard**；`--port` 可改。
- 远程：`--tls-cert/--tls-key` 直接起 HTTPS，或 `--public-url` + `--trusted-host` 挂反代后。
- 鉴权：启动 URL 带一次性 token，换取 signed cookie；Host/Origin 有围栏。
- 接入方式：**Tailscale 私有网（首选）**，或 Cloudflare Tunnel + Access。**不要直接开公网端口。**
- 适合：长日志、大 diff、多会话并行——这些在 IM 里会被 1800 字分段毁掉。

### 3) 编辑器 / 终端 —— 现成，但不是对话形态

| 方式 | 说明 |
|---|---|
| SSH + tmux | 最稳，偏运维；不是聊天 |
| VS Code Remote / code-server | 浏览器里的 IDE，可开终端 |
| ACP（`--profile acp`） | Zed 等编辑器通过 ACP 驱动 agent；偏编码，不是通用控制台 |

### 4) 需要小适配 / 不建议

| 候选 | 判断 |
|---|---|
| Mattermost / Rocket.Chat / Zulip | 都有桌面 + 网页客户端，但 **dsh-im 不覆盖**；要自写 `ChannelPort` 入站/出站适配（几百行）。**第一版不做** |
| Open WebUI / LibreChat | 需要 OpenAI 兼容层，**丢掉 session / 审批 / 任务语义**，等于再造一层，不划算 |
| ntfy / Gotify | 只能单向推送，不能下指令；只适合 P0 告警兜底 |
| Apache Guacamole | 远程桌面，不是 agent 通道 |

### 5) 建议分工

| 场景 | 用哪条 |
|---|---|
| 手机 / 随手 | 飞书或企微 |
| 桌面长任务、看日志、多项目 | 浏览器 GUI + Tailscale |
| 完全不依赖第三方 IM | Matrix / Element（已支持，自托管） |
| Mattermost 类自托管 IM | 不在第一版；确有需要再写适配 |

### 6) 两条硬约束

1. **仍然只有一个受控入口（AR12）**：浏览器 GUI 不直接暴露公网；优先 Tailscale。
   启动 URL 里的 token 是凭证，**不能贴进聊天或日志**。
2. **跨 surface 未验证**：web 与 IM 是同一进程、同一数据面，但**两个 surface**。
   "web 发起的任务能否在 IM 看进度 / 完成审批"必须实测，作为冒烟项并入 V4/V6。
