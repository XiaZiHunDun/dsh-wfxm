# 22-第七阶段闭环检查

> 目标：验证「使用 → 信息收集 → 分析 → 反馈优化 → 测评 → 再使用」是否已经形成可自运转的飞轮。
> 检查时点：2026-11-26，生产 `2026.11.26-7`（`1ccb4d1`）。
> 方法：代码接线核查 + 生产只读实测；不改任何表。

## 一、结论

**半闭环，不是完整飞轮。** 六个环节里：

| 环节 | 状态 | 一句话 |
|---|---|---|
| 使用 | ✅ 自动 | 飞书消息 → 前台/任务 → 执行，已有真实流量 |
| 信息收集 | ✅ 自动 | 遥测、审计、任务、巡检、回执全量落 `ops.sqlite` |
| 分析 | ✅ 自动 | 巡检日报/周报、`/diag`、`trace stats`、事实体检定时产出 |
| 反馈优化 | 🔧 半自动 | 建议/记忆提案/巡检候选都能看到，但采纳靠人；建议无追踪 |
| 测评 | 🔧 半自动 → ✅ 自动（P7-2 已补） | 有 `/eval`、L2 门禁、发布快照；2026-11-26 起 nightly 每日落 `eval_runs`/`eval_findings` |
| 再使用（回流） | 🔧 半自动（P7-1/P7-4 已补） | 生产失败可用 `/eval from-task` 生成候选；nightly 回放判定 verified/regressed，但修复后仍需用新轨迹刷新候选 |

所以飞轮**转了半圈**：使用数据能自动变成日报和指标，但「指标/失败 → 改进 → 验证改进」仍靠人的记忆和手工操作。主要断点不是采集能力，而是**回流与回测**。

## 三、逐环节核查

### 3.1 使用

- 飞书 → 前台只做路由、不执行（[host](../plugins/host/src/host.ts)），任务由 worker 领取并回执。
- 审批、资源锁、预算硬限、合并状态都在执行链上。
- **结论**：可用且有真实流量（66 个任务、163 条出站）。

### 3.2 信息收集

- 遥测四表：`trace_events` / `task_attempts` / `telemetry_usage` / `telemetry_drops`，异步队列写入，14 天保留（[store](../plugins/telemetry/src/store.ts)）。
- 业务正本：`inbox/outbox`、`tasks/task_events/receipts`、`audit_log`、`eval_*`、`inspections`。
- 埋点覆盖 turn、tool、phase、error、attempt；失败 attempt 的可诊断率实测 100%。
- **结论**：这一环是真闭环，自动、可校验、无人工补录。

### 3.3 分析

- 巡检 patrol 每 15 分钟运行，每天 09:00 日报、周一 09:00 周报，自动入 outbox 并投递飞书（[patrol](../plugins/svcops/src/patrol.ts)、[serve](../scripts/serve.mjs)）。
- 日报含：巡检、任务、会话、事实体检、预算、出站健康、建议；周报额外含 open findings 与轨迹指标。
- 只读入口：`/diag`、`node scripts/trace.mjs stats`（[trace.mjs](../scripts/trace.mjs)）。
- **结论**：分析结果会自动到达 owner，不依赖人主动查。

### 3.4 反馈优化

- 建议（G4）：规则优先、最多 3 条，只进日报，不建任务（[suggestions](../plugins/svcops/src/suggestions.ts)）。
- 记忆（G5）：模型 `mem_propose` → owner 对话确认 → `gateFact` 写回，过期自动清理（[proposals](../plugins/knowledge/src/proposals.ts)）。
- 专家/项目路由（O1）：确定性规则 + 显式命令，不自动推断（[project-resolver](../plugins/gateway/src/project-resolver.ts)）。
- **缺口**：建议是纯文本，没有稳定 id、没有「已采纳/已忽略」状态；owner 回复「做 #n」不会被结构化解析，也不会回写建议状态。实测同一条建议连续两天重复，就是证据。

### 3.5 测评

- 入口：`/eval`（摘要/findings/flag/promote/ignore/run l2），发布前 `scripts/eval/snapshot.mjs` 跑 L2 并写 `eval/latest.json`。
- 落库：`eval_runs` / `eval_findings` 已建表，快照同步按 `recordedAt` 幂等写入。
- 门禁：观察期至 2026-12-08，之后 `release prepare` 遇 gate 失败直接阻断（[eval-gate](../scripts/lib/eval-gate.mjs)）。
- **缺口**：生产 `eval_runs` 为 0——测评只在开发机/发布时跑，产品内没有日常节奏；仓库内也没有 nightly 任务（只有 CI 跑 verify-all）。

### 3.6 再使用（回流）

- `/eval promote` 只把 finding 写成 `eval/candidates/<id>.json` 草稿，`turns/expect` 必须人工补全；**不建任务、不写 agent-eval 任务集**（[promote](../plugins/eval/src/promote.ts)）。
- 生产失败 → 测评：`trace.mjs export` 能导出脱敏轨迹，但需要人工逐条执行；巡检/日报不会自动把失败 attempt 变成测评候选。
- 修复后：没有「重跑原失败用例 → 通过才关闭 finding」的机制；finding 状态停在 `promoted`。
- **结论**：这是飞轮真正的断点——测评结果没有进入执行链，执行结果也没有回到测评。

## 四、断点清单（按影响排序）

| # | 断点 | 证据 | 影响 |
|---|---|---|---|
| G1 | 生产失败不自动进入测评集 | `trace.mjs export` 为手动命令；日报无「可回流」入口 | 真实失败样本无法沉淀为回归 |
| G2 | `promote` 只落草稿，不建任务 | [promote.ts](../plugins/eval/src/promote.ts) 只写 `eval/candidates/` | finding → 修复 之间靠人搬运 |
| G3 | 没有日常测评节奏 | 生产 `eval_runs=0`；仓库只有 CI，无 nightly | 测评不是飞轮的一环，只是发布前检查 |
| G4 | 修复后不回测原失败 | 无 verified/regressed 状态与回测命令 | 无法证明「改进有效」 |
| G5 | 建议无结构化采纳 | 建议纯文本；同一条连续两天重复 | 建议→任务→结果无法统计 |
| G6 | 轨迹指标不进优化 | 周报只展示文本；阈值不触发建议/告警 | 有数据但不驱动行动 |
| G7 | 硬门禁失败只阻断进程 | `release prepare` 非 0 退出 | owner 可能事后才知道发布被挡 |
| G8 | 专家/路由无成功率反馈 | `route_decisions` 只记录；expert 无统计 | 路由质量无法迭代 |

## 五、完善方案（建议按此顺序）

| 片 | 目标 | 最小实现 | 验收 |
|---|---|---|---|
| **P7-1 生产失败回流** | 把真实失败变成测评候选 | ✅ 已落地（2026-11-26）：`/eval from-task <task>` 复用 `trace.mjs export` 的 NDJSON/草稿，落数据目录候选；周报显示「可回流失败 N」 | 一条失败任务能生成候选，finding 关联 `task_id`，不导出原文 |
| **P7-2 测评日常化** | 让测评每周自动跑 | ✅ 已落地（2026-11-26）：`scripts/eval/nightly.mjs` + `dsh-wfxm-eval.timer` 每日跑 L2 + 基线，写 `eval_runs`/`eval_findings` | 连续两周每周至少 1 条 run；失败自动成 finding |
| **P7-3 建议可采纳** | 建议有 id、有状态 | 日报建议带稳定 `sug_*` id 与建议表；解析「做 #n」建任务并写 `suggestion_id`，记录 accepted/ignored | 建议→任务→回执可查询；重复日报不再出现已采纳项 |
| **P7-4 修复回测** | 证明改进有效 | ✅ 机制已落地（2026-11-26）：nightly 回放 promoted 候选，PASS → verified、曾经通过再 FAIL → regressed；首次 FAIL 保持 promoted（原失败仍复现） | 周报出现 promoted / verified / regressed 三个计数 |
| **P7-5 门禁可见** | 发布被挡 owner 立刻知道 | 硬门禁失败时除非 0 退出外，向 owner 入一条 outbox/task | 演练：故意失败 → owner 收到飞书 |
| **P7-6 指标进规则** | 遥测驱动建议 | 把 `trace stats` 的错误率/p95 阈值接入 suggestions 与即时告警 | 阈值触发时日报/告警出现对应建议 |

**建议先做 P7-1 + P7-2**：它们把「生产数据 → 测评」接上，是后续 P7-3/P7-4 的前提；P7-5/P7-6 可以随后补。

## 六、第七阶段完成定义

满足以下四条，才把「闭环体系」标记为完成：

1. 一条真实生产失败可走完：`/eval from-task` → 候选 → 任务 → 修复 → 下一轮测评 PASS → finding 关闭，全程无需手工编辑 JSON。
2. 连续两周 nightly 有 `eval_runs` 行，findings 有 open → promoted → verified 的真实流转。
3. 建议可统计采纳率；同一建议不会因为「没人回复」而无条件重复刷屏。
4. 发布硬门禁失败时，owner 在飞书收到通知；`verify-all` 增加闭环套件并全绿。

## 七、非目标

- 不自动改代码、不自动合并、不自动发版。
- 不把生产原文、完整轨迹或绝对路径上传公共仓。
- v1 不做模型自动根因分析；先规则 + 人工确认，有真实需求再升级。
