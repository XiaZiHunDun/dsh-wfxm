## 一、通用约定

| 项 | 约定 |
|---|---|
| Schema 真源 | **zod**（先 schema 后类型），类型一律 `z.infer`（N3；手写重复类型视为违规） |
| 主键 | `TEXT`，**UUIDv7**（时间有序，索引局部性好） |
| 时间 | `TEXT`，ISO-8601 **UTC**，带毫秒；展示时再转本地时区 |
| 布尔 | `INTEGER` 0/1 |
| 结构化字段 | `TEXT` 存 JSON，**写入前过 zod 校验**（不用 SQLite 的 JSON 函数做查询） |
| 必填审计列 | 所有业务表带 `created_at`；可变表带 `updated_at` |
| 删除 | 默认**不物理删除**；需要时用 `deleted_at` 或语义化状态（记忆用 `superseded_by`） |
| 迁移 | 每模块独立（见 §七） |

## 二、库的划分

| 账 | 载体 | 归属 |
|---|---|---|
| **会话账**（对话） | dsh session log | 宿主；**只经公开事件读**，不解析文件 |
| **业务账** | `ops.sqlite`（单库单文件） | 我们 |
| **配置默认层** | `config/*.yaml` | 我们（人可编辑） |
| **配置覆盖层** | `settings` 表 | 管理面（Web 渠道）唯一写 |
| **记忆正本** | `memory/*.md` + `memory_facts` | 模块 ⑥ |
| **快照** | restic 仓库 + `snapshots`（工作区级元数据）+ `file_preimages`（文件级前镜像） | 模块 ⑦ |

**为什么单库**：备份、快照、迁移都简单；跨模块禁止直写，所以不需要分库来"隔离"。

> **修正 12 §10.1 第 11 项**：单库多模块时 `PRAGMA user_version` 只够一个模块用，改为
> `schema_migrations(module, version)` 复合主键（见 §七）。

## 三、表设计（按模块）

> 每张表标注 **唯一写者**；"可重建"指删掉后能由其它正本或外部事实重建。

### 模块 ① 渠道网关

**`inbox`** — 入站消息（可重建，非正本）

```sql
CREATE TABLE inbox (
  id            TEXT PRIMARY KEY,
  channel_id    TEXT NOT NULL,
  msg_id        TEXT NOT NULL,            -- 渠道消息 ID（飞书 event_id）
  kind          TEXT NOT NULL,            -- message | card_action | control
  actor_id      TEXT,
  content_json  TEXT NOT NULL,
  status        TEXT NOT NULL CHECK (status IN
                  ('accepted','triaged','routed','done','failed','rejected')),
  error_code    TEXT,
  received_at   TEXT NOT NULL,
  processed_at  TEXT
);
CREATE UNIQUE INDEX ux_inbox_dedup ON inbox(channel_id, msg_id);   -- 落库即去重（AR28）
CREATE INDEX ix_inbox_status ON inbox(status, received_at);
```

> **H2 准入（Slice BB，`2026.11.19-4`）**：去重之后、分诊之前依次检查
> ① 渠道 allowlist → ② 每主体固定窗口限流 → ③ 单条内容上限（默认 65,536 字符）。
> 主体 = 已配对 `actor_id`，未配对时为渠道 `external_user_id`；未配对 `/bind` 也受限流。
> 拒绝：`inbox.status='rejected'`、`error_code` ∈ `channel-not-allowed` / `rate-limited` /
> `content-too-large`，`route_decisions` 记 `ignore` + `admission: …`，**不产生出站回复**。
> 端口缺省 = 放行（开发/测试兼容）；生产由 `DSH_WFXM_ADMISSION_*` 配置，格式错误启动即失败。

**`actors`** — 主体（**正本**）

```sql
CREATE TABLE actors (
  id           TEXT PRIMARY KEY,
  kind         TEXT NOT NULL CHECK (kind IN ('owner','system')),
  display_name TEXT,
  created_at   TEXT NOT NULL
);
```

**`channel_bindings`** — 渠道身份 ↔ actor（**正本**）

```sql
CREATE TABLE channel_bindings (
  id                TEXT PRIMARY KEY,
  actor_id          TEXT NOT NULL,
  channel_id        TEXT NOT NULL,        -- 飞书 app_id
  external_user_id  TEXT NOT NULL,        -- 飞书 open_id
  bound_at          TEXT NOT NULL,
  revoked_at        TEXT
);
CREATE UNIQUE INDEX ux_binding_live
  ON channel_bindings(channel_id, external_user_id) WHERE revoked_at IS NULL;
```

**`session_routes`** — 渠道会话 ↔ dsh session（可重建）

```sql
CREATE TABLE session_routes (
  channel_id   TEXT NOT NULL,
  chat_id      TEXT NOT NULL,              -- 渠道聊天 ID（飞书 chat_id）；§9.3 三步改名已落地
  session_kind TEXT NOT NULL CHECK (session_kind IN ('orchestrator','chat')),
  session_id   TEXT NOT NULL,
  project_id   TEXT,
  updated_at   TEXT NOT NULL,
  PRIMARY KEY (channel_id, chat_id, session_kind)
);
```

> **v2（C 方案）**：`orchestrator` 行指向**同一个 owner 唯一的前台会话**（多聊天共用同一 `session_id`，Thread 作用域靠装配）；
> `chat` 行只用于 Web 深度会话；任务会话不进本表（记在 `tasks.session_id`）。

**`route_decisions`** — 前台路由决策（**只追加**，① 唯一写者）

```sql
CREATE TABLE route_decisions (
  id             TEXT PRIMARY KEY,
  trigger_id     TEXT NOT NULL,            -- inbox.id
  action         TEXT NOT NULL CHECK (action IN
                   ('answer','ack','ask','accept','attach','ignore','stop')),
  target_task_id TEXT,
  thread_id      TEXT,
  project_id     TEXT,                     -- v7：本轮绑定的项目（11 §5.3.1）
  project_matched_by TEXT,                 -- v7：explicit / anchor / sticky / single / asked
  reason         TEXT NOT NULL,            -- 回答"为什么没理我 / 为什么挂到那件事"
  confidence     REAL,
  prompt_version TEXT,
  created_at     TEXT NOT NULL
);
CREATE INDEX ix_route_decisions_trigger ON route_decisions(trigger_id, created_at);
CREATE INDEX ix_route_decisions_action  ON route_decisions(action, created_at);
```

> **v7（2026-11-09，① 项目解析片 2）**：`project_id` / `project_matched_by` 是可空增量列（`ALTER TABLE`），
> 老行留 `NULL`。决策**只追加**，所以"这轮为什么绑到这个项目"必须可回放（11 §5.3.1）。
> 会话粘性由模块 API **`setSessionProject({channelId, chatId, sessionKind, projectId})`** 写
> `session_routes.project_id`：**只更新已有 route 行，返回 `false` 表示该 chat 还没有 route**——不臆造 `session_id`。

**`outbox`** — 出站队列（**v2 起归 ①**：11 说 ① 负责出站与回执，⑤ 不再直接发人话）

```sql
CREATE TABLE outbox (                     -- 同事务写，投递器发（§13 3.2）
  id TEXT PRIMARY KEY, topic TEXT NOT NULL, payload_json TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('pending','sent','failed')),
  attempts INTEGER NOT NULL DEFAULT 0,
  next_retry_at TEXT, created_at TEXT NOT NULL, sent_at TEXT,
  lease_owner TEXT, lease_expires_at TEXT,  -- 单投递器租约，防重复投递
  external_msg_id TEXT,                     -- ack 判据：拿到渠道消息 id 才算送达
  last_error TEXT
);
CREATE INDEX ix_outbox_pending ON outbox(status, next_retry_at);
```

> ⑤ 终止任务时只写 `receipts` 并发事件；① 订阅事件后写 `outbox` 并负责渲染、重试与送达。

> **落地（2026-11-09，① 第一片）**：`plugins/gateway`（`@dsh-wfxm/gateway`）已建 `inbox` / `actors` /

> 验证：gateway 76 例（v1→v6 升级含旧 `chat_id` 回填、半迁移拒绝、outbox 载荷出站前后均无原文密钥）。
>
> **落地（2026-11-10，① 第八片 = AR37 唤醒接线）**：新增 `plugins/gateway/src/wake.ts` 与两个**注入式结构端口**
> **`GrantCheckPort`**（→ ③ `verify`）和 **`TaskWakePort`**（→ ⑤ `wakeTask`），① 仍不导入 ③/⑤ 包（AR33）；
> 授权动作常量 **`WAKE_ACTION='task.wake'`** 只在这里定义。**`ingestInbound` 锚点命中已 `succeeded` 任务时**：
> 三端口（`grantCheck` + `wake` + `relay`）齐全 → 先复验；通过则 `wake`（`round + 1`）再把本条回复 `attach` + `enqueue`
> 进新轮次，`route_decisions` 记 **`action='wake'`**；复验不通过 → **不 attach、不进任务**，按无主消息交前台分诊（AR37），
> `IngestResult.wake` 带回 ③ 的原因。**fail-closed**：任一端口缺失 → 保持第三片行为（`requiresGrantCheck` 标记 +
> `relay.skipped='finished-needs-grant'`，不唤醒）；`wake` 端口抛错 → `inbox=failed` + `error_code='wake-unavailable'`，
> 决策保留 `targetTaskId`；唤醒成功但 `enqueue` 抛错 → `relay-unavailable`（任务已进入新轮次，回复不假装送达）。
> `gateway` **v8** 重建 `route_decisions`（SQLite 不能改 CHECK），把 `wake` 加入动作白名单并重建只追加触发器。
> 验证：gateway 88 例（+4：放行/拒绝/半接线/唤醒失败），③ 侧另有 27 例含三模块端到端。

**能力声明缓存（`channel_caps`）不落库**：按 `channel_id` 驻进程内，重启后向渠道重新协商即可重建。
它是缓存不是正本，因此不占建表名额（AR5：可重建的东西不存第二份）。

### 模块 ② 策略与判级

**`policy_rules`** — 规则配置（**正本**，来自 `config/policy.yaml` 加载 + 覆盖层）

```sql
CREATE TABLE policy_rules (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  priority    INTEGER NOT NULL,           -- 小者先匹配
  match_json  TEXT NOT NULL,              -- {domain, pathGlob, commandPattern, network}
  verdict     TEXT NOT NULL CHECK (verdict IN ('R0','R1','R2','R3','ask','block')),
  enabled     INTEGER NOT NULL DEFAULT 1,
  updated_at  TEXT NOT NULL
);
```

**`decisions`** — 每次判级留痕（**只追加**）

```sql
CREATE TABLE decisions (
  id             TEXT PRIMARY KEY,
  correlation_id TEXT NOT NULL,
  stage          TEXT NOT NULL CHECK (stage IN ('S1','S2','jev','fallback')),
  rule_id        TEXT,                    -- S1 命中的规则（17 §七）
  ruleset_version TEXT,                   -- 规则集版本，规则变更可追溯
```

### 模块 ④ 审计与证据

**`audit_log`** — 只追加 + 哈希链（**正本**）

```sql
CREATE TABLE audit_log (
  seq             INTEGER PRIMARY KEY AUTOINCREMENT,  -- 连续，链靠它
  id              TEXT NOT NULL,
  ts              TEXT NOT NULL,
  actor_id        TEXT,
  action          TEXT NOT NULL,
  target          TEXT,
  correlation_id  TEXT,
  payload_digest  TEXT NOT NULL,          -- 原文只留摘要（AR16）
  prev_hash       TEXT,                   -- 上一条 hash
  hash            TEXT NOT NULL
);
CREATE TRIGGER audit_no_update BEFORE UPDATE ON audit_log
  BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;
CREATE TRIGGER audit_no_delete BEFORE DELETE ON audit_log
  BEGIN SELECT RAISE(ABORT, 'audit_log is append-only'); END;
```

**写入前脱敏（19 D19-2）**：`payload` 落库前先过 `redact`，凭据形态（私钥 / Secret / JWT / 带密码连接串）一律掩码。
审计不得成为泄露副本；掩码在计算 `payload_digest` **之前**完成，保证同一条记录只有一种 hash。

**哈希链冻结（写代码前定，AR16）**

- **canonical 字段与顺序**：`seq|ts|actor_id|action|target|correlation_id|payload_digest`，空值写空串，**不含 `hash` 自身**；
  **不依赖 JSON 对象键序**（对象键序不稳定，同一记录会算出两种 hash）。
- **算法**：`hash = sha256(prev_hash + canonical)`；`seq = 1` 时 `prev_hash = GENESIS`（64 个 `0`）。
- **校验**：按 `seq` 顺序从头重算，**任一不符即链断** → 告警并停写业务（[16 §十](16-部署与运行.md)），不自动修复。
- **导出**：按 `seq` 区间导出摘要 + 链供外部复核；原文不落库（AR16）。

**H3 查询面（Slice BA，`2026.11.19-3`）**：`GET /admin/audit`，只读，复用 ③ 管理面的
`AdminAuthorizer`（默认 `DSH_WFXM_ADMIN_TOKEN` Bearer，未配置即 401）。
参数 `actorId` / `action` / `target` / `from`（含）/ `to`（不含）/ `limit`（1–500）/ `beforeSeq`（游标）；
返回 `{ rows, count, nextBeforeSeq }`，按 `seq DESC`。`?verify=1` 走 `AuditStore.verifyChain()`
返回 `{ chain:{ok,checked,reason?,badSeq?} }`。`GET + Accept: text/html` 返回自包含查询页外壳
（无服务端数据、CSP `default-src 'none'`）。写方法一律 405。验证：`verify-audit-admin` 10 例
（真实 HTTP + 真实哈希链）；生产库 `verify-audit` 校验 384 条链通过。

## 五、端口契约（签名）

**统一错误类型**（适配器必须翻译成它，不得抛裸错）

```ts
type PortError =
  | { kind: 'Unavailable'; retryable: false; detail: string }
  | { kind: 'Transient';   retryable: true;  retryAfterMs?: number }
  | { kind: 'RateLimited'; retryable: true;  retryAfterMs?: number }
  | { kind: 'Timeout';     retryable: true }
  | { kind: 'PermissionDenied'; retryable: false }
  | { kind: 'NotFound';    retryable: false }
  | { kind: 'Conflict';    retryable: false }
  | { kind: 'InvalidInput'; retryable: false }
  | { kind: 'BudgetExceeded'; retryable: false }
  | { kind: 'NotSupported'; retryable: false };

type Result<T> = { ok: true; value: T } | { ok: false; error: PortError };
```

**关键端口（节选；完整签名进 `contracts/`）**

```ts
interface ChannelPort {                                   // 4 项必需
  capabilities(): Promise<Result<ChannelCaps>>;
  identify(raw: RawInbound): Result<ExternalIdentity>;     // (channel_id, external_user_id)
  deliver(msg: OutboundMessage): Promise<Result<DeliveryRef>>;
  ack(ref: DeliveryRef): Promise<Result<DeliveryStatus>>;  // 可选能力，不保证
}

interface ExecPort {
  run(argv: string[], opts: { cwd: string; timeoutMs: number; signal?: AbortSignal;
                              idempotencyKey?: string }): Promise<Result<ExecResult>>;
  readFile(path: string): Promise<Result<{ content: string; sha: string }>>;
  writeFile(path: string, content: string, expectSha?: string): Promise<Result<{ sha: string }>>;
}

interface SvcOpsPort {
  list(): Promise<Result<UnitInfo[]>>;
  status(unit: string): Promise<Result<UnitStatus>>;
  start(unit: string): Promise<Result<void>>;
  stop(unit: string): Promise<Result<void>>;
  restart(unit: string): Promise<Result<void>>;             // 与 17 的 svc_restart 对应
  logs(unit: string, opts: { since: string; limit: number }): Promise<Result<string>>;
}

interface SchedPort {                                     // 只投原 session
  schedule(spec: { cron: string; sessionId: string; payload: unknown }): Promise<Result<{ id: string }>>;
  cancel(id: string): Promise<Result<void>>;
}
```

**约定**：`ports/` 内**不得出现协议名、命令行、产品名**（AR32），只允许能力动词 + 结构化数据。
`ExecPort.run(argv)` 收的是**参数数组**，不是 shell 字符串——避免拼接歧义。

## 七、迁移规则

| 规则 | 说明 |
|---|---|
| 位置 | `<module>/migrations/NNN_<name>.sql`（纯 SQL） |
| 版本 | `schema_migrations(module, version)` 复合主键（**不是** `user_version`） |
| 只加不改 | 已应用的脚本不得修改；`checksum` 校验，手改即启动失败 |
| 破坏性变更 | 分三步：expand（加新列/新表）→ migrate（双写回填）→ contract（删旧） |
| 失败 | **拒绝启动**，不回退到半旧 schema（11 §四） |
| 顺序 | 启动时按 `module` 各自推进到最新，互不阻塞 |

> **落地（2026-11-26，N8 完成）**：新增共享迁移器 `@dsh-wfxm/sql-migrate`
> （[index.ts](../plugins/sql-migrate/src/index.ts)）。它读取 `<module>/migrations/NNN_<name>.sql`（必须从 001 连续），
> 把每个已应用版本的 sha256 写入 `schema_migrations(module, version, name, checksum, applied_at)`。
> 文件被改写、已应用版本缺文件、版本不连续，都**拒绝打开 store**（即拒绝启动，符合 11 §四）。
> 旧库兼容：`PRIMARY KEY (module)` 形状自动重建为复合主键；只保留最高版本的旧写法按文件 checksum
> **回填缺失行**（`applied_at` 沿用最高版本时间），不会重放 DDL。`name` / `checksum` 可空，
> 供未迁模块过渡，但当前 **14 个模块已全部迁完**。
> 全部迁移模块：tasks（v1–v15）、gateway（v1–v9）、memory（v1–v4）、calendar（v1–v2）、
> changes、reminder、telemetry、eval、snapshot、inspection（v1–v2）、
> approval（v1–v2）、grant、policy、audit（各 v1）。
> gateway v4→v5→v6 是 expand → migrate → contract 的文件化示例（v6 的前置校验仍在代码里，
> 见 `guards[6]`）；DDL/DML 本身保持纯 SQL。memory v3 的 `vcs` 回填需要读文件系统，
> 因此由 store 在 `runMigrations` 返回 `applied` 含 v3 时执行，SQL 文件只负责加列。
> 门禁：[verify-migrations](../scripts/verify-migrations.mjs)（checksum 篡改/缺文件/不连续/旧库回填，
> 并逐一核对 14 个模块的行数、文件名与 checksum）。

## 九、B1 线程/订阅数据契约（已生效 v2.1）

> **状态**：已生效（2026-11-03，owner 确认）。由 [18 附录 C](18-Super-agent对照与改进建议.md) 回写，结构依据 [11 §十三](11-架构锚定.md)。
> **生效后按 §七 的 expand → migrate → contract 三步落地**；`§三` 既有表结构以本节增量为准。
> 本节只写 B1 增量，不重复已有表定义。

### 9.1 新增表（3 张）

```sql
-- ① 渠道网关（正本）
CREATE TABLE threads (
  id           TEXT PRIMARY KEY,
  channel_id   TEXT NOT NULL,
  chat_id      TEXT NOT NULL,
  kind         TEXT NOT NULL CHECK (kind IN ('topic','root')),
  topic_id     TEXT,                      -- 话题群的话题 ID
  root_msg_id  TEXT,                      -- 单聊 / 普通群的根消息
  project_id   TEXT,                      -- 只作路由提示，不作权限判据（AR33）
  created_at   TEXT NOT NULL,
  last_msg_at  TEXT
);
CREATE UNIQUE INDEX ux_thread_key
  ON threads(channel_id, chat_id, kind, COALESCE(topic_id,''), COALESCE(root_msg_id,''));
CREATE INDEX ix_threads_chat ON threads(channel_id, chat_id, last_msg_at);

-- ⑤ 任务运行时（正本）
CREATE TABLE task_threads (
  id             TEXT PRIMARY KEY,
  task_id        TEXT NOT NULL,
  thread_id      TEXT NOT NULL,
  relation       TEXT NOT NULL CHECK (relation IN ('default_owner','anchor')),
  anchor_msg_id  TEXT,                    -- anchor 时：发起 / 结果 / 提问消息
  created_at     TEXT NOT NULL,
  released_at    TEXT,
  release_reason TEXT CHECK (release_reason IN ('handback','stopped','superseded','failed'))
);
CREATE UNIQUE INDEX ux_task_thread_live
  ON task_threads(task_id, thread_id, relation, COALESCE(anchor_msg_id,''))
  WHERE released_at IS NULL;
CREATE UNIQUE INDEX ux_thread_default_owner
  ON task_threads(thread_id) WHERE relation='default_owner' AND released_at IS NULL;
CREATE INDEX ix_task_threads_thread ON task_threads(thread_id, released_at);

CREATE TABLE task_inputs (                -- 只存引用与状态，不复制正文（AR2）
  id           TEXT PRIMARY KEY,
  task_id      TEXT NOT NULL,
  inbox_id     TEXT NOT NULL,
  round        INTEGER NOT NULL,
  status       TEXT NOT NULL CHECK (status IN ('pending','delivered','read','returned')),
  delivered_at TEXT,
  read_at      TEXT,
  error_code   TEXT,
  created_at   TEXT NOT NULL
);
CREATE UNIQUE INDEX ux_task_input_dedup ON task_inputs(task_id, inbox_id);
CREATE INDEX ix_task_inputs_pending ON task_inputs(task_id, status, round);
```

**三条约束**

1. `task_threads(thread_id)` **不设外键到 `threads`**：跨模块只经 API / 只读视图，不靠 FK 表达归属（AR33）。
2. `task_inputs` 的 `round` 必须与 `tasks.round` 同值；由 ⑤ 在入队时取当前轮，**不允许调用方自带**。
3. `release_reason` 只允许四值；`superseded` 仅由"新任务接管默认归属"产生。

### 9.2 字段扩展（4 处）

| 表 | 新增字段 | 用途 | 兼容性 |
|---|---|---|---|
| `inbox` | `chat_id TEXT`、`thread_id TEXT`（可空）、`reply_to_msg_id TEXT` | 锚点解析；去重键仍是 `(channel_id, msg_id)` | 可空，旧写入不阻塞 |
| `tasks` | `round INTEGER NOT NULL DEFAULT 1`、`origin_msg_id TEXT`、`task_ref TEXT` | 轮次；发起锚点；不可猜测短码 | 默认值可回填 |
| `receipts` | `round INTEGER`、`external_msg_id TEXT` | 每轮一次回执；结果消息可作新锚点 | 可空 |
| `outbox` | `task_id TEXT`、`thread_id TEXT`、`reply_to_msg_id TEXT` | 回到原线程 / 原消息，不新开会话；**表归 ①（v2）** | 可空 |

追加索引：

```sql
CREATE UNIQUE INDEX ux_tasks_task_ref ON tasks(task_ref) WHERE task_ref IS NOT NULL;
CREATE UNIQUE INDEX ux_receipts_round  ON receipts(task_id, round) WHERE round IS NOT NULL;
CREATE INDEX ix_outbox_thread ON outbox(thread_id, status, next_retry_at);
```

> `task_ref` 规则：8–12 位、随机、不可猜测、全局唯一；**撞码即重试生成（≥3 次）**，仍冲突则任务创建失败。
> 它只用于路由提示，不参与授权判断（见 [11 §十三](11-架构锚定.md)）。

### 9.3 `session_routes` 迁移（命名冲突）

现状把 `thread_id` 当"渠道聊天 ID"用，与 Thread 语义冲突。目标：`(channel_id, chat_id, session_id)`。

| 步 | 脚本（模块 ①） | 内容 |
|---|---|---|
| 1 expand | `002_session_route_add_chat_id.sql` | `ALTER TABLE session_routes ADD COLUMN chat_id TEXT;` |
| 2 migrate | `003_session_route_backfill_chat_id.sql` | `UPDATE session_routes SET chat_id = thread_id WHERE chat_id IS NULL;`，双写窗口内两侧同写 |
| 3 contract | `004_session_route_drop_thread_id.sql` | 重建表（PK `(channel_id, chat_id)`），删 `thread_id`；重建前校验无 `chat_id` 为空 |

**约束**：

- 三步**不得合并进同一脚本**；contract 前必须有一次全量校验（`chat_id` 非空、无重复 PK）。
- **C 方案（v2，已定）**：`§三` 已加 `session_kind`，迁移后的 PK 必须是 `(channel_id, chat_id, session_kind)`；
  本节 **B1 已生效（v2.1）**；`session_kind` 与 `chat_id` 的改名必须在同一次迁移中落地。
- 话题 / 根消息**不进 `session_routes`**：它们属于 `threads`，会话粘性仍按"聊天"粒度。
- 迁移失败即拒绝启动（§七），不回退到半旧 schema。

> **落地（2026-11-09，① 第六片）**：三步按版本列表拆成 `gateway` **v4（expand）/ v5（backfill）/ v6（contract）**，未合并；
> v6 前有 `guard`（`chat_id` 为空或 `(channel_id, chat_id, session_kind)` 重复即抛错拒绝启动，不回退半旧 schema）；
> 迁移后 PK 为 `(channel_id, chat_id, session_kind)`，`thread_id` 已删。模块 API 同步改名：
> `SessionRoute.chatId`、`setSessionRoute({chatId})`、`getSessionRoute(channelId, chatId, kind)`、`listSessionRoutes({chatId})`；
> `thread_lookup` 输出同样用 `chatId`。验收：v1 库带旧行升级后 `chatId` 已回填、`thread_id` 列消失；
> 半迁移行（`chat_id IS NULL`，version=5）打开即抛 `contract refused`。

### 9.4 单一写者矩阵（增行）

| 表 | 唯一写模块 | 谁可读 |
|---|---|---|
| `threads` | ① 网关 | ⑤ 不读（`thread_id` 由 ① 经 API 传入）；管理面只读 |
| `task_threads` `task_inputs` | ⑤ 任务 | ① 经只读视图 `v_task_anchors`；看板只读 |

其余行不变；`inbox` 仍归 ①，`tasks` / `receipts` 归 ⑤；**`outbox` 已按 C 方案改归 ①（见 §三）**。

> **修订说明（相对 18 C.3）**：`v_task_anchors` **不跨模块 join**。原始建议里带了 `channel_id` / `chat_id` / `kind`，
> 那需要 join ① 的 `threads`；改为只出 ⑤ 自己的字段，由 ① 用自己的 `threads` 补全，避免"视图成为跨模块直读后门"。

### 9.5 只读视图 `v_task_anchors`

```sql
CREATE VIEW v_task_anchors AS
SELECT tt.task_id,
       tt.thread_id,
       COALESCE(tt.anchor_msg_id, tk.origin_msg_id) AS anchor_msg_id,
       tk.round,
       tk.status
FROM task_threads tt
JOIN tasks tk ON tk.id = tt.task_id
WHERE tt.released_at IS NULL;
```

- 供 ① 在**锚点解析**时读取；① 拿到 `thread_id` 后用本地 `threads` 补 `channel_id` / `chat_id` / `kind`。
- 视图只暴露"活归属"；已释放的历史归属不出现在视图里，审计仍可查表（管理面只读）。
- ① 不得以任何形式直读 `task_threads` / `tasks`（AR33，lint 可验）。

### 9.6 模块 API 签名（内核内部，**不是** §五 的端口层）

> **定性说明**：这三个接口是 ① 网关 ↔ ⑤ 任务运行时的**跨模块 API**（AR33），
> **不计入 §五 / [11 §五](11-架构锚定.md) 的 13 个端口**——端口是可替换的外部能力边界，模块 API 是内核内部接缝。
> 沿用 `Result` 与 10 类 `PortError` 语义，只为避免两套错误风格；调用方不得据此认为"可替换"。

```ts
interface ThreadApi {                      // 写者 ①；⑤ 不直接调用
  ensure(key: ThreadKey): Promise<Result<ThreadRef>>;              // 幂等 upsert
  resolve(q: AnchorQuery): Promise<Result<AnchorMatch | null>>;    // 锚点解析（内部经 ⑤ 的只读视图）
}

interface TaskSubscriptionApi {            // 写者 ⑤
  bind(input: { taskId: string; threadId: string;
                relation: 'default_owner' | 'anchor'; anchorMsgId?: string }): Promise<Result<void>>;
  release(input: { taskId: string; threadId: string;
                   reason: 'handback' | 'stopped' | 'superseded' | 'failed' }): Promise<Result<void>>;
  occupancy(threadId: string): Promise<Result<ThreadOccupancy>>;   // live / wakeable / defaultOwner
  /** AR37：仅 succeeded 且仍有 live 订阅；round + 1、attempt=0，写 task.woken */
  wake(input: { taskId: string; reason?: string }): Promise<Result<TaskRef>>;
}

interface TaskInputApi {                   // 写者 ⑤
  enqueue(input: { taskId: string; inboxId: string }): Promise<Result<TaskInputRef>>;
  pending(taskId: string): Promise<Result<TaskInputRef[]>>;
  markDelivered(id: string): Promise<Result<void>>;
  markRead(id: string): Promise<Result<void>>;
}

type ThreadKey = { channelId: string; chatId: string;
                   kind: 'topic' | 'root'; topicId?: string; rootMsgId?: string };
type AnchorQuery = { channelId: string; chatId: string;
                     replyToMsgId?: string; taskRef?: string };
type AnchorMatch = { taskId: string; round: number; status: TaskStatus; relation: 'default_owner' | 'anchor' };
type ThreadOccupancy = { defaultOwnerTaskId?: string; live: string[]; wakeable: string[] };
```

**约定**：

- `enqueue` **不接受调用方传 `round`**（见 9.1 约束 2）；入队即取 `tasks.round`，保证回执与投递同轮。
- `bind` 的 `default_owner` 冲突由唯一索引兜底，端口翻译为 `Conflict`，**不自动抢占**。
- `resolve` 的优先级：`taskRef` → `replyToMsgId`（命中锚点集合）→ `null`；`null` 交给 ① 的分诊，**不由端口猜**。
- `ports/` 内不得出现渠道产品名（AR32）；`topic` / `chat` 只是键名，不是协议名。

**`PortError` 映射（10 类，仅列新增端口会产生的）**

| 类 | 触发 |
|---|---|
| `Unavailable` | 迁移未完成、视图 / 表不可用 |
| `Transient` | 写锁冲突、SQLite busy，可重试 |
| `RateLimited` | 不适用（不发外部请求） |
| `Timeout` | 锚点解析 / 回填对账超时 |
| `PermissionDenied` | actor 非已配对 owner（投递 / 唤醒前置校验） |
| `NotFound` | `thread_id` / `task_id` / 锚点不存在 |
| `Conflict` | 第二个 `default_owner`、重复 `bind`、`task_ref` 撞码 |
| `InvalidInput` | `kind='topic'` 却无 `topic_id`，或 `kind='root'` 却无 `root_msg_id` |
| `BudgetExceeded` | 不适用 |
| `NotSupported` | 跨渠道 Thread、context-only 订阅（v1 边界） |

**回执送达的锚点回填（切片 C，2026-11-10）**：`receipts.external_msg_id` 由 ① 投递器 `onSent` 回填后，
**组合根 `@dsh-wfxm/host` 用同一 `external_msg_id` 追加一条 `task_threads(relation='anchor')` 订阅**，
使「直接回复机器人的结果消息」能命中锚点回到原任务（同键 `bind` 幂等，每轮最多一条）。
该动作只经 ⑤ 模块 API `bindThread`，① 不读 ⑤ 表、⑤ 不读 ① 表（AR33）。

**L3 恢复（2026-11-25）**：若行已 `sent` 而回执仍未 settle（崩溃 / 钩子抛错），下一轮 `pump` 按
`dedupe_key` 找到该行后，用它的 `external_msg_id` 先重建锚点再 `settle`；`bindThread` 同键幂等，
重复恢复不会产生第二条锚点，也不会重发消息。

**`resource_key` 规范化**（写入前由 ⑤ 的 API 归一，不接受调用方原文）

|---|---|
| `port:<proto>:<port>` | `proto` 小写；`port` 十进制无前导零 |

| `docker:<project>` | 项目名小写 |
| `git:<repoRoot>` | `realpath` 后的仓库根 |

### 10.5 状态机

**`merge_state`**

| 当前 | 允许迁移到 | 触发 |
|---|---|---|
| `none` | `pending` / `abandoned` | 任务成功请求合并；任务取消 |
| `pending` | `merged` / `conflict` / `abandoned` / `none` | 合并成功；合并冲突；放弃；本次尝试未落地（git 直接失败）回退未合并 |
| `conflict` | `pending` / `abandoned` | 冲突解决后重试；放弃 |
| `merged` | — | 终态 |
| `abandoned` | — | 终态 |

> `succeeded` 只表示分支就绪，**不等于 `merged`**；两者不得混用。
> worktree 任务收敛前由 worker 执行一次 `git add -A && git commit`（干净工作区不产生空提交，失败则任务置 `failed`/`commit-failed`）：执行器只改工作区，若不提交，`merge` 会因「worktree 有未提交改动」拒绝（2026-11-25 第五阶段验收发现并修复，`commitWorktreeChanges`）。

**`prepare_state`**

| 当前 | 允许迁移到 | 触发 |
|---|---|---|
| `none` | `running` | 开始 prepare |
| `running` | `done` / `failed` | 成功；超时或非零退出 |
| `done` / `failed` | — | 终态（失败需新任务或 owner 显式重置） |

> 重启时若发现 `running` 但任务租约已失效 → 置 `failed`，不自动重跑。

### 10.7 模块 API 签名（内核内部，**不是** §五 的端口层）

> 与 §9.6 同理：这是 ⑤ 对外暴露的**模块 API**，不计入 13 个端口；
> `IsolationApi` 内部调用宿主 `ctx.worktrees` 服务（实验包），失败必须显式返回，不得静默降级（AR13）。

```ts
interface IsolationApi {                  // 写者 ⑤
  plan(taskId: string): Promise<Result<IsolationPlan>>;          // 只判定，不建目录
  prepare(taskId: string): Promise<Result<PrepareResult>>;       // 幂等，只跑一次
  release(taskId: string, reason: 'merged' | 'abandoned' | 'failed'): Promise<Result<void>>;
  merge(taskId: string): Promise<Result<MergeResult>>;
  status(taskId: string): Promise<Result<IsolationStatus>>;
}

interface ResourceLockApi {               // 写者 ⑤
  acquire(input: { keys: string[]; taskId: string; ttlSec: number }): Promise<Result<LockGrant>>;
  heartbeat(input: { lockIds: string[]; ttlSec: number }): Promise<Result<void>>;
  release(lockIds: string[]): Promise<Result<void>>;
}

type IsolationPlan = { mode: 'serial' | 'worktree'; worktreePath?: string;
                       baseCommit?: string; branch?: string };
type PrepareResult = { state: 'done' | 'failed'; exitCode?: number; durationMs: number };
type MergeResult = { state: 'merged' | 'conflict' | 'pending'; conflictPaths?: string[] };
type IsolationStatus = { mode: 'serial' | 'worktree'; prepareState: PrepareState; mergeState: MergeState };
type LockGrant = { lockIds: string[]; expiresAt: string };
```

**约定**

- `plan` 只读：判定 `vcs`、工作区是否干净、域是否允许；不创建目录。
- `prepare` 幂等：`done` / `running` 直接返回；`failed` 不自动重试。
- `release` 幂等：已释放再调用无副作用。
- `merge` 内部先取 `git:<repoRoot>` 资源锁，再执行合并；冲突只返回 `conflict`，不自行解决。
- 宿主 worktree 服务不可用 → `Unavailable`，**不回退共享 workspace**。

> **Phase 2 落地（2026-11-12）**：`merge` 的仓库串行由进程内队列 + `<git-common-dir>/wfxm-merge.lock`
> 实现（`git:<repoRoot>` 资源锁表仍未做）；任务此时已是终态 `succeeded`，冲突不改任务状态，只写
> `merge_state=conflict` 与 `task.merge` 事件（owner 确认，终态不回退）。
> **Slice Z 补全（2026-11-12，release `2026.11.12-11`）**：合并现在在文件锁内再取
> `git:<realpath(repoRoot)>` 租约（TTL 600s，100ms 重试到 `lockTimeoutMs`）；超时抛 `conflict`，
> 成功/冲突/异常均释放。`prune` / `release` 不取该锁。

**`PortError` 映射（仅列新增 API 会产生的）**

| 类 | 触发 |
|---|---|
| `Unavailable` | 宿主 worktree 服务未启用 / 迁移未完成 |
| `Transient` | git 管理目录被占用、SQLite busy |
| `RateLimited` | 不适用 |
| `Timeout` | prepare 超时、合并超时 |
| `PermissionDenied` | worktree 路径越出 `writeRoots`（AR11） |
| `NotFound` | 任务 / worktree / 分支不存在 |
| `Conflict` | worktree 路径已存在、分支已存在、资源键被占 |
| `InvalidInput` | 非 git 项目请求 worktree、`resource_key` 非法、多键为空 |
| `BudgetExceeded` | 磁盘水位低于阈值（拒绝新 worktree） |
| `NotSupported` | 跨仓库共享 worktree、非 git 建 worktree（v1 边界） |

## 十二、第六阶段遥测数据契约（2026-11-26，P6-0 已落地）

> 目标：让“后台已失败、用户只看到一句处理失败”变成可定位、可复盘。本节的表由
> `@dsh-wfxm/telemetry`（`module='telemetry'` v1）唯一写；采集点接线在 P6-1，用户面在 P6-2。
> 设计取舍见 `.trae/specs/phase6-observability/spec.md`。

### 12.1 表与写者

| 表 | 用途 | 唯一写者 | 读取方 |
|---|---|---|---|
| `trace_events` | 结构化事件时间线（任务/阶段/工具/模型/错误） | 遥测 | `/diag`、周报、导出（经 store API） |
| `task_attempts` | 单次执行 attempt：执行器、模型、起止、结果、错误码、会话引用 | 遥测 | `/diag`、复盘 |
| `telemetry_usage` | 配额计数：`day:<YYYY-MM-DD>` 与 `task:<id>` | 遥测 | 遥测自身（`stats()`） |
| `telemetry_drops` | 丢弃计数：按天 × 原因聚合 | 遥测 | 巡检/周报（“采到了多少、丢了多少”） |

`trace_events` 与 `task_attempts` 不设外键：跨模块关联靠 `task_id` / `trace_id`，由 owner 提供读 API，
其它模块不 join（AR33）。`trace_events` 允许保留期清理删除，因此不加 append-only 触发器；
需要不可篡改的证据仍写 `audit_log`。

### 12.3 关联规则

1. **一个 trace 贯穿消息、任务、attempt、步骤与工具调用**：网关首条消息生成 `trace_id`，
   写入 `tasks.correlation_id`；attempt 与事件复用它。
2. `message → task` 用 `message_id` / `thread_id`；`task → attempt` 用 `(task_id, attempt)`；
   `attempt → dsh 会话` 用 `session_ref`；`task → 工作区` 用 `attrs` 的 `worktree` / `branch`。
3. 用户只看到 `task_ref`；服务端用 `task_ref → task_id → trace_id` 反查，不要求用户理解内部 id。
4. `task_attempts` 的幂等键是 `(task_id, attempt)`：重复 `begin` 保留原 `started_at`，
   `finish` 只允许 `running → succeeded|failed|cancelled`。

### 12.4 默认模式、脱敏与配额

| 项 | 约定 |
|---|---|
| 模式 | `DSH_WFXM_TRACE` 取 `off` / `meta` / `full`，缺省 `meta`；未知值创建 store 即失败 |
| `meta`（默认） | 只落 id、摘要（`message_digest` / `stack_digest`）、错误码、工具名、耗时；不落原文与 `attrs` |
| `full` | 额外落二次脱敏后的 `error.message` / `error.stack` 与白名单 `attrs`；工具参数仍只落摘要 |
| `off` | 事件全丢，只保留丢弃计数；便于临时止血 |
| 单任务配额 | 2 MiB（`telemetry_usage` 的 `task:<id>`） |
| 单日配额 | 200 MiB（`day:<YYYY-MM-DD>`，宿主本地日） |
| 磁盘水位 | ≥85% 时 `full` 自动降为 `meta`，不丢事件；恢复后自动回升 |
| 写入 | 有界队列 + 批量事务；队列满/校验失败/超配额/写库失败只记 `telemetry_drops`，**不向业务抛错** |
| 保留期 | SQLite 行 14 天；`traceDir` 下 `YYYYMMDD` 归档目录 7 天（NDJSON 写入已由 P6-3 导出接线） |

`attrs` 白名单（其余键静默丢弃，不丢整条事件）：`channel` `chat_id` `project` `risk_level`
`isolation` `branch` `merge_state` `prepare_state` `step` `turn` `exit_code` `retry_after_ms`
`http_status` `unit` `session_ref` `worktree` `receipt_id` `approval_id` `grant_id` `provider`
`tool_call_id` `topic` `error_stage` `degraded`。

## 十三、采集点与 trace 关联（2026-11-26，P6-1 已落地）

> 采集点只负责把结构化事实交给 `telemetry.emit`；隐私过滤、配额和降级都在 store 内完成。
> 采集器不得因为遥测失败改变任务结果。

### 13.1 trace 来源

1. 网关 `acceptInbound` 为每条入站消息生成 `inbox.id`（uuidv7），P6-1 直接把它当作 `traceId`。
2. 前台创建任务时写 `tasks.correlation_id = result.inbox.id`；worker、执行器、Verifier、隔离/合并、
   投递都从任务的 `correlation_id` 取同一个 trace。
3. 消息根 span 的 `spanId` 等于 `traceId`；其余 span 用确定性 id，见下表。

| 层级 | spanId | parentSpanId |
|---|---|---|
| message | `traceId` | — |
| task | `task:<taskId>` | `traceId` |
| attempt | `attempt:<taskId>:<attempt>` | `task:<taskId>` |
| step | `step:<taskId>:<attempt>:<n>` | `attempt:<taskId>:<attempt>` |
| tool_call | `tool:<taskId>:<attempt>:<step>:<seq>` | 对应 step |

非消息来源的任务（工具创建/测试）仍用 `createTask` 默认 uuidv7，允许没有消息根 span。

### 13.2 采集点

| 采集点 | 事件 |
|---|---|
| 网关接入 | `message.received`（attrs 只带 `channel`，会话用 `threadId`）；前台失败 `message.failed` |
| 任务生命周期 | `task.created`、`task.claimed`、`task.settled` |
| attempt | `attempt.started`、`attempt.finished`（失败带 `error.code`） |
| 执行器 | `executor.started`、`executor.step`（模型用量）、`executor.finished` |
| 工具调用 | `tool.call`、`tool.result`（参数只落 digest） |
| Verifier | `verify.started`、`verify.succeeded`、`verify.failed` |
| 隔离 | `isolation.prepare.*`、`isolation.commit.*` |
| 合并 | `merge.started`、`merge.succeeded`、`merge.conflict`、`merge.failed` |
| 投递 | `receipt.sent`、`delivery.failed`（`delivery-retry` / `delivery-failed`） |

等级约定：正常生命周期 `info`，步进/工具 `debug`，可重试失败 `warn`，终态失败 `error` 且必须带
`error.code`（P6-0 schema 强制）。

### 13.3 失败与非阻塞

1. `emit` 返回 `false`（`off`/配额/队列满）时调用方忽略，不重试、不改业务分支。
2. `beginAttempt` / `finishAttempt` 的数据库异常由 worker 捕获并经 `onError` 上报；
   任务照常执行/收敛。
3. 事件字段缺失（如 `error` 缺 `code`）由 schema 拒绝并计入 `invalid`，不影响业务。
4. 执行器的 `tool.args` / `error.message` 只作为原始输入交给 store；`meta` 下只保留摘要。

### 13.4 装配与关闭

- `scripts/serve.mjs` 在 storage 阶段创建**唯一** `createTelemetryStore({ dbPath, traceDir })`，
  注入执行器、隔离解析器与宿主；宿主 `close()` 负责 `telemetry.close()`（内部先 flush）。
- 手动合并（`scripts/isolation.mjs`）读同一 `DSH_WFXM_TRACE`，合并事件与任务共用 trace。
- `DSH_WFXM_TRACE=off` 时业务路径不变，只保留丢弃计数。

- `plugins/telemetry/scripts/verify-instrumentation.mjs`：完整 span 树、失败 attempt/错误码、
  重试第二 attempt、Verifier 失败、commit 失败、真实 dsh NDJSON 的 step/tool 事件、遥测抛错不影响任务、

## 十四、诊断入口与失败回执（2026-11-26，P6-2 已落地）

### 14.1 增强后的失败回执

失败回执固定最多 4 行，替换原来的泛化文案：

```
任务 abc123 失败。
阶段：验证
原因：verification-failed
追踪：tr_a1b2c3d4
```

- 数据来源：宿主在 `pendingReceipts` 处用 `telemetry.attempts(taskId)` 的最新 attempt 与
  该任务最后一条 `level=error` 事件补齐 `failurePhase / errorCode / failureKind / traceId`；
  遥测不可用时回退到旧格式（摘要 + 重试提示）。
- 回执只给短追踪号 `tr_<前8位>`；完整 trace 在 `/diag` 中给出。

### 14.2 `/diag <任务号>`（仅 owner）

只读、不进模型、不建任务，最多约 8 行：

```
任务 abc123 失败。
状态：failed · 第 2/3 次尝试 · 轮次 1
阶段：验证（verify）
原因：verification-failed（验证未通过）
最后成功：executor.step
耗时：1m12s
追踪：<完整 trace id>
```

- 任务号支持完整 id / `taskRef` / 前缀。
- 健康任务明确输出「无异常。」；`DSH_WFXM_TRACE=off` 时明确说「诊断数据未启用」。
- 阶段优先取执行/验证/隔离/合并等真实错误事件，避免被 `attempt.finished` 的书签事件覆盖。

### 14.3 `/status`（仅 owner）

```
服务：运行中
任务：running 2 · queued 1 · waiting_input 0 · waiting_approval 0
近 1 小时：失败 3 / 8（38%）
卡住：abc123（23 分钟无事件）
遥测：meta · 丢弃 0 · 今日 1.2MB
```

失败率按近 1 小时已终结任务（`finishedAt`）统计 `failed / (failed+succeeded+cancelled)`；
卡住定义为 `running` 且最新事件超过 `stuckAfterMs`（默认 15 分钟）。

### 14.4 主动告警

- 每 `diagnosticsIntervalMs`（默认 60s）扫一次，告警先入 outbox 再由同一 tick 的 dispatcher 发出。
- 卡住：每个 `(task, attempt)` 只提醒一次（dedupe `diag:stuck:<task>:<attempt>`）。
- 重复失败：同一 `error.code` 近 1 小时 ≥ `repeatFailureThreshold`（默认 3）提醒一次
  （dedupe `diag:repeat:<code>:<小时桶>`）。
- 告警投递到该任务的 live thread；没有线程则跳过，不广播。
- `diagnosticsIntervalMs=0` 关闭主动告警；`/diag` `/status` 仍可用。

### 14.5 验证

`plugins/host/scripts/verify-diagnostics.mjs`：命令解析、4 行失败回执、回执补齐、
`/diag`（执行/验证/隔离三类真实失败）、`/status` 渲染、错误码聚合与告警文案；
已注册进 `verify-all`。

## 十五、查询、导出与周报指标（2026-11-26，P6-3 已落地）

> 只读入口：`scripts/trace.mjs` 读与业务相同的 `ops.sqlite`，不改任何表。
> 周报指标由 `plugins/telemetry/src/report.ts` 的纯函数计算，CLI 与 patrol 共用。

### 15.1 `scripts/trace.mjs`

| 命令 | 用途 |
|---|---|
| `query` | 按 `--task`（id/`taskRef`/前缀）、`--trace`、`--error`、`--level`、`--since`/`--until`、`--limit` 过滤；`--json` 输出完整行 |
| `show <task\|trace>` | 任务优先解析 `taskRef`/前缀，输出尝试摘要 + 时间线；纯 trace 也可查看 |
| `stats` | 近 7 天（可改窗口）的轨迹指标，见 §15.3；`--json` 供脚本消费 |
| `export <task>` | 生成 `agent-eval` 兼容的 NDJSON + 草稿任务 JSON |

- 时间参数同时接受 ISO 与相对时长（`24h`、`7d`、`30m`、`90s`）。
- 库路径与生产一致：`parseServeConfig(process.env)` 读取 `DSH_WFXM_DB` / `DSH_WFXM_DATA_DIR`。
- `query` 的 `--limit` 上限 5000；`show` 默认 500，达到上限时明确标注。

### 15.2 导出格式（与 `agent-eval` 兼容）

`export` 默认写到 `eval/trajectory`（`.gitignore` 内，仅留本机），目录必须在
`--repo-root`（默认仓库根）之内：

```
{"type":"session","sessionId":"prod-<hash8>"}
{"type":"tool_call","name":"read"}
{"type":"tool_result","name":"read","ok":true}
{"type":"status","phase":"step_end"}
{"type":"status","phase":"turn_end","reason":{"kind":"transient"}}
{"type":"status","phase":"error","reason":{"kind":"merge-conflict"}}
{"type":"final","text":"<脱敏摘要>"}
```

> `phase:error` 是 P6-4 新增：prepare/commit/merge/delivery 这类没有 attempt 的失败，
> 也必须能在回放里看到停在哪一步；`reason.kind` 就是错误码。

- 只保留工具名/成败、步骤与终结原因、脱敏后的 attempt 摘要；不导出参数、工具输出与原文。
- 草稿 JSON：`suite=dsh-trajectory`、`taxonomy=online-replay`、`runtimeHints.dsh.traceFile`
  指向 NDJSON；有工具时判据为 `requiredTools`，否则退化为回复片段 `containsAny`。
- 无事件的 task 直接报错；输出目录越界同样报错（防止把生产轨迹写进公共仓）。

### 15.3 指标定义

| 指标 | 口径 |
|---|---|
| 事件/失败事件 | 窗口内 `trace_events` 行数；`level='error'` 行数 |
| attempt/失败 | 窗口内 `task_attempts`（按 `started_at`）；`outcome='failed'` |
| Top 错误码 | 失败事件的 `error.code` 计数，取前 3 |
| 失败阶段 | 失败事件的 `phase` 计数，取前 3（`execute`→执行、`verify`→验证等） |
| p50/p95 时延 | 已结束 attempt 的 `finished_at - started_at`；无 attempt 时回退失败事件的 `durationMs` |
| 工具错误率 | `tool.result` 中 `status='failed'` 或 `exitCode≠0` 的占比 |
| 执行/模型错误率 | `executor.finished` 中 `level='error'` 或 `status='failed'` 的占比 |
| 可诊断率 | 失败 attempt 中 `errorCode` 与 `traceId` 均非空的比例（目标 100%） |

周报追加 3 行（无事件时整段省略）：

```
轨迹：事件 120 · attempt 9 · 失败 2 · 可诊断 2/2（100%）
错误 Top：timeout 2 · verification-failed 1；阶段：执行 2 · 验证 1
时延 p50 1.2s · p95 8.4s · 工具失败 1/20 · 执行失败 1/6
```

- 读取失败只丢轨迹段，不影响任务/会话/测评段（`serve.mjs` 内局部 try/catch）。
- `telemetry.attemptsSince({from,to,limit})` 是本切片新增的只读方法，供 CLI 与周报共用。

### 15.4 验证

`plugins/telemetry/scripts/verify-trace-cli.mjs`：临时库造 2 个任务/3 个 attempt，
断言指标口径（含“无错误码的失败”把可诊断率拉低）、`query/show/stats` 子进程输出、
导出 NDJSON 首行 session + 工具/步骤/终结事件、草稿判据与越界拒绝；已注册进 `verify-all`。

## 十六、故障演练与可诊断率（2026-11-26，P6-4 已落地）

> 目标：11 类故障都能在 5 分钟内回答“停在哪、为什么、下一次看哪”。
> 确定性演练入口：`node scripts/verify-drills.mjs`（12 个断言，已注册 `verify-all`）。

### 16.1 11 类故障与注入点

| # | 故障类 | 注入点（真实模块） | 期望 code · phase | 验收形态 |
|---|---|---|---|---|
| 1 | 网关适配器断连 | `TransportError('unavailable')` → outbox | `delivery-retry` · `deliver` | 重试吸收，不产生失败回执；行保持 `pending` |
| 2 | 模型超时 / 429 | dsh stub 挂起或 `turn_end` error | `timeout` / `rate_limited` · `execute` | 失败回执 + `/diag` |
| 3 | 沙箱拒绝 | dsh stub 报 `sandbox-denied` | `sandbox-denied` · `execute` | 失败回执 + `/diag` |
| 4 | 磁盘配额满 | `perTaskLimitBytes=1` | 采集丢弃 `task-quota` | 业务仍 `succeeded`，丢弃可计量 |
| 5 | SQLite busy | 第二连接 `BEGIN EXCLUSIVE` | 采集丢弃 `store-error` | 业务不受影响，解锁后恢复写入 |
| 6 | worktree prepare 失败 | `prepareCmd='exit 7'` | `prepare-failed` · `isolation` | 失败回执 + `/diag` + 导出 |
| 7 | commit 失败 | 任务 worktree 缺失 | `commit-failed` · `isolation` | 失败回执 + `/diag` + 导出 |
| 8 | Verifier 失败 | `file_exists` 指向不存在文件 | `verification-failed` · `verify` | 失败回执 + `/diag` + 导出 |
| 9 | 合并冲突 | 真实 git 两分支冲突 | `merge-conflict` · `merge` | 状态 `conflict`，`/diag` + 导出可见 |
| 10 | 投递失败（终态） | `TransportError('rejected')` | `delivery-failed` · `deliver` | outbox `failed`，`/diag` + 导出可见 |
| 11 | 进程中途崩溃 | 租约过期后 `worker.recover()` | `lease-expired` · `attempt` | 孤儿 attempt 收敛，`/diag` + 导出可见 |

- 第 1/4/5 类是**基础设施故障**：设计上不产生任务失败，验收改为“fail-open + 可计量”
  （§2.2/§5.5）。其余 8 类都是任务级失败，统一断言回执 ≤4 行、`/diag` 三要素、
  attempt 行 `errorCode`/`traceId` 非空、导出含停止点。
- 第 9 类走人工合并路径，没有用户回执；验收以 `/diag` 与导出为准。

### 16.2 为满足可诊断率补齐的三个缺口

1. **具体错误码透传**：executor 的 `ExecFailure` 新增 `errorCode`，`timeout`、
   `rate_limited`、`sandbox-denied`、`lease-lost`、`budget-exceeded` 等不再退化成
   `unknown`；worker 写入 attempt 时优先使用它。
2. **prepare 失败带码**：隔离 resolver 的 prepare 失败抛 `code='prepare-failed'`，
   不再只落到通用的 `workdir-resolver`。
3. **崩溃可诊断**：`worker.recover()` 在租约过期的同一轮关闭孤儿 attempt
   （`outcome=failed`、`errorCode=lease-expired`）并写 `attempt.finished` 事件；
   此前这类失败没有任何错误码。
4. **合并冲突升级为 error**：`merge.conflict` 由 `warn` 改为 `error`，否则 `/diag`
   的“最后错误”看不到它。
5. **回执阶段取根因**：`enrichFailureReceipt` 不再取“最新 error”（会被
   `attempt.finished` 覆盖），而是按 `verify/isolation/merge/delivery > tool >
   execute` 取根因阶段；真机验收因此从“阶段：尝试”修正为“阶段：验证”。

### 16.3 可诊断率口径

失败 attempt 中 `errorCode` 与 `traceId` 均非空的比例必须为 **100%**：

- `traceId` 来自 `tasks.correlation_id`，创建任务时默认 `uuidv7`，不会为空；
- `errorCode` 由失败路径显式写入，缺省回退到 failure kind，再兜底 `unknown`；
- `scripts/trace.mjs stats` 的“可诊断 x/y（%）”与 `verify-drills` 的断言共用同一口径。
