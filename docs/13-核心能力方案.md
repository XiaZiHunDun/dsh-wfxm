## 一、两个痛点的失败模式拆解

### 1.1「对话和记忆不乱」不是一件事

| 子问题 | 症状 | 主解 | 是 RAG 吗 |
|---|---|---|---|
| **上下文腐化** | 聊久了忘事、风格漂移 | 分层上下文装配 + 硬配额 | ❌ |
| **跨项目污染** | A 项目的规则漏进 B 的会话 | 作用域硬隔离（`project_id` 绑定） | ❌ |
| **事实冲突** | 记忆里同时存着旧 IP 和新 IP | 事实卡：版本化、只取代不删除 | ❌ |
| **检索不中** | 存了但找不到 | 混合检索（FTS5 优先，向量条件触发） | ✅ |

> **RAG 只解决第四项。** 前三项靠"写入纪律 + 作用域 + 装配预算"，比换向量库重要得多。

### 1.2「任务成功率」是五个环节的乘积

| 环节 | 典型失败 | 手段 | 归属 |
|---|---|---|---|
| 理解 | 意图歧义、选错工具 | 计划级确认 | 内核 ② + ③ |
| 选路 | 用最脆弱的方式（点页面 vs 调 API） | **确定性优先（选路梯子）** | 内核 ② |
| 执行 | 工具报错、页面改版 | 重试分级 + 幂等键 | 端口错误分类 |
| 长任务 | 中断、状态丢失 | 持久队列 + 租约 | 任务 ⑤ |
| **结局** | 改坏系统 / **静默错**（返回成功但结果错） | **前置快照 + 任务级验证** | 任务 ⑤ + 运维 ⑦ |

> **核心判断**：成功率不靠更强的模型，靠三件事——**减少可失败环节、失败可检测、失败可恢复**。

## 二、对话与记忆不乱（四条机制）

### 2.1 分层上下文装配 + 硬配额

挂在 `system-prompt/assemble`（11 §三 编排策略·上下文构建）。

| 块 | 内容 | 预算上限 | 超预算时 |
|---|---|---|---|
| 固定块 | 身份、规则、当前项目约束 | 20% | 不可裁 |
| 检索块 | 相关记忆，**带来源与时效** | 30% | **先裁这块** |
| 近期对话 | 窗口 | 35% | 按轮次裁 |
| 任务块 | 当前计划、进度、约束 | 15% | 不可裁 |

**不可裁的两块**是防"越聊越糊"的底线：规则与任务目标永远在。

### 2.2 作用域硬隔离

- 每个会话绑定 `project_id`；检索默认只在本项目
- 跨项目检索必须显式（对应 08 决策 #3：默认隔离，分层共享后置）
- 隔离的检验方式：**建两个项目各写一条事实，在 A 的会话里问 B 的事实，必须检索不到**

### 2.3 事实卡（代替自由文本记忆）

**表结构（属于模块 ⑥ 记忆，唯一写者）**

| 字段 | 含义 |
|---|---|
| `subject` / `predicate` / `value` | 三要素（"本项目的包管理器" = pnpm） |
| `scope` | `project` / `global` |
| `source` | `user-confirmed` / `observed`（工具观测）/ `inferred`（模型推断） |
| `valid_from` / `superseded_by` | **只取代不删除** |
| `confidence` | 仅 `inferred` 需要 |

**五条写入纪律**

1. **唯一写者**：只有模块 ⑥ 能写（AR23）
2. **只取代、不删除**：旧值标 `superseded_by`，历史可回溯
3. **来源分级**：`inferred` **不得直接提升为事实**，需一次确认
4. **冲突不静默**：同 `subject+predicate` 出现多条 active → 巡检告警，不自动择一
5. **事实体检**作为巡检项（见 2.5）

### 2.4 压缩有损可控

- 摘要**写回记忆并标 `source=summary`**，不是直接丢弃
- **计划、审批、变更**三类记录**不参与压缩**
- 压缩后必须保留"为什么这么决定"（决策理由），否则下次会重复犯同样的错

### 2.5 事实体检（把记忆治理变成巡检，而不是靠人自觉）

作为运维域（模块 ⑦）的固定巡检项，检查四类：

| 检查 | 阈值/动作 |
|---|---|
| 冲突 | 同 subject+predicate 多条 active → 告警，交给 owner 择一 |
| 过期 | `valid_from` 超过 N 天且未被观测确认 → 标记待复核 |
| 无来源 | 缺 `source` 的记录 → 拒绝写入（写时校验） |
| 孤儿 | 指向已注销项目的记忆 → 归档，不删除 |

### 2.6 存储选择

| 方案 | 结论 | 理由 |
|---|---|---|
| **SQLite：`memory_facts` + `memory_edges` + 递归 CTE** | **采用** | 节点千级、多跳深度 ≤3，CTE 足够 |
| **Kùzu**（嵌入式图库，单文件、Cypher、无服务进程） | **备选（L2）** | 真需要图查询时的首选，不是 Neo4j |
| Neo4j / JanusGraph | **不采用** | 多一个进程、备份、升级面，收益不成比例 |
| **GraphRAG** | **事实层不采用** | LLM 抽取会制造幻觉事实、结果难校正、每次重建烧 token；而端口/路径这类事实必须精确 |
| GraphRAG / 向量 RAG | **知识层可用** | 运维手册、会议纪要、历史任务摘要属于"模糊检索"，可接受 |

**两层分开**：

```
事实层（结构化、人工/观测确认）→ SQLite 表 + 边表           精确、可审计
知识层（非结构化文档、纪要）    → Markdown + FTS5（可选向量）  模糊、可检索
```

> **别用一种存储解决两类对象。** 这是"自维护会不会乱"的真正答案：乱的根因在写入纪律，不在库。

## 三、任务成功率（六条机制，按收益排序）

| # | 机制 | 解决 | 可行性 | 落点 |
|---|---|---|---|---|
| 1 | **任务级验证（Verifier）** | 静默错、假成功 | 高 | 任务 ⑤：每条任务带可执行断言 |
| 2 | **R3 前置快照 + 回滚** | 改坏不可逆 | 高 | 运维 ⑦ + restic |
| 3 | **重试分级 + 幂等键** | 重复执行、无限重试 | 高 | 端口错误分类 → 任务层策略 |
| 4 | **Transactional Outbox** | 回执/审计静默丢 | 高 | 业务库单表 + 投递器 |
| 5 | **失败即回归** | 同类错误反复犯 | 高（宿主现成） | `llm-replay` + `session-snapshot` |
| 6 | 计划 DAG + 前置/后置条件 | 选错路径 | 中 | 宿主 `plan-mode` 打底 |

### 3.1 Verifier 断言（最大缺口）

每条任务在**提交时**声明"怎么算成功"，执行后自动校验：

```
成功判据（可执行，不是自然语言）
  exit_code == 0
  service_active("nginx")            # SvcOpsPort.status
  port_listening(8080)
  file_exists("/etc/nginx/conf.d/x.conf")
  git_diff_matches(pr)
  page_contains("#dashboard .title")
```

- **无判据的任务**：只能执行 R0–R1（只读 / 局部可逆），不允许 R2+
- 判据失败 → 按端口错误分类决定"重试 / 升级给人 / 回滚"
- 判据结果进审计（AR15：无审计即未完成）

> 08 有 N4（契约测试），但**没有"任务级成功判据"**——这是本文补的 O3。没有它，成功率无从度量，也就无从改进。

### 3.2 Outbox

写业务库时**同事务**写一条 outbox 记录，再由投递器发出（通知 / 审计 / 看板投影）。

解决的是最隐蔽的一类失败：**任务成功了，但回执没发、审计没落**——用户以为没执行，实际执行了。

### 3.3 重试分级

| 端口错误 | 任务层动作 |
|---|---|
| `Transient`（超时、限流、网络抖动） | 指数退避重试，**必须带幂等键**；超上限转 `Failed` |
| `PermissionDenied` / `NotFound` / `InvalidInput` | **不重试**，直接升级给人 |
| `Conflict` | 先对账（是否已生效），再决定重试或升级 |

## 四、专家系统：领域能力外包，治理自留

### 4.1 为什么必须外包

让单一运行时把所有领域打磨到高成功率是不现实的。方向是**编排优于自建**的纵向版本：
横向用 MCP 接工具，纵向用专家接领域（编码、浏览器、邮件等）。

### 4.2 但专家必须以「受限执行器」接入（ExpertExecutor）

| 约束 | 要求 | 违反的后果 |
|---|---|---|
| **无自有审批** | 它内部的问询一律无效；R3 动作回到我们的闸 | 治理被穿透 |
| **无自有凭据** | 凭据逐操作注入，拿不到明文 | 凭据外泄 |
| **不得出 A 域** | 只在工作区活动；主机/出网由我们的适配器代做 | 越域 |
| **事件必须回传** | 工具调用转成我们的审计事件 | 审计断链 |
| **无状态** | 上下文由我们装配（记忆/规则/审批历史不交给它） | 又变成"对话乱" |
| **接入方式** | 优先 CLI，其次 MCP，再次 A2A | 不可观测 |

> A2A 的位置**修正**：它的价值不在 agent 间自由协商，而在**把第三方专家 agent 当工具接入**。
> 仍不做 agent 间自由协商——那是不可控的涌现行为。

### 4.3 领域路由（内核 ②，不是适配器）

```
S1 规则（项目类型 / 显式指令 / 工具可用性）──命中──▶ 路由到专家
        │ 不确定
        ▼
项目默认专家（项目注册时声明）
        │ 仍无
        ▼
问一次（"交给编码专家，还是我自己做？"）──▶ 写回项目默认
```

- **路由表是可学习的映射**，不是每轮推理
- 路由判断错 = 全盘错，所以**规则优先、确认兜底**

### 4.4 试点顺序

先接**编码类**专家（最容易验证，有明确成功判据：测试通过 / diff 匹配），跑通 `ExpertExecutor` 的治理穿透，
再接浏览器类，最后才是邮件/生活类（那些更依赖账号与页面状态）。

## 五、技术评估结论

| 技术 | 结论 | 一句话理由 |
|---|---|---|
| RAG（混合检索） | **采用，但降级为增强项** | 语料偏结构化，FTS5 优先；向量只在召回不足时启用 |
| 图数据库 | **不采用**（Kùzu 备选） | 深度 ≤3、节点千级，CTE 足够；多一个进程不值得 |
| GraphRAG | **仅知识层** | 事实层用 LLM 抽取会制造幻觉 |
| 分布式系统 | **不采用** | 单机单 owner；但借四个概念：事件溯源 / 租约 / 幂等 / **Outbox** |
| A2A | **仅作专家接入协议**，不做协商 | 成功率的瓶颈在执行与验证，不在 agent 握手 |

## 六、落地顺序与度量

| 阶段 | 内容 | 度量 |
|---|---|---|
| **P0 保命** | 治理链 + 任务运行时 + **Verifier 断言** + 前置快照 + 重试分级 + Outbox | 失败可检测率、可回滚率 |
| **P1 外包** | `ExpertExecutor` 接口 + 一个编码专家试点 | 专家任务成功率 ≥ 自建基线 |
| **P2 不乱** | 分层装配 + 项目隔离 + 事实卡 + 事实体检 | 跨项目污染 = 0；冲突事实可追 |
| **P3 增强** | 混合检索（向量条件触发）+ 失败回归库 + 领域路由表 | 同类失败复发率下降 |

**顺序不能反**：先有闸与验证，才敢外包；否则专家一进来就把治理穿透了。
