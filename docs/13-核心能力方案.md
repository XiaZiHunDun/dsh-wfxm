## 一、两个痛点的失败模式拆解

### 1.1「对话和记忆不乱」不是一件事

| 子问题 | 症状 | 主解 | 是 RAG 吗 |
|---|---|---|---|
| **上下文腐化** | 聊久了忘事、风格漂移 | 分层上下文装配 + 硬配额 | ❌ |
| **跨项目污染** | A 项目的规则漏进 B 的会话 | 作用域硬隔离（`project_id` 绑定） | ❌ |
| **事实冲突** | 记忆里同时存着旧 IP 和新 IP | 事实卡：版本化、只取代不删除 | ❌ |
| **检索不中** | 存了但找不到 | 混合检索（FTS5 优先，向量条件触发） | ✅ |

> **RAG 只解决第四项。** 前三项靠"写入纪律 + 作用域 + 装配预算"，比换向量库重要得多。

### 1.2「任务成功率」是五个环节的乘积

| 环节 | 典型失败 | 手段 | 归属 |
|---|---|---|---|
| 理解 | 意图歧义、选错工具 | 计划级确认 | 内核 ② + ③ |
| 选路 | 用最脆弱的方式（点页面 vs 调 API） | **确定性优先（选路梯子）** | 内核 ② |
| 执行 | 工具报错、页面改版 | 重试分级 + 幂等键 | 端口错误分类 |
| 长任务 | 中断、状态丢失 | 持久队列 + 租约 | 任务 ⑤ |
| **结局** | 改坏系统 / **静默错**（返回成功但结果错） | **前置快照 + 任务级验证** | 任务 ⑤ + 运维 ⑦ |

> **核心判断**：成功率不靠更强的模型，靠三件事——**减少可失败环节、失败可检测、失败可恢复**。

## 二、对话与记忆不乱（四条机制）

### 2.1 分层上下文装配 + 硬配额

挂在 `system-prompt/assemble`（11 §三 编排策略·上下文构建）。

| 块 | 内容 | 预算上限 | 超预算时 |
|---|---|---|---|
| 固定块 | 身份、规则、当前项目约束 | 20% | 不可裁 |
| 检索块 | 相关记忆，**带来源与时效** | 30% | **先裁这块** |
| 近期对话 | 窗口 | 35% | 按轮次裁 |
| 任务块 | 当前计划、进度、约束 | 15% | 不可裁 |

**不可裁的两块**是防"越聊越糊"的底线：规则与任务目标永远在。

**压缩预算与切点（区分"dsh 已有"与"我们要补"）**

dsh `@deepseek-ai/dsh-compaction-basic` 已提供，直接用、不重造（[09 F2](09-能力对照与实现路径.md)）：

- 阈值取 `min(窗口 × thresholdRatio, 窗口 − 预留输出 − headroom)`，并校验 `retainTokens < thresholdTokens`
- 保留近期按 `retainRatio` / `retainTokens`
- 切点由 tool-call/result 配对平衡决定，不会切在未完成的工具调用中间

**我们要补的只有三条**（dsh 没有，或只靠提示词不确定）：

1. **超长单轮**：dsh 明确不能拆分不可分单元（如一次超大工具调用）；我们要求**摘要前缀 + 保留后缀**，不整轮丢。
2. **前缀摘要必须列在飞工作**（运行中任务、子代理、heartbeat、goal），否则压缩后重复派工。
3. **摘要不含事实卡**：事实按 §2.3 冷边界重投，避免摘要里出现旧版本事实。

> 机制参考：dsh [compaction-basic/src/config.ts](file:///home/ailearn/githubpro/deepseek-harness/packages/compaction/compaction-basic/src/config.ts#L191-L204)（阈值与 retain 校验）、[tool-pairing.ts](file:///home/ailearn/githubpro/deepseek-harness/packages/compaction/compaction/src/tool-pairing.ts)（切点平衡）；
> 超长单轮处理参考 prime-agent [compaction.rs](file:///home/ailearn/githubpro/prime-agent/crates/pa-core/src/session_engine/compaction.rs)。

**装配作用域（v2，C 方案：一个前台、按 Thread 装）**

| 会话 | 装配键 | 装什么 | 不装什么 |
|---|---|---|---|
| `orchestrator`（唯一前台） | `owner` + 当前 Thread | 当前议题近轮、锚定任务的**摘要**（id / 阶段 / 在等谁）、待确认事项、本项目事实 | 其它 Thread 的对话、全量历史、任务完整计划 |
| `task`（worker） | `task_id` | 计划 DAG、断言、预算、本任务专属上下文 | 其它任务、前台闲聊 |
| `chat`（仅 Web 深度会话） | `project_id` | 当前对话目标 + 待办 | 完整计划 |

> **前台只有一个会话，但上下文不混**：同一会话承载多个议题时，靠装配边界隔离，不靠"换 session"。
> 裁剪顺序不变（检索块先裁），且裁剪必须留 `decisions.reason`。

### 2.2 作用域硬隔离

- 每个会话绑定 `project_id`；检索默认只在本项目
- **`orchestrator` 单轮装配只允许一个 `project_id`**；切换项目即切换装配作用域，不把两个项目的事实混进同一轮
- **跨项目边界已定（08 §七 #3）**：**项目事实隔离、偏好共享**
  - `scope=project` 的事实只在所属项目可见；跨项目读取必须显式发起
  - `kind=preference` 恒为全局（`scope=global`、`projectId` 必须为空）；带 `projectId` 的偏好**拒写**——否则会出现"同名不同值"的假隔离，用户习惯被项目切碎
  - 项目上下文读取 = **全局偏好 ∪ 本项目事实**，永不返回其他项目的行；无项目上下文时**只读全局**
  - 落地位置：⑥ 写时校验（`prepareFact`）+ `liveFacts({ forProject })` + `mem_facts` 的读取作用域（无 `projectId` 默认 global）
    + **装配点 `projectMemoryContext`（片 3）**：返回本轮的 `{ projectId, project, facts, fingerprint }`，
      未知/归档项目 **拒绝装配**（`not-found`），不回退成全局（回退会静默换作用域）；`fingerprint` 供冷边界防重（§2.3）
- 隔离的检验方式：**建两个项目各写一条事实，在 A 的会话里问 B 的事实，必须检索不到**

### 2.3 事实卡（代替自由文本记忆）

**表结构（属于模块 ⑥ 记忆，唯一写者）**

| 字段 | 含义 |
|---|---|
| `subject` / `predicate` / `value` | 三要素（"本项目的包管理器" = pnpm） |
| `scope` | `project` / `global` |
| `source` | `user-confirmed` / `observed`（工具观测）/ `inferred`（模型推断） |
| `kind` | `environment`（可探针核验：路径 / unit / 端口 / 版本 / 包管理器）/ `preference`（偏好，只能 owner 确认） |
| `evidence` | 仅 `environment` 必填：`{ probe, value, observed_at, fingerprint }`；探针输出截断 ≤200 字符 |
| `valid_from` / `superseded_by` | **只取代不删除** |
| `confidence` | 仅 `inferred` 需要 |

**五条写入纪律**

1. **唯一写者**：只有模块 ⑥ 能写（AR23）
2. **只取代、不删除**：旧值标 `superseded_by`，历史可回溯
3. **来源分级 + 确认方式**：`inferred` **不得直接提升为事实**；`kind=environment` 须经一次只读探针核验（`observed` 亦然），`kind=preference` 只能由 owner 确认。核验三态：**吻合**→写入；**矛盾**→拒绝并记原因（不删旧值）；**探不到**→写入但标 `unverified`，由 §2.5 兜底
4. **冲突不静默**：同 `subject+predicate` 出现多条 active → 巡检告警，不自动择一
5. **事实体检**作为巡检项（见 2.5）

> **落地（2026-11-09，⑥ 第一片）**：`@dsh-wfxm/knowledge` 已把纪律 2/3 变成代码——`kind=environment` 缺 `evidence` 拒写、
> `scope=project` 缺 `projectId` 拒写、`inferred` 缺 `confidence` 拒写；三态闸按**吻合→写入 / 矛盾→拒绝且不删旧值 / 探不到→写入并标 `unverified`** 执行，
> 探针只读且 fail-soft（异常按 `unverified`）。当前只接了 `path` 探针，`unit` / `port` / 版本类谓词待 ⑦ 探针接线，**在此之前不得宣称"环境类事实已可核验"**。

**注入策略（冷边界 + 指纹，避免"每轮复读"）**

| 规则 | 要求 |
|---|---|
| 投递时机 | 只在冷边界：会话创建、恢复、压缩后首轮；**不进每轮装配** |
| 防重 | 摘要消息带指纹（本次投递的事实版本集合哈希）；已投递过的不再注入 |
| 排序 | 当前目标（权重 3）+ 最近 4 条用户/助手文本（递减权重），词上限 48 |
| 截断 | 单条 ≤140 字符、每次 ≤3 条、历史 ≤10 条；超限先丢低权重 |
| 开关 | 关闭只影响模型上下文，**不删事实**；历史仍可检索 |

> 机制参考：prime-agent [harness_digest.rs](file:///home/ailearn/githubpro/prime-agent/crates/pa-core/src/session_engine/harness_digest.rs)（冷边界投递/指纹/排序）与 [planner.rs](file:///home/ailearn/githubpro/prime-agent/crates/pa-core/src/refinement/planner.rs)（条目类型与校验）。
> 事实卡仍以 15 的 `memory_facts` 为准，本节只约束"怎么进提示"。

### 2.4 压缩有损可控

- 摘要**写回记忆并标 `source=summary`**，不是直接丢弃
- **计划、审批、变更**三类记录**不参与压缩**
- 压缩后必须保留"为什么这么决定"（决策理由），否则下次会重复犯同样的错
- 摘要必须列出**未完成工作**（任务/子代理/heartbeat/goal）；事实卡不进摘要，按 2.3 的冷边界重投

### 2.5 事实体检（把记忆治理变成巡检，而不是靠人自觉）

作为运维域（模块 ⑦）的固定巡检项，检查五类：

| 检查 | 阈值/动作 |
|---|---|
| 冲突 | 同 subject+predicate 多条 active → 告警，交给 owner 择一 |
| 过期 | `valid_from` 超过 N 天且未被观测确认 → 标记待复核 |
| 无来源 | 缺 `source` 的记录 → 拒绝写入（写时校验） |
| 孤儿 | 指向已注销项目的记忆 → 归档，不删除 |
| **失效** | `kind=environment` 的事实复探不符（路径没了 / unit 不在 / 端口未监听 / 版本已变）→ 标 `stale` 待复核，**不自动取代**（A2，随 ⑥ 实施） |

**复核候选（D19-4=B）**：active 事实记录 `last_injected_at`；超过 **30 天**未被装配引用 → 进体检报告的「复核候选」清单。
**只提示、不降权、不自动归档**——"没被引用" ≠ "没用"（可能是任务类型未覆盖或注入位次靠后），
自动降权会形成"降权→更不会被用→再降权"的自我强化式淘汰。

> **落地（2026-11-09）**：五类检查与复核候选已在 `@dsh-wfxm/knowledge`（`mem_health`，R0）实现，
> 全部只读、不改写事实：`stale` 只报告不取代，探针不可用只计数（`probeUnavailable`）不算失效。

### 2.6 存储选择

| 方案 | 结论 | 理由 |
|---|---|---|
| **SQLite：`memory_facts` + `memory_edges` + 递归 CTE** | **采用** | 节点千级、多跳深度 ≤3，CTE 足够 |
| **Kùzu**（嵌入式图库，单文件、Cypher、无服务进程） | **备选（L2）** | 真需要图查询时的首选，不是 Neo4j |
| Neo4j / JanusGraph | **不采用** | 多一个进程、备份、升级面，收益不成比例 |
| **GraphRAG** | **事实层不采用** | LLM 抽取会制造幻觉事实、结果难校正、每次重建烧 token；而端口/路径这类事实必须精确 |
| GraphRAG / 向量 RAG | **知识层可用** | 运维手册、会议纪要、历史任务摘要属于"模糊检索"，可接受 |

**两层分开**：

```
事实层（结构化、人工/观测确认）→ SQLite 表 + 边表           精确、可审计
知识层（非结构化文档、纪要）    → Markdown + FTS5（可选向量）  模糊、可检索
```

> **别用一种存储解决两类对象。** 这是"自维护会不会乱"的真正答案：乱的根因在写入纪律，不在库。

## 三、任务成功率（六条机制，按收益排序）

| # | 机制 | 解决 | 可行性 | 落点 |
|---|---|---|---|---|
| 1 | **任务级验证（Verifier）** | 静默错、假成功 | 高 | 任务 ⑤：每条任务带可执行断言 |
| 2 | **R3 前置快照 + 回滚** | 改坏不可逆 | 高 | 运维 ⑦ + restic |
| 3 | **重试分级 + 幂等键** | 重复执行、无限重试 | 高 | 端口错误分类 → 任务层策略 |
| 4 | **Transactional Outbox** | 回执/审计静默丢 | 高 | 业务库单表 + 投递器 |
| 5 | **失败即回归** | 同类错误反复犯 | 高（宿主现成） | `llm-replay` + `session-snapshot` |
| 6 | 计划 DAG + 前置/后置条件 | 选错路径 | 中 | 宿主 `plan-mode` 打底 |

> 上表按**收益**排序；下文小节按**实现顺序**展开：Outbox（3.2）与重试分级（3.3）先写，因为回执与审计依赖它们；快照（3.4）随 R3 动作落地。

### 3.1 Verifier 断言（最大缺口）

每条任务在**提交时**声明"怎么算成功"，执行后自动校验：

```
成功判据（可执行，不是自然语言）
  exit_code == 0
  service_active("nginx")            # SvcOpsPort.status
  port_listening(8080)
  file_exists("/etc/nginx/conf.d/x.conf")
  git_diff_matches(pr)
  page_contains("#dashboard .title")
```

- **无判据的任务**：只能执行 R0–R1（只读 / 局部可逆），不允许 R2+
- 判据失败 → 按端口错误分类决定"重试 / 升级给人 / 回滚"
- 判据结果进审计（AR15：无审计即未完成）

> 08 有 N4（契约测试），但**没有"任务级成功判据"**——这是本文补的 O3。没有它，成功率无从度量，也就无从改进。

> **落地（2026-11-09，⑤ 第一片）**：`@dsh-wfxm/tasks` 已实现七类断言的静态校验（≤8 条、禁 shell 片段与通配、路径必须在允许根内、URL 禁凭据、unit/port/host 可配白名单）与只读求值。
> `file_exists` / `port_listening` / `http_status` / `git_diff_matches` 内置；`service_active` / `unit_restarted` / `page_contains` 必须由 SvcOps / Browser 适配器注入，**缺适配器记 `skipped`**。
> `complete` 只在全部断言 `pass`（R0 可无断言）时允许 `succeeded`；**R1 worktree 任务**在计划未声明断言时，
> worker 于收敛前自动补一条 `git_diff_matches(任务分支, changed)`——分支没有任何改动就判 `verification-failed`
> （2026-11-27，此前 R1 代码任务以 `no-assertions` 通过，只能人工复验）。`skipped` 视为不可判定并拒绝完成；Transient 失败只重测一次；
> `exit_code` 读已记录的执行证据、**不重跑命令**。R2+ 无判据在提交与完成两处都拒绝。重试分级（§3.3）与前置快照（§3.4）尚未接到任务层。

### 3.2 Outbox

写业务库时**同事务**写一条 outbox 记录，再由投递器发出（通知 / 审计 / 看板投影）。

解决的是最隐蔽的一类失败：**任务成功了，但回执没发、审计没落**——用户以为没执行，实际执行了。

**投递器语义（四条）**

- **单投递器 + 租约**：`lease_owner` / `lease_expires_at` 抢占 `pending`，租约过期回收；多实例也不会重复发。
- **ack 判据**：渠道返回成功**且拿到 `external_msg_id`** 才置 `sent`；只有 HTTP 200 不算送达。
- **退避**：`1s → 5s → 30s → 2m → 10m`，6 次后置 `failed` 并告警；`failed` 可在管理面手动重投。
- **幂等**：`outbox.id` 即幂等键，与 `ExecPort` / 渠道调用共用；重投不重复打扰用户。

> **落地（2026-11-09）**：`@dsh-wfxm/gateway` 已按本节实现单投递器——
> 抢占即计一次 attempt（崩溃丢租约也消耗尝试，避免无限循环）、租约过期可被其他 owner 回收、
> transport 未返回 `external_msg_id` 记为失败并重试、6 次后 `failed`、`failed` 可手动重置重投；
> `outbox.id` 作为幂等键传给 transport。**未接真实渠道**：`OutboxTransport` 为注入缝，飞书长连接/卡片回调待 Step 2。

### 3.3 重试分级

| 端口错误 | 任务层动作 |
|---|---|
| `Transient`（超时、限流、网络抖动） | 指数退避重试，**必须带幂等键**；超上限转 `Failed` |
| `PermissionDenied` / `NotFound` / `InvalidInput` | **不重试**，直接升级给人 |
| `Conflict` | 先对账（是否已生效），再决定重试或升级 |

### 3.4 工作区快照（R3 / 步级的"退得回"）

快照不是定期备份，而是嵌在 Agent 循环里的**事务性原语**：任意危险步骤之后能原子回滚，或把确定状态交出去，
而不必重跑前面的回合。触发时机是**语义边界**（R3 判定 / 写工具调用前 / 回合结束），不是定时器。

**三层粒度，叠加使用**（没有一种万能快照能同时满足"开销极低"与"覆盖一切"）

| 层 | 存什么 | 何时触发 | 我们的取舍 |
|---|---|---|---|
| **文件级前镜像** | 单个文件写入前的原文（≤1 MiB 内联，超限走外置引用；文件不存在记 `absent` 墓碑）；恢复用同目录临时文件 + 原子 `replace` | 每次 `write` / `edit` 工具调用**之前** | **做**：`file_preimages`（归 ⑦；④/⑤ 只经端口调用，AR33）。回答"这个文件在本次操作前长什么样" |
| **工作区级** | 整个工作区的逻辑状态 + 基线（git `HEAD tree` / 非 git `manifest`）+ 还原定位 | R3 且会改系统状态；B 域危险命令前 | **做**：`snapshots` 由 ⑦ 产生、⑤ 快照闸强制 |
| **沙箱级（含内存）** | 文件系统 + 运行时状态，用于跨副本恢复 / 冷启动 | 每次 `call()` 结束、沙箱回收前 | **不引入**：单机 systemd、无常驻沙箱池；重启靠重启 + 快照点，不冻结内存 |

> **粒度三"不引入"是决定，不是遗漏**：我们没有 microVM / 热池，"装好依赖的环境秒级就位"由 systemd unit + 依赖锁保证，
> 冷启动不是瓶颈；含内存快照会引入暂停—恢复语义和另一套存储治理，收益不抵成本。

**工作区级（R3 前置快照）**

- **触发**：判为 R3 且会改变系统状态（配置、unit、数据库、发布）。
- **来源**：由 ⑦ 运维域产生，`changes.snapshot_id` 关联；**快照失败即拒绝执行**，不"先做了再说"。
- **还原**：按 `snapshots.locator` 还原；回滚本身也要审批并复验。
- **非 git 工作区必须有自包含的 `locator`**：`manifest:<sha256>` **只是基线校验**，不能单独用于还原；
  `locator` 必须是 `restic:<snapshot>:<subpath>` 或 `dir:<绝对路径>` 之一，**缺 `locator` 的快照创建即失败**（否则 B 域改坏了退不回去）。
- **保留期**：按 `expires_at` 分级（发布前 ≥30 天，临时 ≥7 天）；磁盘水位巡检覆盖快照占用；**每个工作区保留最近 100 个检查点**，超出按时间淘汰。
- **去重与引用计数**：同内容只存一份（`content_key`），检查点只记引用，`ref_count` 归零才删实体；文件级前镜像的**首份**作为基线保留，后续版本可淘汰。
- **超时**：`SnapshotPort.capture` 必须在 `SNAPSHOT_TIMEOUT_MS`（默认 10s）内返回；**超时 = 快照失败 = 拒绝执行**，
  不允许"先跑着、快照稍后到"。工作区级是工具路径上的同步调用；含内存 / 全量打包类快照必须异步化，不阻塞主循环。
- **fail-closed**：将来若引入隔离写层（COW / OverlayFS），**建立失败必须拒绝执行**，禁止静默退化为"无快照直接写"——
  静默失效的快照比没有快照更危险，会让编排层误以为存在回滚点。

**步级回滚（与任务级回滚的关系）**

- 每次写工具调用前落一条 `file_preimages`（`task_id` + `tool_call_id` + `realpath`，18 G6），可选关联当前工作区检查点 `checkpoint_id`。
- 任务失败时先按 `checkpoint_id` 逆序做**步级试回滚**（只动本任务写过的文件），复验通过即止；仍不通过才整任务回滚（`snapshots`）。
  这样第 3 步改坏了，不必重跑第 1–2 步。
- 回滚也受闸：步级回滚只撤销本任务自己的写入、幂等、不跨域，按 R2 处理；整任务 / 跨域回滚按 R3（审批 + 复验）。

**快照有效性校验（失败即拒绝）**

- **基线校验**：git 工作区按 HEAD tree 的 object id 校验，非 git 工作区按 `manifest:<sha256>` 校验（B4-b 串行分支）；不能只信工作区文件。
- **并发变更**：快照期间工作区被改动 → 报 `ConcurrentMutation` 并拒绝继续，不静默取后写值。
- **排除项**：凭据/密钥、嵌套仓库、submodule、symlink 祖先目录不入快照。
- 任一项校验失败 = 快照失败 = **拒绝执行**（不因"先做了再说"放宽）。

**落地位置（2026-11-09）**：`plugins/snapshot`（`@dsh-wfxm/snapshot`，17 例）——`snapshots` + `file_preimages` 两表、
`capturePreimage` / `restorePreimage` / `rollbackPreimages`、`captureWorkspace` / `restoreWorkspace`、`createSnapshotPort`（⑤ 的结构契约）。
**④ 已把前镜像钩进编辑路径**（`plugins/governance/src/preimage/hook.ts`，13 例）：在 `tools/pre-execute` 里，策略放行之后、`next()` 之前
对 `write` / `edit` / `str_replace_editor` 的目标文件取前镜像；**取不到就拒绝这次调用**（`preimage-failed`），不写没有回滚点的文件；
相对路径**跳过而不猜**（hook 拿不到会话 cwd）；可写根之外不取；`policy.yaml` 的 `preimages.enabled=false` 可整体关闭。
`restic:` locator 只做契约校验。
**⑤ → ④ 任务归因已接**：worker 在 `runWithTaskContext` 里跑执行器（`AsyncLocalStorage`），宿主用
`setTaskContextResolver(currentTaskContext)` 接一行，前镜像就带上 `file_preimages.task_id`；**解析器缺失/抛错只丢归因、不丢前镜像**。
**步级 checkpoint 已落（2026-11-09）**：⑤ 的 `task_checkpoints`（`tasks` v5）+ `beginCheckpoint` / `closeCheckpoint(committed|aborted)`；
执行器用 `runWithCheckpoint(id, fn)` 圈住一步，期间的写带 `checkpoint_id`；⑦ 的 `rollbackPreimages({taskId, checkpointId})`
只回这一步、按 `created_at` 逆序（同毫秒用 `rowid` 兜底）。验收：真实 worker 两步写作 → 只回第二步（第一步保持改动）→ 再整任务回滚还原。
**回滚触发入口已落（2026-11-09）**：⑤ 新增 `rollbackTask({taskId, checkpointId?})` + 独立工具 **`task_rollback`（R1）**
（只动本任务写入集合、局部可逆、**必须显式触发**，绝不自动）；端口 `CheckpointRollbackPort` 由 ⑦ 的
`createPreimageRollbackPort(store)` 实现（结构契约，AR33，⑤ 不导入 ⑦ 包）；① 侧 `/rollback` 走 `TaskControlPort`
（可选 `checkpointId`，**绕过 live 闸**以支持任务结束后悔）。回滚后把范围内仍 `open` 的 checkpoint 关为 `aborted`、
写 `task.rollback` 事件；**不改任务状态、不删除任务新建的文件**（只报告 restored）。
**仍未定**："哪算一步"的语义边界归调用方/产品（机制只认 checkpoint 标记）；签名卡片回滚按钮归 v1.1；`open` 未关闭的 checkpoint 需调用方或巡检收尾。**租约过期重试**的任务由 ⑤ 的 `recoverExpiredLeases` 统一关为 `aborted`（2026-11-27）。

> 机制参考：prime-agent [pa-core/README](file:///home/ailearn/githubpro/prime-agent/crates/pa-core/README.md) 的 `create_workspace_snapshot`（基线校验、并发变更、排除规则）。

### 3.5 失败即回归（把失败变成用例）

- `failed` 且带断言证据的任务，落一条**回归样例**：输入、执行路径、期望判据。
- 样例进宿主的 `llm-replay` / `session-snapshot`，同类任务先跑回归，再跑新路径。
- 度量：**同类失败复发率**（P3 阶段的验收指标）。

### 3.6 计划 DAG 与前后置条件（选错路径的兜底）

- **MVP 不做通用 DAG 引擎**：用宿主 `plan-mode` 的线性计划 + 每步断言即可。
- 只有出现"并行分支 + 依赖"的真实需求才升级（条件触发，见 [12 §六](12-技术栈选型.md)）。
- 每一步必须声明**前置条件**（可执行）与**后置断言**，缺一条则不允许 R2+。

## 四、专家系统：领域能力外包，治理自留

### 4.1 为什么必须外包

让单一运行时把所有领域打磨到高成功率是不现实的。方向是**编排优于自建**的纵向版本：
横向用 MCP 接工具，纵向用专家接领域（编码、浏览器、邮件等）。

### 4.2 但专家必须以「受限执行器」接入（ExpertExecutor）

| 约束 | 要求 | 违反的后果 |
|---|---|---|
| **无自有审批** | 它内部的问询一律无效；R3 动作回到我们的闸 | 治理被穿透 |
| **无自有凭据** | 凭据逐操作注入，拿不到明文 | 凭据外泄 |
| **不得出 A 域** | 只在工作区活动；主机/出网由我们的适配器代做 | 越域 |
| **事件必须回传** | 工具调用转成我们的审计事件 | 审计断链 |
| **寻址受限** | 只允许 parent / sibling / child 家族寻址；禁止广播与位置参数混用 | 消息误投、越权传播 |
| **消息配额** | 单条 ≤16KB、单会话 pending ≤20、每发送者 3 突发 + 1/秒；超限拒收并记审计 | 刷屏、审计膨胀 |
| **无状态** | 上下文由我们装配（记忆/规则/审批历史不交给它） | 又变成"对话乱" |
| **接入方式** | 优先 CLI，其次 MCP，再次 A2A | 不可观测 |

> A2A 的位置**修正**：它的价值不在 agent 间自由协商，而在**把第三方专家 agent 当工具接入**。
> 仍不做 agent 间自由协商——那是不可控的涌现行为。

### 4.3 领域路由（内核 ②，不是适配器）

```
S1 规则（项目类型 / 显式指令 / 工具可用性）──命中──▶ 路由到专家
        │ 不确定
        ▼
项目默认专家（项目注册时声明）
        │ 仍无
        ▼
问一次（"交给编码专家，还是我自己做？"）──▶ 写回项目默认
```

- **路由表是可学习的映射**，不是每轮推理
- 路由判断错 = 全盘错，所以**规则优先、确认兜底**

### 4.4 试点顺序

先接**编码类**专家（最容易验证，有明确成功判据：测试通过 / diff 匹配），跑通 `ExpertExecutor` 的治理穿透，
再接浏览器类，最后才是邮件/生活类（那些更依赖账号与页面状态）。

## 五、技术评估结论

| 技术 | 结论 | 一句话理由 |
|---|---|---|
| RAG（混合检索） | **采用，但降级为增强项** | 语料偏结构化，FTS5 优先；向量只在召回不足时启用 |
| 图数据库 | **不采用**（Kùzu 备选） | 深度 ≤3、节点千级，CTE 足够；多一个进程不值得 |
| GraphRAG | **仅知识层** | 事实层用 LLM 抽取会制造幻觉 |
| 分布式系统 | **不采用** | 单机单 owner；但借四个概念：事件溯源 / 租约 / 幂等 / **Outbox** |
| A2A | **仅作专家接入协议**，不做协商 | 成功率的瓶颈在执行与验证，不在 agent 握手 |

## 六、落地顺序与度量

| 阶段 | 内容 | 度量 |
|---|---|---|
| **P0 保命** | 治理链 + 任务运行时 + **Verifier 断言** + 前置快照 + 重试分级 + Outbox | 失败可检测率、可回滚率 |
| **P1 外包** | `ExpertExecutor` 接口 + 一个编码专家试点 | 专家任务成功率 ≥ 自建基线 |
| **P2 不乱** | 分层装配 + 项目隔离 + 事实卡 + 事实体检 | 跨项目污染 = 0；冲突事实可追 |
| **P3 增强** | 混合检索（向量条件触发）+ 失败回归库 + 领域路由表 | 同类失败复发率下降 |

**顺序不能反**：先有闸与验证，才敢外包；否则专家一进来就把治理穿透了。
