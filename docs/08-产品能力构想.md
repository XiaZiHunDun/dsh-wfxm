# 08 — 产品能力构想

> **本文只定义"产品应该有什么"，不带任何实现考虑。**
> 与 dsh/Butler 的能力对照是**下一篇**（`09-能力对照与实现路径`）的事。
> 这样做的目的：避免"实现有什么就设计什么"，也避免"设计很好但实现接不住"时误判。

---

## 一、产品定位

> **一句话**：一个跑在自己服务器上的个人总管 —— 既做开发与运维，也管日常生活；用企业微信/飞书（个人微信可选）下达，自主多步执行，每一步可审计。

| 属性 | 含义 |
|---|---|
| **P1 载体** | 企业微信 / 飞书为首要入口，个人微信可作过渡；从手机发起 |
| **P2 体验** | 对标 Claude Code / Cursor：**自主多步执行**，不是问答 |
| **P3 范围** | **服务器全域**，不锁单个项目目录 |
| **P4 并发** | 多项目多会话同时进行，**互不干扰** |
| **P5 管家** | 不只你叫我做，还能主动发现问题、报告、建议 |
| **P6 双域** | **开发/运维是深度，日常生活是广度**：两域共用同一套记忆、权限与审计 |

### 即时消息这个载体会反向塑造能力设计

这是本产品与"终端上的开发助手"最本质的差异，**必须在设计时就考虑**：

| 载���约束 | 对能力的要求 |
|---|---|
| 手机输入慢、容易打错 | **指令要一次到位**——不能指望你像在终端里那样反复微调，能力必须"聪明" |
| 屏幕小、不能横向滚动 | 大输出（diff、日志）不能塞进聊天记录，**要能落成附件让你打开看** |
| 网络随时断 | 长任务**不能绑定一个活着的连接**，要能异步、能恢复 |
| 你不在电脑前 | **确认门槛要高**——你没法盯着屏幕，所以不可逆操作必须先问 |
| 随时被打断（回消息、接电话） | 任务要能**暂停、恢复、纠偏**，而不是打断即丢失 |
| 碎片时间 | 任务要能**排队**，回来能看到"还有几件事没做完" |

> 这六条会反复出现在后面的能力设计里。看到某项能力时，回想它是否适配这些约束。

## 二、能力总览

| 域 | 回答什么问题 | 能力项数 |
|---|---|---|
| **A 接入与交互** | 我怎么跟它说话、它怎么回我 | 7 |
| **B 理解与定位** | 它得先搞清楚状况才能动手 | 6 |
| **C 执行** | 它到底能碰到什么 | 7 |
| **D 任务编排** | 它能不能自己把事做完 | 8 |
| **E 多项目与隔离** | 多个项目同时干会不会打架 | 6 |
| **F 记忆与知识** | 它能不能记住、能不能忘掉 | 6 |
| **G 管家主动性** | 它会不会自己动 | 5 |
| **H 治理与信任** | 我敢不敢把服务器全域交给它 | 7 |
| **I 可靠性与可观测** | 出问题时我看得懂吗 | 5 |
| **J 日常生活** | 工作之外的事它能不能管 | 12 |

## 三、逐域展开

### A. 接入与交互 —— "我怎么跟它说话"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| A1 | **单条消息下达指令** | 一句话说清一件事，不需要来回解释 | 必须 |
| A2 | **多轮保持上下文** | 它记得这次对话的前文 | 必须 |
| A3 | **主动推送结果** | 任务完成/需要决策时主动找你，不等你问 | 必须 |
| A4 | **富媒体输出** | 大 diff、日志、图片、文件能作为附件给你打开 | 必须 |
| A5 | **长任务进度可见** | 跑到一半你能看到"现在在干什么"，而不是干等 | 应该 |
| A6 | **中断与纠偏** | 你能随时打断它、纠正方向，已做的不白做 | 应该 |
| A7 | **异步与恢复** | 关掉手机/换设备，任务不受影响；回来能接着 | 应该 |
| A8 | **多模态输入** | 语音、截图、图片、文件都能作为指令的输入 | 必须 |

**关键设计点**
- A4 是**载体决定的**：微信聊天记录不适合放大段内容。大 diff 应该写成文件推给你，而不是刷屏。
- A6 的"已做的不白做"很重要——纠偏不是重来，是在已有进展上调整。
- A7 是异步的前提：**任务状态必须持久化**，不能只活在内存里。

---

### B. 理解与定位 —— "它得先搞清楚状况"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| B1 | **文本/文件搜索** | 找字符串、找文件 | 必须 |
| B2 | **项目结构识别** | 自动知道这是个什么项目、入口在哪、怎么构建 | 必须 |
| B3 | **代码语义理解** | 符号定义/引用/实现/调用关系，而不只是文本匹配 | 应该 |
| B4 | **服务器现状感知** | 有哪些服务在跑、什么配置、端口占用、磁盘水位 | 应该 |
| B5 | **跨项目依赖识别** | A 项目依赖 B 项目吗？改了 A 会不会影响 B | 可以 |
| B6 | **历史决策回忆** | "我们上次为什么这么改" | 可以 |

**关键设计点**
- B3 与 B1 不是一回事。文本搜索回答"哪里出现过"，语义理解回答"谁在调用它"。**Cursor 之所以好用，很大程度是 B3**。
- B4 是"服务器全域"定位的必然要求——你说了是全域，它就该知道全域的状况。
- B5 是多项目场景下最容易踩坑的地方（见 E6）。

---

### C. 执行 —— "它到底能碰到什么"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| C1 | **读文件** | | 必须 |
| C2 | **精确编辑** | 改指定片段，不是整文件重写（保留格式、不误伤） | 必须 |
| C3 | **命令执行** | 一次性命令 | 必须 |
| C4 | **持久 shell** | `cd` 之后状态还在，能设环境变量、进虚拟环境 | 应该 |
| C5 | **版本控制** | diff / 分支 / 提交 | 必须 |
| C6 | **服务操作** | 起停 / 重启 / 看日志 / 看状态 | 应该 |
| C7 | **网络访问** | 拉依赖、调外部 API | 必须 |
| C8 | **测试与验收** | 跑测试、复现问题、用测试证明修好了 | 必须 |
| C9 | **构建与发布** | 构建产物、灰度、发布与回滚 | 应该 |

**关键设计点**
- **C2 是开发代理的生命线**。整文件重写会破坏格式、误伤无关内容，diff 会爆炸。精确编辑能力直接决定"敢不敢让它真的改代码"。
- **C4 是"类似 Claude Code"的具体形态**。一次性命令意味着 `cd project-a && ls && cat x` 要写成一条命令；持久 shell 意味着它可以先 `cd`，然后后面几条都在那个目录。这是两种完全不同的开发体感。
- **C6 是"管家"定位的落点**。只会写代码不会管服务，那只是开发助手，不是管家。

---

### D. 任务编排 —— "它能不能自己把事做完"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| D1 | **自主多步执行** | 一句话下去，它自己读→想→改→跑，不逐步问你 | 必须 |
| D2 | **计划与拆解** | 复杂任务先拆步骤 | 必须 |
| D3 | **长任务** | 跑几分钟到几小时，不需要你盯着 | 必须 |
| D4 | **断点续做** | 中断/重启后能接着做 | 应该 |
| D5 | **并行子任务** | 一个大任务拆给多个执行体并行 | 可以 |
| D6 | **失败重试与降级** | 失败要重试或换路，不能一碰就散 | 必须 |
| D7 | **挂起等待人工决策** | 需要确认时停下来等你，而不是替你决定 | 必须 |
| D8 | **跨会话任务队列** | 断了之后回来能看到"还有什么没做完" | 应该 |
| D9 | **任务对象与回执** | 每次委派是一个可追踪的 Task，结束有 Receipt（证据 + 产物 + 可否回滚） | 必须 |

**关键设计点**
- **D1 和 D7 是一对张力**：默认自主（少打扰），但关键节点必须停下问。**这个平衡点是产品最重要的设计决策之一**，配比错了就是"太啰嗦没人用"或"不敢用"。
- **D6 里的"静默失败"是这个产品最容易翻车的地方**。一个 agent 做不到时，最糟的不是报错，而是假装做完了。

---

### E. 多项目与隔离 —— "多个项目同时干会不会打架"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| E1 | **项目注册与切换** | 它知道有哪些项目，你说"切到 X" | 必须 |
| E2 | **上下文隔离** | A 的对话不会漏进 B | 必须 |
| E3 | **能力隔离** | A 只用 A 该用的工具集 | 必须 |
| E4 | **同项目并行编辑约束** | 两个人/两个会话不静默覆盖同一文件 | 应该 |
| E5 | **项目状态总览** | 有哪些项目、各自进度如何 | 应该 |
| E6 | **跨项目知识的明确边界** | 哪些知识可跨项目共享、哪些不 | 应该 |

**关键设计点**
- **E2/E3/E4 是三种不同的隔离**，不能混谈：
  - E2 是**认知隔离**（它记得什么）
  - E3 是**能力隔离**（它能用什么）
  - E4 是**物理互斥**（同一资源谁在写）
- **E4 容易被忽略**。两个会话同时改同一个文件，能力隔离和上下文隔离都救不了——这是物理冲突。
- **E6 是必须显式决策的产品问题**，不能默认。默认"跨项目共享记忆"会让 agent 在 A 项目里用上 B 项目的错误认知。

---

### F. 记忆与知识 —— "它能不能记住、能不能忘掉"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| F1 | **会话内记忆** | 本次对话的上下文 | 必须 |
| F2 | **长任务上下文管理** | 聊很久也不会把前面的忘了或塞爆 | 必须 |
| F3 | **项目记忆** | 属于某个项目的知识、约定、历史决策 | 应该 |
| F4 | **长期偏好** | 你的习惯、代码风格、常用命令 | 应该 |
| F5 | **知识检索** | 能查回来 | 应该 |
| F6 | **遗忘与过期** | 知识会过时，要有淘汰机制 | 应该 |

**关键设计点**
- **F6 最容易被忽略，也最影响长期体验**。只进不出的知识库半年后就是垃圾场，agent 会引用已经过期的约定，比没有记忆更糟。
- F2 与 F1 不同：F1 是"记得刚才"，F2 是"记得住并且知道该压缩"。

---

### G. 管家主动性 —— "它会不会自己动"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| G1 | **定时触发** | 到点自动做事 | 应该 |
| G2 | **巡检** | 主动发现问题（服务挂了？磁盘满了？） | 应该 |
| G3 | **报告** | 日报/周报，把这段时间发生了什么讲清楚 | 应该 |
| G4 | **建议** | 基于现状告诉你该做什么 | 可以 |
| G5 | **记忆维护** | 主动整理、提出"这条要不要记下来" | 可以 |
| G6 | **打扰分级** | 静默 / 每日摘要 / 即时告警，只推异常和需要人的事 | 必须 |

**关键设计点**
- **必须划一条边界：管家只"发现 + 报告"，不"擅自修复"。**
  发现问题后主动去修，等于让一个不受监督的进程改你的服务器。修复应该是你确认后的动作。
- G2 的难点不是技术，是**定义巡检清单**——这完全取决于你实际在管什么。
- G3 是最容易见效的：不需要它做任何判断，只要把已有记录讲清楚，就有价值。

---

### H. 治理与信任 —— "我敢不敢把服务器全域交给它"

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| H1 | **不可逆操作确认** | 删除、覆盖、部署、外发前必须问 | 必须 |
| H2 | **操作准入控制** | 谁能给它下指令（防外人误触） | 必须 |
| H3 | **审计与追溯** | 每个动作用了什么、改了什么，事后能查 | 必须 |
| H4 | **全局中止开关** | 一键让它停下 | 必须 |
| H5 | **限域** | 默认只在允许的范围内活动 | 必须 |
| H6 | **授权与撤销** | 临时授权有到期，能撤销 | 应该 |
| H7 | **数据安全** | 密钥不进上下文，输出脱敏 | 必须 |

**关键设计点**
- **这是"全域 + 微信可达"这个组合的前提**。两者单独看都不危险，合起来就是一把指向你整台服务器的远程钥匙。
- **H2 常被忽略**。一个能从手机触发的 agent，如果没有准入控制，任何知道你微信号的人都能驱动它。
- **H5 限域要和 P3 全域做权衡**。全域是能力诉求，限域是安全诉求。产品上更可能是"全域可达，但按操作类型分级"而不是"按目录限死"。
- H7 在微信场景尤其重要：长输出里一旦带出密钥，截图分享就泄漏了。

---

### I. 可靠性与可观测

| # | 能力 | 说明 | 优先级 |
|---|---|---|---|
| I1 | **状态可见** | 现在在干什么 | 必须 |
| I2 | **失败可诊断** | 出错时告诉你为什么，不是一句"失败了" | 必须 |
| I3 | **幂等** | 重复消息不会重复执行破坏性操作 | 必须 |
| I4 | **历史可追溯** | 上次那个任务是怎么做的 | 应该 |
| I5 | **成本可见** | token/花了多少钱 | 可以 |

**关键设计点**
- **I3 在微信场景是刚需**：网络重传、用户手滑重发、长轮询重连都会导致重复投递。
- I2 直接影响 D6——**静默失败是这个产品最致命的失败模式**。

---

### J. 日常生活 —— "工作之外的事它也能管"

> **边界：只做"信息、事务、内容"，不做"资金"。**
> 支付、下单、转账、投资等资金类操作**永不由 agent 执行**；它可以比价、查票、准备好订单，最后一步交给人。
> 这一域与 A-I 共用同一套治理：读取可自主，写外部系统（发邮件、改日历）必须走 H1/H6。

| # | 能力 | 说明 | dsh 现状 |
|---|---|---|---|
| J1 | 邮件读取与搜索 | 收件箱、按人/主题/时间检索、多账号 | ❌ 无 mail 包，需自建 |
| J2 | 邮件摘要与归档 | 每日摘要、批量归类、从邮件提取待办 | ❌ |
| J3 | 邮件草稿与发送 | 起草与润色；**发送必须确认并回显收件人/主题/正文** | ❌ |
| J4 | 日历与日程 | 查看忙闲、建/改日程、会前提醒 | ❌ 需接 CalDAV/厂商 API |
| J5 | 提醒与个人待办 | 一次性/周期性提醒，到点推到 IM | 🔧 schedule 可做定时，缺自然语言解析 |
| J6 | 网页检索与内容提取 | 搜索、抓正文、给出处 | ✅ `web_search` / `web_fetch` |
| J7 | 浏览器任务 | 带登录态完成查询、填表、多步操作 | 🔧 browser-use 有 provider，缺持久登录态 |
| J8 | 网页监控与订阅 | 价格/公告/更新，变化才通知 | 🏗 需自建（定时抓取 + diff） |
| J9 | 文档阅读与总结 | PDF/网页/邮件附件 | ✅ 文件读取 + 模型；需补 PDF 解析 |
| J10 | 写作与润色 | 邮件、报告、文案 | ✅ 模型直出 |
| J11 | 到期提醒 | 账单、订阅、证件、续费 | 🔧 依赖 J5 + 结构化记忆 |
| J12 | 出行与票务查询 | 查询、比价、给出建议；**不代付** | 🔧 浏览器/API |

**两条硬规则**

1. **邮件正文、网页内容都是不可信输入。** 里面的"指令"一律不执行，只作为信息；据此产生的副作用操作必须重新走审批（与 H 域一致）。
2. **生活域不碰 shell。** 浏览器/邮件/日历各有自己的工具面，不允许用"跑个命令"绕过治理。

## 三·五、协议与决策层（K）—— 增强项，不进 MVP

> 先把三件事分清，它们经常被混为一谈：
>
> | | 连接什么 | 是不是标准 | dsh 现状 |
> |---|---|---|---|
> | **MCP** | agent ↔ 工具 | ✅ AAIF 标准（2026-07-28 版） | ✅ 有客户端（stdio + Streamable HTTP），**无服务端** |
> | **A2A** | agent ↔ agent | ✅ AAIF 标准（150+ 组织） | ❌ 无 |
> | **System One / Jev** | 不连接任何东西 | ❌ **不是协议，是托管模型 API** | ❌ 无 |
>
> 把 Jev 叫"协议"是误读：它是 TypeSafe 的产品接口（`POST /v1/systemone`），
> 返回 Choice / Score / Noul 三类带置信度的结构化答案，70–500ms，输入仅文本。

| # | 能力 | 说明 | 建议版本 |
|---|---|---|---|
| K1 | MCP 工具接入 | 直接使用外部 MCP server 提供的工具 | P1（原生） |
| K2 | MCP 工具治理 | 服务白名单、版本锁定、凭据隔离、逐工具风险映射、首用审批 | **P1（治理前置）** |
| K3 | MCP 资源接入 | 外部知识/文档以资源形式进入上下文 | P1（原生） |
| K4 | 对外 MCP Server | 把项目/服务/审计暴露给 IDE 或其他 agent | P2 |
| K5 | 统一决策接口 | `decide(问题, 选项, 上下文) → {选择, 置信度, 理由}` | P1 |
| K6 | 入站分诊 | 一条消息先判：哪个域、什么意图、要不要追问、风险几档 | P1 |
| K7 | 告警与邮件分诊 | 严重度、是否需要人、是否值得记 | P1 |
| K8 | A2A 兼容任务模型 | Task/Receipt 字段与状态对齐 A2A Task，**只对齐模型，不实现协议** | **P0（设计约束）** |
| K9 | A2A 出站委托 | 把任务委托给外部专用 agent | P2 |
| K10 | A2A 入站服务 | 让别的 agent 把任务委托给我们（需鉴权 + 准入） | P2 |

**三条硬约束**

1. **决策必须留痕。** 任何自动判级（规则/主模型/Jev）都要把 `choice + confidence + reason` 写进审计，
   否则无法解释"它为什么自己批了"。
2. **协议不成为硬依赖。** MCP server 挂掉、A2A 对端不可达、Jev 停服，产品必须能降级运行。
3. **不可信内容不出域。** 邮件正文、日志、代码默认不送 Jev 这类外部判级服务；
   只送标签、命令串、元数据。是否放宽由 owner 逐项授权。

## 三·六、可替换能力（L）—— 把"换掉"做成产品能力

> **可替换不是"什么都抽象"。** 判据只有两条：
> **供应商风险高**（会涨价、会停服、会因合规被封）× **迁移成本高**（数据/凭据/流程被锁死）。
> 两条都高 → 必须做 seam；只有一条高 → 用适配层；都不高 → 直接调用，别加间接层。

| # | 可替换能力 | 替换对象 | dsh 现状 | 降级策略 | 版本 |
|---|---|---|---|---|---|
| L1 | Provider 契约与一致性测试 | 所有 seam | 🏗 需自建 | 新 provider 必须跑同一套契约用例 | P1 |
| L2 | 模型供应商 | DeepSeek / OpenAI 兼容 / 本地模型 | ✅ `llm` seam（`llm-deepseek`、`llm-pi-ai`） | 主模型不可用 → 只读降级 + 明确报错 | 原生 |
| L3 | 消息渠道 | 企微 / 飞书 / 个人微信 / Telegram | 🔧 渠道是插件，但需自己的入站/出站接口 | 入站拒收；出站进队列重试 | **P0** |
| L4 | 执行沙箱 | 本地 bwrap / SSH 远端 / 容器 | ✅ `sandbox` seam：`sandbox-local` + `sandbox-ssh` | **不可用即拒绝执行**，绝不降级到无沙箱 | 原生 |
| L5 | 浏览器与屏幕 provider | Playwright / Chrome DevTools / Stagehand / CUA | ✅ `browser-use`、`computer-use` 都是 provider 槽 | 报"浏览器不可用"，不偷偷换脚本 | P1 |
| L6 | 决策供应商 | 规则 / 主模型 / Jev | 🏗 `DecisionProvider` | Jev 挂 → 回落规则 + 主模型 | P1 |
| L7 | 邮件供应商 | IMAP/SMTP / Gmail API / MCP | 🏗 | 连不上 → 报错，不反复重试轰炸 | P1 |
| L8 | 日历供应商 | CalDAV / Google / Outlook / MCP | 🏗 | 只读走缓存；写失败明确告知 | P1 |
| L9 | 搜索供应商 | DeepSeek / Exa / Perplexity / 自建 | ✅ `web-search-*` 三个 provider | 搜索挂 → 退化为直接 fetch | 原生 |
| L10 | 运行环境操作后端 | systemd / Docker / k8s / 云 API / SSH | 🏗 `svcops` | 后端不可达 → 只报告不执行 | P1 |
| L11 | 凭据存储 | dsh credentials / OS keychain / 1Password | ✅ `credentials` seam（引用式、逐操作解析） | 取不到 → 操作失败，绝不落明文 | 原生 |
| L12 | 审计落点 | JSONL / SQLite / OTel | 🏗 | **写失败 → 拒绝执行（fail closed）** | **P0** |
| L13 | 记忆存储 | 文件 / SQLite / 向量库 | 🔧 `storage` 可承载后端，记忆语义自建 | 不可用 → 只影响召回，不影响执行 | P1 |
| L14 | 定时调度 | dsh schedule / system cron / 外部 | 🔧 `schedule` 存在，但投递绑原 session | 停摆 → 巡检暂停并告警 | P1 |
| L15 | MCP server 集 | 任意 MCP server | ✅ `mcp-client` | 单个挂 → 只摘除它的工具 | P1 |

**不可替换的内核（稳定契约，不是 provider）**

| 内核 | 为什么不能换 |
|---|---|
| PolicyGate 语义 / approval 范围 | 换掉就不是同一个产品，审计无法解释 |
| Task / Receipt 模型 | 回执是用户契约，字段一变历史全废 |
| 审计 schema | 审计链断一次就不可信 |
| 项目 / workspace 语义 | 隔离单位，变了等于重装 |
| 配对与准入规则 | 安全边界，不允许"可配置地放松" |
| 数据目录布局 | 备份/迁移/卸载都依赖它 |

**三条硬约束**

1. **可替换 ≠ 同时支持。** 默认只装一个 provider；备选"支持但不随版本发布"，避免维护四套渠道。
2. **没有契约测试的"可替换"是假的。** 同一个 seam 的两个 provider 行为不一致，
   换过去就是静默变形 —— L1 是其他 14 项的前提。
3. **降级策略必须逐项写死。** 沙箱与审计是 **fail closed**（不可用就停），
   模型/搜索/记忆是 **fail soft**（降级但可用），不能一刀切。

## 三·七、运行保障（M）—— 让它"活得久、退得回"

> 前面的域解决"能做什么"，这一域解决"出事怎么办"。
> 单人、单机、自托管的形态下**没有第二个运维**，所以这些不是锦上添花，而是**上线门槛**。

| # | 能力 | 说明 | dsh 现状 |
|---|---|---|---|
| M1 | **变更预演与快照回滚** | 部署/改配置前自动快照；失败自动回滚 | 🏗 |
| M2 | **备份、恢复与迁机** | 配置、记忆、审计、项目状态的定期备份与一键恢复 | 🏗 |
| M3 | **自身看门狗与启动自检** | 宿主挂了谁拉起；启动时检查工具/凭据/服务是否可用 | 🏗 |
| M4 | **升级与数据迁移** | dsh 承诺破坏兼容；插件与 schema 必须有迁移路径 | 🏗 |
| M5 | **紧急吊销与远程止损** | 手机丢了：撤销全部授权、停掉所有任务、断开渠道 | 🔧 |
| M6 | **审计完整性** | 只追加、哈希链、可导出，防篡改 | 🔧 |
| M7 | **提示注入与来源防护** | 外部内容分级、指令层级、出站守卫 | 🔧 |
| M8 | **预算与配额硬限制** | 按任务/按日 token 与费用上限，超了硬停 | 🏗 |
| M9 | **行为评测与回归** | 固定用例集，防止"对话劣化"（V3） | 🏗 |
| M10 | **供应链与许可证治理** | 依赖/插件来源、版本锁定、SBOM、许可证扫描 | 🏗 |

**上线门槛（必须先于"接管真实服务器"）**

| 门槛 | 没有它会怎样 |
|---|---|
| M1 快照回滚 | 一次误改就没有退路 |
| M2 备份恢复 | 机器坏了，记忆与审计一起没 |
| M3 看门狗自检 | agent 挂了没人知道，任务静默消失 |
| M6 审计完整性 | 审计可被篡改，等于没有审计 |
| M7 注入防护 | 一封邮件就能让它执行任意指令 |
| C8 测试验收 + M9 评测基线 | "改好了"和"没变差"都无法证明 |

> 这六项**不进 MVP 功能清单**（不影响首版演示），但**不能带着缺口接管真实服务器**。

## 四、贯穿性约束

不属于某个域，但处处适用：

| # | 约束 | 说明 |
|---|---|---|
| X1 | **微信优先** | 所有能力的价值判断，以"在手机上是否可用"为准绳 |
| X2 | **单用户** | 不做多人协作、团队空间、权限分级 |
| X3 | **自托管** | 跑在你自己控制的机器上 |
| X4 | **移动端不适配桌面交互** | 不假设有终端可视化、不假设能看大段滚动输出 |
| X5 | **失败必须可见** | 任何降级、静默截断、"做不到"都要让 owner 知道 |
| X6 | **默认自主，关键处停下** | 自主与确认的配比是持续调优的产品决策 |

## 六、MVP 边界

第一版**必须**有（否则产品不成立）：

```
A1 A2 A3 A4      说得清、记得住、回得丰富、推得主动
B1 B2            会找、会认项目
C1 C2 C3 C5      会读、会精确改、会执行、会用 git
D1 D2 D3 D6 D7   自主多步、长任务、不静默失败、该问就问
E1 E2 E3         项目切换、上下文隔离、能力隔离
J1 J5 J6         邮件读取、提醒、网页检索（生活最小闭环）
H1 H2 H3 H4 H5 H7  确认、准入、审计、中止、限域、脱敏
I1 I2 I3         状态可见、失败可诊断、幂等
```

**第一版可以没有**（但要留好接口）：

```
A5 A6 A7         长任务进度、中断纠偏、异步恢复
B3 B4            语义理解、服务器感知
C4 C6 C7         持久 shell、服务操作、网络
D4 D5 D8         断点续做、并行子任务、任务队列
E4 E5 E6         并行编辑约束、项目总览、知识边界
F3 F4 F5 F6      项目记忆、长期偏好、检索、遗忘
G1 G2 G3 G4 G5   全部管家能力
J2 J3 J4 J7 J8 J9 J10 J11 J12  邮件发送/摘要、日历、浏览器登录态、监控、文档、写作、到期、票务
I4 I5            历史追溯、成本可见
```

> **注意 G（管家能力）整个域都在第二梯队**。
> 这是刻意的：先把"你叫我做"做到可靠，再做"它自己动"。
> 反过来做会得到一个**不可靠的自主系统**——比不可靠的被动系统更糟。

## 七、这一版需要你确认的决策点

| # | 决策点 | 我的倾向 |
|---|---|---|
| 1 | **D1 自主 vs D7 确认的配比** | 读/查/跑非破坏命令自主；写/删/部署/外发必须确认 |
| 2 | **H5 限域的范围** | 全域可达，但按**操作类型**分级，而非按目录锁死 |

| 5 | **C6 服务管理范围** | systemd / Docker / 两者 |
| 6 | **G2 巡检清单** | 需要你列出实际在管的资产 |
