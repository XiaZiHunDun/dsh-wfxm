# 05 — 落地路线

> **依据**：[07-dsh 能力盘点与覆盖评估](07-dsh能力盘点与覆盖评估.md)（实现侧证据）+ [09-能力对照与实现路径](09-能力对照与实现路径.md)（**判定与顺序以 09 §五 为准**）
> **原则**：每步独立可交付、可中止。不做一次性大重构。

## 架构定调

```
本仓  dsh-wfxm/                ← 唯一写代码的地方
├── plugins/
│   ├── governance/            ← ③ 准入白名单 + 审计落库 + 最小授权
│   ├── wechat-channel/        ← ④ 可选，仅当 V5/V6/V7 不达标时
│   ├── svcops/                ← ⑤ 服务/进程管理（dsh 与 WFXM 都没有，需立项）
│   └── knowledge/             ← ⑥ 跨项目知识（先做语义决策再实现）
├── cordis.patch.yml
└── package.json  (peer: @deepseek-ai/dsh  >=0.2.0-rc.2 <0.3.0-0)
        │  dsh plugin --profile web add
        ▼
dsh 本体（npm @deepseek-ai/dsh）      ← 依赖，不 fork
```

**不 fork 的三条理由**：
1. dsh 的设计前提就是"没有特权内核，扩展方式=挂插件"，改源码违背其设计哲学
2. fork dsh = 跟 breaking change 赛跑（README 第一句就承诺会破坏）
3. fork dsh-im = 跟 47 贡献者 / 900 commit 赛跑，只为改一个渠道目录

**什么时候才需要 fork**：想改 agent loop 本身。按当前规划不需要。

**WFXM 侧**：**不需要 ADR。** 本仓是独立新仓，**不修改 WFXM**——
WFXM 保持全绿（`cf5f5510`）继续作为可用系统与回退路径，其产品边界未发生变更。
早前建议补 ADR 是把"新建产品"误当成"改造 WFXM"，已作废。

## Step 0 — 环境隔离（前置）

**问题**：本机 Node 22.13.0 / pnpm 9.15.0；dsh 要 Node ≥22.19 / pnpm 11.28.5。

推荐 **nvm + 独立 node 版本**：WFXM 保留 22.13，dsh 仓直接用 **Node 24 LTS**（见 12 §一）。
（corepack 会全局切 pnpm，影响 WFXM 的 v9 lockfile，不推荐。）

**验收**：`npx @deepseek-ai/dsh web` 能在 `127.0.0.1:3080` 起来。

## Step 1 — 冒烟测试（**并入 Step 2 第一步**）

装 `dsh-im@5.7.0` 并**只启用飞书**（主通道，见 [03 §结论](03-渠道选型.md)），跑通后**逐条验 V1–V11**。

> **准入检查（先于安装）**：该插件能否只启用传输能力、关闭其自建 `session.create` 与 `approval.persist`？
> 不能 → 直接淘汰，不进冒烟（依据 [11 §三·接入剖面](11-架构锚定.md)）。

> **Step 1 已降级为"冒烟测试"，不再是独立阶段。** 原因见 [`12-技术栈选型`](12-技术栈选型.md) §一：
> 用保守选型（Node 24、better-sqlite3、单 workspace 单活跃写任务、审批自持久化）
> 消除了大部分不确定性，只剩"dsh + 渠道插件这条链能否跑通"需要实测。
> 这件事并入 Step 2 第一步，半小时内出结果。

```sh
dsh plugin --profile web add -w @xmanrui/dsh-im@5.7.0
node <dsh-im>/scripts/verify-injected-context.mjs /home/ailearn/githubpro/deepseek-harness
```

### 必验的三条（**成立条件**）

| 验收 | 怎么做 | 不通过意味着 |
|---|---|---|
| **V1 多项目并行不打架** | 建 workspace-A / workspace-B，飞书里**同时**发两条任务，各配不同 preset；确认：彼此看不到对方的能力集与上下文、job 互不可见停、两边 LSP 能并行跑 | **方案不成立**，停下来重估 |
| **V2 同项目并行改文件** | 同一 workspace 两条会话改同一文件，观察是否静默覆盖 | 需要先定策略（git worktree / 文件锁 / 任务粒度约束） |
| **V3 对话不再劣化** | 连聊 10+ 轮，检查是否出现 Butler 那种「突然跑偏」；对照 `decodeDecision failed` 类现象 | owner 的核心判断被推翻，方向需重估 |

> **V2 是 dsh 完全没有的部分**（grep `file lock`/`mutex`/`concurrent edit` → 零产品命中）。
> 它的结论不一定是"不能做"，而是"必须自己定策略"。这一步就是把策略的必要性坐实。

> **V3 检验的是迁移的第一动因。** Butler 的 decoder 决策失败会静默降级，
> 而 dsh 的工具调用配对不变式会让不合约的请求直接抛错 —— 结构上不会"悄悄跑偏"。
> 这一条要在真实多轮对话里确认，不能只看文档。

### 其余七条

| 验收 | 关注点 |
|---|---|
| V4 会话 resume | 关进程重开，未完成会话能接着聊；**另验 web ↔ IM 跨 surface 续跑** |
| V5 长任务进度 | >2 分钟的任务在飞书能看到进度（飞书有流式 + 卡片，但**仍需自写进度出站**，这条最可能不达标） |
| V6 审批闭环 | 飞书里点**卡片按钮**完成一次需要确认的操作（**卡片由网关出站层渲染，不是插件自带审批消息**）；另验 web 发起 → 飞书里完成审批 |
| V7 入站准入 | **dsh-im 当前无白名单，必然不达标** → 进入 Step 2 |
| V8 全域执行 | agent 在 workspace 外读写/执行，行为可审计 |
| V9 定时任务 | 触发并在飞书投递结果 |
| V10 服务起停 | 起停一个真实服务并看日志（**两边都缺 → Step 4 `svcops` 立项**） |
| V11 免公网接入 | 飞书事件订阅走 **WebSocket 长连接**：不配置公网 IP/域名、不开端口也能收发 |

**这一步不写任何代码。跑不通就停下来重估。**

## Step 2 — 治理插件（补 V7/V8 的缺口）

**先做审计落库**，再做授权。顺序不能反——没有审计就没法验证授权是否生效。

### 2a. 审计落库
- 接缝：消费 dsh session event 流（`tool/call`、`tool/result`、`approval/asked`、`approval/decided`）
- 写入：**复用 WFXM 现有 `audit_events` schema**（actor/subject/action/correlation_id），不重设计
- 目的：V8 的"行为可审计"依赖它

### 2b. 入站白名单（补 V7）
- **dsh-im 的入站默认不设白名单**（微信渠道已确认 fail-open，飞书同样要外层兜底） —— 违反 WFXM §4.2「禁止未配对的远程入口」
- 最小可用形态：**小号物理隔离**（零代码）即可过 V7
- 若要支持多用户/团队：需自己写过滤器

### 2c. 最小授权（不是照搬 Butler 12 条准入条件）
按 `07` 的重新定位 —— 单 owner 全域开发 ≠ 多租户 SaaS。
最小形态建议：
- 破坏性操作确认（dsh approval + `permission-presets` 已覆盖大半）
- 路径 / 命令白名单
- 全局 kill switch
- 撤销路径
- **审计字段补全**（来自 2a）

> **不要在 Step 2 就去重建 Butler 那套完整 ScopedGrant 体系。**
> 先用最小形态跑通 V8，再按真实痛点加。

## Step 3 — 中文体验（触发式，非预设）

**触发条件**：冒烟测试中 V5 或 V6 不达标。

此时才写自己的微信渠道插件。**复用 WFXM 那 1,228 行非测试 iLink**，不重写协议层。

要做的胶水：
- 入站：微信消息 → `session.prompt`
- 出站：`session/event` → 微信消息（**含流式**，这是 V5 的核心）
- 审批应答：解析中文 `确认`/`👌`/`y` → 返回 `allowed-once`（V6 的体验提升）
- 入站白名单（若 2b 走了代码路线）

**规模判断**：协议层 0 行，胶水层几百行。

## Step 4 — 管家主动性（对应 P5，**已进第一版**）

> **2026-10-28 owner 决定：管家进 V1。** 故 Step 4 从"后置增强"变为 **MVP 必交付**，
> 最小切片 = B4 + C6 + G1 + G2 + G3 + G6；`svcops` 立即立项。
> 边界仍守：**只发现 + 报告；修复动作走 C6 + R3 确认**。

| 能力 | 状态 |
|---|---|
| 定时提醒 | ✅ dsh 原生（冒烟测试验 V9） |
| 待办 | ✅ dsh 原生 |
| 摘要 / 周报（G3） | ❌ 自建（可参考 Butler 的 `task_digest`） |
| 巡检 / 健康检查（G2 + B4） | ❌ 自建；**清单需 owner 提供**（决策 #6） |
| 打扰分级（G6） | ❌ 自建：静默 / 每日摘要 / 即时告警 |
| **服务/进程管理**（C6 / V10） | ❌ **dsh 和 WFXM 都没有** —— 起停、看日志、看状态；**MVP 先做 systemd，Docker 后置** |

> **注意这一层的能力现状**：dsh 原生覆盖的 3 项（定时/待办/后台任务）都是"你叫我做"，
> 而"我该主动做什么"的三项（摘要/巡检/告警）都要自建。
> 服务管理更是从零——**这就是它进 V1 后必须立即立项的原因**。

## Step 5 — 跨项目知识语义（必须做决策）

dsh 是 workspace 隔离；Butler 的 PK recall 是**故意跨项目**的（D43 闭环项）。
两者语义对立，**不能照搬也不能丢**。

要决策的是：
- (a) 显式的跨 workspace 查询（承认跨项目是有意为之）
- (b) 知识挂在 workspace 上不跨（承认隔离优先）
- (c) 分层：workspace 私有 + 一层显式共享

**这是产品决策，不是实现细节。** 建议在 Step 3 之后、实际用起来之后再定。

## Step 6 — Butler 收尾

WFXM 保持全绿（`cf5f5510`），作为：
- iLink 客户端的真相源（若走 Step 3）
- 验收场景库的来源（58 个场景可重写为 dsh 验收用例）
- 产品设计文档归档
- **ScopedGrant 语义的参考实现**

**不删除、不冻结** —— 迁移验证完成前它仍是可用系统。

## 明确不做的

| 不做 | 理由 |
|---|---|
| fork dsh 或 dsh-im | 见上方三条理由 |
| sidecar 过渡架构 | dsh-im 已有现成渠道，sidecar 只增加跨进程状态 |
| 一次性重构 | 每件独立交付，跑不通就停 |
| Step 2 一上来就重建完整 ScopedGrant 体系 | 先最小形态，按真实痛点加 |
| 搬 dsh 已有的能力 | 见 `04-A` |
| 把 Butler 的死链/文档漂移带过来 | 与迁移无关 |

## 关键路径

```
Step 0 环境 ──→ Step 2 治理（第一步：dsh-im 冒烟） ──→ Step 4 管家 ──→ Step 5 知识
                      └── 冒烟不通 ──→ 换渠道 / 写适配
```

**Step 1 已不再是独立分叉点。** 技术栈用保守选型消除了大部分不确定性（见 12 §一），
冒烟测试只回答"渠道这条链是否可用"。多项目隔离（V1）与对话质量（V3）在 Step 2/4 验收。

**Step 4 现在是 MVP 内的交付项，不再是"以后再说"。** 它依赖两件 owner 输入
（决策 #5 服务范围、#6 巡检清单），所以要在 Step 2 期间就并行索取，不能等到 Step 4 才问。
