## 一、目录布局

```
/opt/dsh-wfxm/                 # 代码与依赖，root:root，服务只读
  releases/<version>/          # 每次发布一个目录（蓝绿）
    scripts/  plugins/  docs/  package.json
    node_modules/              # 同盘硬链自构建机；跨盘则复制
    release.json               # 版本 / commit / 准备时间 / 依赖链接统计
  current -> releases/<v>      # 软链，切换即发布/回滚

/var/lib/dsh-wfxm/             # 数据（正本），dshwfxm:dshwfxm，0700
  ops.sqlite  ops.sqlite-wal
  workspace/                   # 执行器默认工作区（v1 单根）
  snapshots/                   # 工作区级 / 文件级快照（⑦）
  memory/                      # Markdown 正本（知识层，可选）
  outbox-files/                # 待投递附件
  home/                        # 服务用户的 HOME（dsh 的 sessions / .dsh 落这里）
  readiness                    # 就绪标记文件（本地）
  serve.lock                   # 单实例锁（写入 pid）

/etc/dsh-wfxm/                 # 配置与凭据，root:dshwfxm，0750
  env                          # 非敏感环境变量，0640（模板：deploy/systemd/dsh-wfxm.env.example）
  credentials/                 # 0640（root:dshwfxm）；飞书 config.json + 凭据文件
                                 #   （ProtectHome 让 $HOME 不可达，必须搬到这里；服务组需读，故非 0600）

/var/backups/dsh-wfxm/         # 备份归档（*.tar.gz + *.sha256）
/var/log/journal/              # 日志走 journald，不另建目录
```

> **没有根级 `dist/` 与 `migrations/`**：本仓直接跑 TypeScript 编译产物/源码模块（插件各自 `lib/`），
> 迁移 SQL 放在各插件自己的 `plugins/<pkg>/migrations/`，启动时由 `schema_migrations` 逐模块推进（15 §七）。
> 配置只有环境变量（`/etc/dsh-wfxm/env`），没有 `default.yaml`/`policy.yaml`/`patrol.yaml`。

| 规则 | 理由 |
|---|---|
| **代码只读、数据可写** | 发布不可被运行进程改写，供应链更干净 |
| 专用系统用户 `dshwfxm` | 无 login shell；不属于 sudo/docker 组 |
| 数据目录 0700 | 会话正文、邮件、凭据引用都在里面 |
| profile 按项目分目录 | 对应 AR / 11 §5.8 浏览器 profile 资源化 |

## 三、systemd unit

**实际文件是 SSOT：[`deploy/systemd/dsh-wfxm.service`](../deploy/systemd/dsh-wfxm.service)**（本仓已提供，
`scripts/verify-deploy.mjs` 用 `systemd-analyze verify` 做静态校验）。关键行：

```ini
[Service]
User=dshwfxm
Group=dshwfxm
WorkingDirectory=/opt/dsh-wfxm/current
EnvironmentFile=/etc/dsh-wfxm/env
Environment=HOME=/var/lib/dsh-wfxm/home          # ProtectHome 下 dsh 的落点
ExecStart=/usr/bin/node scripts/serve.mjs
Restart=on-failure
TimeoutStopSec=30
KillSignal=SIGTERM
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
CapabilityBoundingSet=
SystemCallFilter=@system-service landlock_create_ruleset landlock_add_rule landlock_restrict_self
ReadWritePaths=/var/lib/dsh-wfxm /var/backups/dsh-wfxm
```

> **没有 `ExecReload`**：`serve.mjs` 不实现 `SIGHUP` 热重载；升级一律走蓝绿切换 + `systemctl restart`
> （文档早前的 `ExecReload=kill -HUP` 已删除，避免承诺不存在的语义）。
> **`Restart=on-failure` 会重试**：自检失败退出码 1，`StartLimitBurst=5` 内重试几次后停住，
> 不会无限重启把日志刷满。**退出码 3（已有实例）也算失败退出**，但因单实例锁由 systemd 的
> `Restart` 重试一次即可确认；运维处置见 §十。

> **`SystemCallFilter` 必须显式放行 Landlock 三个 syscall**（2026-11-11 真机踩到）：
> systemd 249 的 `@system-service` 早于 Landlock（kernel 5.13），`landlock_*` 会被
> `SystemCallErrorNumber=EPERM` 一律拒掉，dsh 的命令沙箱直接报 `SANDBOX_UNAVAILABLE`。
> bwrap 在这里**不能兜底**：`CapabilityBoundingSet=` 让它在自己的 user namespace 里也拿不到
> `CAP_SYS_ADMIN`，`mount --make-rslave` 报 `Operation not permitted`。放行这三个 syscall 后，
> 沙箱走 Landlock（旧 ABI 报 `partial enforcement`，命令可正常执行）。
> 验证方式见 §12.6 的 `systemd-run` 命令。

**主机侧一次安装（root）：`sudo bash deploy/install.sh`**

脚本幂等，只做「创建用户/目录/env/unit/polkit/受控 wrapper」这几件必须 root 的事：

- 建系统用户 `dshwfxm`（`--system --shell /usr/sbin/nologin`，**不加 docker 组**）、`/var/lib/dsh-wfxm{/home}`、`/var/backups/dsh-wfxm`、`/etc/dsh-wfxm{/credentials}`，并按 unit 的 `ReadWritePaths` 收紧权限；
- `/etc/dsh-wfxm/env` **仅在缺失时**由 `dsh-wfxm.env.example` 生成（不覆盖 owner 已改的配置），权限 `root:dshwfxm 0640`；
- 安装 unit、polkit 规则、受控 wrapper（`/usr/local/sbin/dsh-wfxm-unit-control` 0755）与 sudoers 片段（0440，先 `visudo -cf` 预检）后 `systemctl daemon-reload`；
- 安装 `dsh-wfxm-backup.service` / `.timer`，只 `systemctl enable` timer（**不 `--now`**，安装不应立刻压一次备份）；首次备份由 timer 或人工 `systemctl start dsh-wfxm-backup.service` 决定；
- 安装 `deploy/journald/10-dsh-wfxm.conf` 到 `/etc/systemd/journald.conf.d/`，仅在内容变化时 `systemctl restart systemd-journald`；
- **不**替你发布 release、**不**拷凭据、**不** `systemctl start`；缺项会打印提示。
- `sudo DRY_RUN=1 bash deploy/install.sh` 只打印将执行的命令（非 root 也能预览）。

> 创建用户/写 `/etc` 需要 root。开发用户（如 `ailearn`）即使在 `sudo` 组，也需要交互式密码；
> 非交互执行会因 `sudo: a password is required` 失败——这一步必须由 owner 在终端执行。

### 服务 HOME 运行面（install 之后、start 之前）

`ProtectHome=yes` 让服务看不到真实的 `$HOME`，而 dsh 的 profile、会话和模型凭据都在 `$HOME/.dsh`。
除 `/etc/dsh-wfxm/credentials/`（Feishu 用）外，**必须再给服务 HOME 铺一份 dsh 运行面**，否则
启动能过八步，但一执行任务就报错：

```bash
install -d -o dshwfxm -g dshwfxm -m 0700 /var/lib/dsh-wfxm/home/.dsh
cp -a /home/ailearn/.dsh/profiles /var/lib/dsh-wfxm/home/.dsh/
install -m 0600 -o dshwfxm -g dshwfxm \
  /home/ailearn/.dsh/.credentials.yaml /var/lib/dsh-wfxm/home/.dsh/.credentials.yaml

# 关键：profile 里的 @dsh-wfxm/* 若是指向仓库的相对软链，在服务 HOME 下会解析到
# /var/lib/dsh-wfxm/projects/...（不存在），dsh 会静默跳过 governance/svcops bundle。
P=/var/lib/dsh-wfxm/home/.dsh/profiles/headless/node_modules/@dsh-wfxm
rm -f "$P/governance" "$P/svcops"
ln -s /opt/dsh-wfxm/current/plugins/governance "$P/governance"
ln -s /opt/dsh-wfxm/current/plugins/svcops "$P/svcops"
chown -h dshwfxm:dshwfxm "$P/governance" "$P/svcops"
```

- 软链指向 `current`（而不是某个具体 release），升级切软链后自动跟随。
- `.credentials.yaml` 是 dsh 的模型凭据（headless profile 显式启用了 credentials store）；
  少了它，任务会在模型调用处失败，而不是在八步自检里。
- 验证：`sudo -u dshwfxm -H test -r "$P/governance/package.json"` 与 `svcops` 均应通过；
  dsh 启动日志里**不应**再出现 `skipping profile bundle`。

**关键取舍：怎么在不给 root 的前提下管服务（`svcops`）**

| 方案 | 结论 |
|---|---|
| 服务跑 root | ❌ 一个 agent 进程 root = 全盘皆输 |
| 加入 `docker` 组 | ❌ **等价 root**（可挂载宿主根、起特权容器） |
| **受控 wrapper + sudoers** | ✅ 允许 `dshwfxm` 对**匹配前缀的 unit** 做 start/stop/restart：`dsh-wfxm-managed-*.service` |
| polkit 细粒度授权 | ⚠️ 仅 polkit **0.106+** 有效；0.105（Ubuntu 22.04，本机）**不解析 JS 规则**，见下 |
| docker socket proxy（只读/白名单） | ⚠️ 条件方案：仅当确实需要 docker 时启用 |
| 自己用 `systemd-run --user` | ⚠️ 用户态 unit，能力弱，看情况 |

**实际生效链路（2026-11-13 起）**：`svcops` 写操作 → `DSH_WFXM_UNIT_CONTROL`
（`/usr/local/sbin/dsh-wfxm-unit-client`）→ `/run/dsh-wfxm/unit-control.sock`（`root:dshwfxm 0660`）
→ root helper（`dsh-wfxm-unit-control.service`）白名单校验 → `systemctl`。

> **为什么换掉 sudo**：本服务 `NoNewPrivileges=yes`，`sudo` 直接报
> `The "no new privileges" flag is set, which prevents sudo from running as root`，
> 所以「wrapper + sudoers」在服务内**根本不可用**（2026-11-13 实测）。改为 root 侧常驻 helper：
> 只接受 `start|stop|restart` + `dsh-wfxm-managed-[a-z0-9.-]*.service`，socket 靠文件权限
> `0660 root:dshwfxm` 限定调用方；服务不需要任何提权能力。wrapper/sudoers 文件仍随 install 安装，
> 仅作旧版兼容，不再写入 `env`。

```sh
# deploy/bin/unit-control-server.mjs → /usr/local/lib/dsh-wfxm/（root:root 0755）
#   校验 verb/unit → execFile('/bin/systemctl', [verb, unit])
# deploy/bin/unit-control-client.mjs → /usr/local/sbin/dsh-wfxm-unit-client（root:root 0755）
#   JSON 行协议，转发 stdout/stderr 与退出码，svcops 解析不变
```

```sh
# deploy/bin/dsh-wfxm-unit-control → /usr/local/sbin/（root:root 0755）
case "$verb" in start | stop | restart) ;; *) exit 64 ;; esac
case "$unit" in dsh-wfxm-managed-*.service) ;; *) exit 64 ;; esac
case "$unit" in *[!a-z0-9.-]* | *..*) exit 64 ;; esac
exec /bin/systemctl "$verb" "$unit"
```

```
# deploy/sudoers/dsh-wfxm-unit-control → /etc/sudoers.d/（root:root 0440）
dshwfxm ALL=(root) NOPASSWD: /usr/local/sbin/dsh-wfxm-unit-control *
```

`deploy/install.sh` 安装这两个文件（sudoers 写前 `visudo -cf` 预检，失败不落盘）。
读操作（`list` / `status` / `logs`）不需要提权，仍直接走 `systemctl` / `journalctl`。

> **polkit 的坑（2026-11-11 实测）**：`deploy/polkit/50-dshwfxm.rules` 仍随 install 安装到
> `/etc/polkit-1/rules.d/`（供 0.106+ 主机），但本机 `polkitd` 报
> `authority implementation 'local' version '0.105'`，**JS 规则根本不执行**；现场表现是
> `systemctl` 返回 `Interactive authentication required`（写 `polkit.log` 规则也不产生任何日志）。
> 所以**不能**把 0.105 主机上的提权寄托在 polkit 规则上。

> **结论**：`svcops` 默认**只能管白名单前缀的 unit**；不在名单内的服务一律 `PermissionDenied`。
> docker 适配器**按运行时探测启用**（[12 §10.3](12-技术栈选型.md) 决策 #5：探到才挂、探不到就摘除），启用时**只能经 socket proxy（只读 + 白名单）**，
> 不允许直连 root socket，首次启用单独评审。命令级白名单见 [17 §4.4](17-Agent侧设计.md)。

## 四、启动顺序与自检（八步，任一步失败即拒绝启动）

实现：`scripts/lib/startup.mjs`（启动序列库，生产与验证走同一路径）+ `scripts/serve.mjs`（生产入口）。
`node scripts/serve.mjs --check` 跑完八步后立即退出（不建长连接、不常驻），供发布验证与还原演练使用。

| # | 步骤 | 实际检查 | 失败语义 |
|---|---|---|---|
| 1 | 读配置 | `parseServeConfig()` 校验 `dataDir`/`dbPath`/`workdir`/`snapshotDir`/`channel`/`foreground`/超时等；目录可建 | 配置错误即退出，**不猜默认值** |
| 2 | 打开 `ops.sqlite`，推进各模块迁移 | 六个 store 依次打开（approval / gateway / grant / memory / snapshot / tasks），`PRAGMA integrity_check` | 迁移失败即退出，**不回退半旧 schema**（15 §七） |
| 3 | 模块注册 | `assertModules()` 逐个核对八项必需导出存在（`createMemoryStore` / `createSnapshotStore` / `createApprovalStore` / `createGrantStore` / `createWfxmHost` / `createDshExecutor` / `createDecisionRunner` / `createResourceProbe`） | **缺任一即退出**（宿主 peer 不匹配会静默跳过整个 bundle） |
| 4 | 插件剖面 + 工具注册 | `assertZeroToolAsset()` 解析 `frontdesk*.patch.yml`，**启用项里不得残留 `tool-*`**（仅允许 `tool-result-pruner`） | 有残留工具 → 拒绝启动（AR25 / 17 §四） |
| 5 | 端口探活 | 执行器二进制可执行（`resolveExecutable`）、工作区/快照目录可写、飞书凭据路径存在 | 关键不可用 → 退出 |
| 6 | 恢复 | `host.worker.recover()` 回收过期租约；`outbox` 由投递器轮询接管 | 失败 → 退出（宁可不开，不可半开） |
| 7 | 渠道 | `loopback` 直接通过；`feishu` 建长连接并等 `ready`（20s 超时），无绑定时打印 `/bind` 配对码 | 失败 → 退出（渠道是主入口） |
| 8 | 写 `readiness` | `writeReadiness()` 落 `readiness` 文件（内容含 pid / 版本 / 时间） | 不可写 → 退出 |

> **为什么第 6 步不能省**：崩溃后最危险的状态是"任务在跑但没人知道它跑到哪了"。

**退出码**（`scripts/lib/startup.mjs`）：

| 码 | 含义 |
|---|---|
| 0 | `--check` 通过，或 `SIGTERM`/`SIGINT` 正常退出 |
| 1 | 自检失败（`StartupError` 带 `step` / `stepName`，日志前缀 `[startup] N/8 <step>`） |
| 3 | 已有实例（单实例锁被活进程持有，见 §五） |

## 五、停止与崩溃恢复

| 场景 | 行为 |
|---|---|
| `SIGTERM` / `SIGINT` | 停接新任务 → `host.stop()` → 最多 3 轮 `pump()` flush `outbox` → 断长连接 → `host.close()` + 各 store 关闭 → 删 `readiness` → 释放锁 → exit 0 |
| `waiting_approval` / `waiting_input` | **冻结租约**（不占并发槽），重启后仍是等待态 |
| 进程崩溃 | 租约到期（2× 心跳）后由恢复流程回收 → `failed` 或重排队 |
| 重复启动 | **`serve.lock`**（`O_EXCL` 原子创建，含 pid）→ 第二个进程退出码 3 |
| 陈旧锁（宿主被杀、pid 已不存在） | 启动时检测 pid 存活为假 → 回收旧锁并继续 |
| 锁被活进程持有 | **不抢占**，退出码 3；由 systemd `Restart` 重试一次即可确认（见 §三） |

> **`HOME` 重定向说明**：unit 把 `HOME` 指到 `/var/lib/dsh-wfxm/home`，因为 `ProtectHome=yes` 让真实 `$HOME`
> 不可达，而 dsh 的 `sessions/`、`.dsh/` 需要可写落点。数据目录是唯一可写区。

## 六、发布、升级与回滚

```
prepare → verify（release 自己的 serve.mjs --check）→ switch（tmp symlink + rename）
        → systemctl restart（由运维执行）→ 保留上一版（N-1，gc 永不删 current）
失败     → switch <N-1> → restart → 报告
```

实现：`scripts/release.mjs`（子命令 `prepare` / `verify` / `switch` / `rollback` / `list` / `current` / `gc`），
默认根 `/opt/dsh-wfxm`（可用 `--root` 覆盖），`npm run release -- <子命令>`。

| 项 | 规则 |
|---|---|
| **发布单元** | `releases/<v>/` 自包含：`scripts/` / `plugins/` / `docs/` / `package.json` / `release.json`；`EXCLUDES` 掉 `node_modules` / `.git` / `.wfxm` / `releases` / `current` / `coverage` |
| **依赖树** | 同盘用 `cp -a --link` 硬链构建机的 `node_modules`（快、省盘）；跨盘回退整树复制。相对 symlink 保留，release 自包含 |
| **verify 先行** | `release verify <v>` 跑 **release 自己的** `scripts/serve.mjs --check`，并断言 `@dsh-wfxm/gateway` 的 realpath 落在该 release 内（防"验证了错的代码"） |
| **switch 拒收** | 必需文件不全或 `verify` 未通过 → **拒绝切换**，不留半成品 `current` |
| **回滚** | `release rollback` 切到上一个可 `verify` 的版本（N-1 永远可用）；`gc` 只删非 `current` 且非 N-1 的旧版本 |
| **我们自己的升级** | 蓝绿目录 + 软链；**N-1 永远可用** |
| **宿主（dsh）升级** | 整行重测（12 §10.5 版本矩阵），过 V1–V11 + 契约测试才进版本 |
| **DB 迁移前** | 必先 `VACUUM INTO` 备份；迁移失败用备份恢复并回滚 |
| **回滚判据** | 任一步自检失败或冒烟失败 → 回滚，不"带病上线" |
| **restart 不代劳** | `release switch` 只换软链；`systemctl restart dsh-wfxm` 由运维执行（不给发布脚本 root） |
| 灰度 | 无用例：单机单用户，不做灰度 |

## 七、备份与恢复

实现：`scripts/backup.mjs`（制作）+ `scripts/restore-drill.mjs`（还原演练），`npm run backup` / `npm run restore:drill`。

```
backup  → VACUUM INTO ops.sqlite → 拷 memory/ snapshots/ outbox-files/ (+ config) → manifest.json
        → tar.gz + .sha256 sidecar →（可选）restic backup --tag <tag>
drill   → 校验 sha256 → 解包 → integrity_check + 各表行数比对 manifest → 部件存在
        → 用 serve.mjs --check 在还原目录跑八步 → 断言 [startup] 8/8
```

| 项 | 做法 |
|---|---|
| 一致性 | SQLite 用 **`VACUUM INTO`**（WAL 折入，不是文件拷贝）；源库先 `PRAGMA integrity_check`，非 `ok` 即失败 |
| 同一个还原点 | `ops.sqlite` + `memory/` + `snapshots/` + `outbox-files/`（+ `/etc/dsh-wfxm` 配置）打进**同一个 tag**，`manifest.json` 记 `tag` / `counts` / `components` / `source` |
| 完整性 | `<tag>.sha256` sidecar；演练**先校验 hash**，不符即拒（篡改用例已验证） |
| manifest 缺失 | 拒绝还原（不猜结构） |
| 行数不符 | 拒绝（`counts` 逐表比对，含 `projects` / `memory_facts` / `tasks` / `task_events` / `grants` / `approvals` / `outbox` / `inbox`） |
| 演练判据 | 不是"解包成功"，而是**在还原目录跑完整八步自检**并拿到 `8/8` |
| restic | **可选**：配置 `--restic-repo` / `DSH_WFXM_RESTIC_REPO` 才执行；未配置时打印 `restic: skipped`，**绝不静默假装异地已备** |
| 频率 | 每日 03:30（`dsh-wfxm-backup.timer`，±15 分钟随机、`Persistent=true` 补跑）；**变更前（R3 动作前）额外快照**（13 §三） |
| 保留 | `--keep N` / `DSH_WFXM_BACKUP_KEEP`（默认 **7** 份）；`0` / `--no-prune` 关闭。只匹配 `dsh-wfxm-YYYYMMDDTHHMMSSZ.tar.gz` 与其 `.sha256`，其他文件永不删除；非法值显式失败 |
| 定时器 | oneshot 以 `dshwfxm` 运行，`ProtectSystem=strict` + `ReadWritePaths=/var/lib/dsh-wfxm /var/backups/dsh-wfxm`；安装只 `enable`，不 `--now` |
| 异地 | Backblaze B2（12 §10.4 默认）— 需 owner 配 restic repo，未配即 skipped |
| 审计 | **不归档、不裁剪**；随快照一起备 |
| 演练 | **每月一次真实还原**到临时目录并跑自检（纪律：没跑的测试不算绿） |
| 空数据目录 | `backup` 找不到 `ops.sqlite` → 显式失败（不产空归档） |
| 配置不可读 | 备份以 `dshwfxm` 运行并拷贝 `/etc/dsh-wfxm`；`env` 必须 `0640 root:dshwfxm`（`0600` 会在 `cpSync` 报 `EACCES`，2026-11-20 已修正并复跑成功） |

> **R3 前置快照 ≠ 备份**：前者是**工作区快照**（git HEAD tree 基线，排除凭据 / 嵌套仓库 / submodule / symlink 祖先，见 [13 §3.4](13-核心能力方案.md)），
> 缺 `baseline_ref`（[15 `snapshots`](15-数据与契约.md)）不得用于 R3；后者是 restic 灾备，两者不要混称。

### 九之一、定时巡检与日报（G2/G3）

`serve` 启动后由宿主定时跑最小安全集巡检，结果写 `inspections` 表，异常与日报经 ⑥ outbox 推到飞书。

| 项 | 默认 | 配置 |
|---|---|---|
| 巡检间隔 | 15 分钟（启动后 15s 首跑） | `DSH_WFXM_PATROL_INTERVAL_MINUTES`（0 关闭） |
| 日报时间 | 每天 09:00（本机时区） | `DSH_WFXM_DIGEST_HOUR`（0–23，-1 关闭） |
| 周报 | 每周一 09:00（跟随日报时间） | `DSH_WFXM_WEEKLY_DIGEST_DAY`（0=周日…6=周六，-1 关闭；默认 1） |
| 巡检目标名 | `hostname()` | `DSH_WFXM_PATROL_TARGET` |
| 阈值/端口 | 09 §五 默认值 | `DSH_WFXM_INSPECT_THRESHOLDS` / `DSH_WFXM_EXPECTED_PORTS` |
| 巡检库 | `/var/lib/dsh-wfxm/ops.sqlite` | 与宿主同库；需 `DSH_WFXM_AUDIT_DB` 指向它，子进程 `svc_report` 才能读到 |

- **打扰分级**：`fail` 立即推（同一组失败项 30 分钟静默窗 + outbox `dedupeKey` 防重）；`warn` 只进日报；`ok/skipped` 静默。
- **收件人**：当前最新的活跃 `channel_bindings.external_user_id`；无绑定则丢推送并记 `patrol:warn`。
- **日报**：窗口 24h，内容为巡检次数、状态/告警分布、最新一次与去重后的持续异常。
- **周报**：窗口 7 天，内容为巡检次数/状态/持续项 + 任务计数与 bullet + 会话计数与 bullet；周报日**取代**当天三封日报，
  失败/为空时回落日报；dedupeKey `weekly-digest:<ISO周>`，重启不重发。
- **出站健康行**（Slice Q）：日报末尾与周报附加段之后各追加一行 `出站：失败 N · 积压 M`（重试中 >0 时附 `（重试 K）`）；
  数据来自 ① `outboxHealth`（窗口内 `failed` + 当前 `pending`/`retrying`/最老积压年龄），只读、不改投递语义。
- **长任务提醒**（Slice R）：不走巡检调度，由 host pump 每秒对 `running` 任务按 2/10 分钟里程碑与 15 分钟无事件做一次性提醒
  （`task.progress`，见 §12.13）；不改任务状态，也不影响巡检/日报。
- **边界**：静默窗是进程内状态，重启后首轮可能重推一次（`dedupeKey` 会挡住同一桶）；日报覆盖巡检、任务与会话（任务/会话各有独立 dedupeKey），
  语义级会话摘要只作用于日报；周报**不调模型**、不按项目拆分；出站行只给计数，不列消息正文。
- **验证**：`node scripts/verify-patrol.mjs`（26 例：配置、静默窗、跨日、投递失败隔离、任务/会话日报窗口与去重、周报取代/隔离/ISO 周、出站行与异常隔离）；生产首轮见 §12.6 / §12.9 / §12.11 / §12.12。

## 十、运行手册（常见故障处置）

| 现象 | 排查 | 处置 |
|---|---|---|
| 飞书无响应 | 长连接日志、应用权限版本是否发布 | 重连；权限未发布 → 重新发布版本 |
| 任务堆积不前进 | 租约是否过期、是否有 `waiting_approval` 卡住 | 释放租约；过期审批转 `expired` 并重发提醒 |
| 启动即退出 | 八步自检哪一步失败 | 按失败步骤修；迁移失败先恢复备份 |
| 磁盘满 | `df`、`spill/`、journald | 清 `spill`；按保留策略归档；扩容 |
| **审计链断**（hash 不连续） | `audit_log` 相邻 `prev_hash` | **立即告警并停写业务**，人工介入（不自动修复） |
| 端口探活失败 | 该适配器日志 | 摘除该适配器（11 适配器探活规则），其余继续 |
| better-sqlite3 加载失败（`libstdc++` 版本符号缺失） | 由 Trae 等宿主环境注入的 `LD_LIBRARY_PATH` 把旧 `libstdc++` 抢在系统库前加载（2026-11-10 实测） | 跑 dsh / node / pnpm 前 `unset LD_LIBRARY_PATH`；unit 里不写 `Environment=LD_LIBRARY_PATH=…`，若必须覆盖则显式置空 |

### 12.1 与设计稿的差异（以实际为准）

| 设计稿原设想 | 实际 | 原因 |

### 12.2 第八步之外的运行面

- **`--check` 模式**：跑完八步即退出，供 `release verify` 与 `restore-drill` 复用；不建长连接、不常驻。
- **loopback 渠道**：`DSH_WFXM_CHANNEL=loopback` 用于本机验证与还原演练（无飞书凭据也能跑八步）。
- **`--check` 后的保活**：常驻模式用 `setInterval` 维持事件循环（否则无活动句柄时 Node 会静默退出）。
- **日志**：带 ISO 时间戳，前缀 `[startup] N/8 <step>`；不写文件，走 journald。

### 12.24 协作式取消：`停止` 真正终止子进程（2026-11-16，`2026.11.16-4`）

**问题**：控制帧 `停止 <ref>` 原先只把任务行改成 `cancelled`，宿主里的 dsh 子进程继续跑到超时；
子进程结束后 worker 调 `settle()`，撞上非法的 `cancelled → succeeded`，任务与回执都会失真。

**链路**（每一层都不知道对方的实现，只走既有端口）：

1. gateway 控制帧 → ① `TaskControlPort.cancel` → host `control()`；
2. `control()` 先调 `cancelRunning(taskId)`（host 在 `createHostPorts` 时晚绑定 `worker.cancel`），再落 `cancelled` 迁移；
3. `worker.cancel(taskId)` 从 `activeAttempts` 取到该次尝试的 `AbortController` 并 `abort()`；
4. executor 监听 `hooks.signal`，abort 后 `SIGTERM`（宽限 `killGraceMs` 后 `SIGKILL`），checkpoint 以 `aborted` 关闭，
   返回 `{status:'failed', failure:'conflict', summary:'cancelled by owner'}`；
5. worker 看到行已是 `cancelled` → 释放资源锁，返回 `skipped:'cancelled'`，**不 settle、不迁移、不追加回执**。

**stale 判定的一处放宽**：`transition` 会清空 `lease_owner`，所以 `leaseOwner !== owner` 时先看状态，
只有「不是 `cancelled`」才判 `stale-lease`；否则取消会被误判为租约丢失，永远到不了取消分支。

**验证**：`verify-executor 20/20`（挂起子进程 + abort → 5s 内退出、pid 已消失、`conflict`）、

### 12.25 纯文本控制命令（2026-11-16，`2026.11.16-5`）

### 12.26 静默自动暂停与一键恢复（B3 v2，2026-11-16，`2026.11.16-7`）

**配置**（`/etc/dsh-wfxm/env`，均可选）：

- `DSH_WFXM_TASK_STALL_MINUTES`（默认 `15`）：任务多久无事件算「静默」；
- `DSH_WFXM_WATCHDOG_PAUSE`（默认开）：设为 `0` 时退回 v1——只发一条提醒，不暂停。

**行为**（`host.pump()` 每个 tick）：

1. 静默任务先按 v1 发一条 `task.progress`（`stall: true`），正文给「继续 `<ref>`」「停止 `<ref>`」；
2. 随后 `worker.cancel()` 中止执行器子进程（协作式取消），checkpoint 以 `aborted` 关闭；
3. **先 abort 再迁移**：`transition({to:'paused', reason:'watchdog:stalled'})`——顺序反了会撞
   `paused → succeeded` 非法迁移；迁移失败只 warn，不回滚已杀进程；
4. worker 看到 `paused|cancelled` 只释放资源锁（`skipped`），不再结算/补回执。

**恢复**：控制命令 `继续 <ref>` → `tasks.resumeTask()`。允许 `paused → queued`，清租约、
`next_attempt_at`、`started_at`，`attempt` 归零并写 `task.resumed`；任务**从头执行**，不是断点续跑。
再次静默会再次暂停（循环稳定）。

**验证**：`verify-gateway 117`、`verify-tasks 100`、`verify-host 36`；生产演练把阈值临时调成 1 分钟：
`sleep 3600` 任务 60s 自动 `paused`、checkpoint 77ms 后 `aborted`；`继续` 后 150ms 内重新 `running`、
60s 后再次暂停。演练后阈值已还原 15。

### 12.30 对话连续性：线程历史与补充指令打断重跑（2026-11-18，`2026.11.18-3`）

**修掉的三个实测缺陷**：

1. `task_inputs` 只写不读：生产库 4 条 `pending`（11-13 起）从未被任何执行器消费，补充指令被静默吞掉；
2. 前台决策共用一个常驻 SDK 会话，prompt 只带当前消息，跨 chat 还会串味；
3. 任务执行只拿 `intent`，没有线程历史，追问与「在刚才结果上再改」无法完成。

**实现**：

- **`gateway.threadHistory(threadId, limit=12)`**：只取本线程的入站 `message` 与已发送的 `say`
  （control / card_action / 其他 topic 不算对话），文案在 ① 边界脱敏，旧→新返回；
- **决策 prompt** 增加「最近对话（旧→新）」最多 8 轮 / 每轮 220 字，并明确要求指代从历史解析、
  仍不清楚就问；**SDK 会话按 `threadId` 隔离**（同一常驻进程、每个线程一个 session）；
- **`tasks.steerTask`**：
  - `running`/`paused` → `queued`，`intent` 追加「补充指令：…」，`attempt=0`、清租约与 `started_at`
    （`applied=rerun`）；host 随后 `worker.cancel()` 中止旧子进程；
  - `queued` → 只改写 `intent`（`merged`）；
  - `waiting_approval`/`waiting_input` → 只改写 `intent`（`recorded`，恢复后生效）；
  - 输入行 `pending → delivered`，下一次 `claimTask` 标 `read`，生命周期闭环；
- **host 两条入口都生效**：orchestrator 的 `input-queued` 与 ① 直接路由到任务的锚定消息
  （`target.kind='task'` + `relay.enqueued`）都会调用 `steerTask`，并回执三种文案之一。

**边界**：`intent` 是追加不是替换；`waiting_approval` 的卡片摘要不会重画（以任务 `intent` 为准）；
历史只用于决策与指代，不是完整转写；本次不改变终态任务的唤醒规则（仍走 AR37 复验）。

**验证**：`verify-gateway 119`、`verify-tasks 102`、`verify-orchestrator 52`、`verify-host 41`；
全量 41 套件通过。生产实测（飞书网页端发送「执行 sleep 300」→「等待改成 30 秒，重新开始」）：
`task.steered`（rerun）→ 旧 checkpoint `aborted` → 新 attempt 立即 `running`，输入行 `delivered→read`，
回执为「实际耗时 30.004 秒」；随后追问「刚才那个任务的结果是什么？」正确解析到同一任务。
生产上原有 4 条历史 `pending` 行保留不动（早于本切片，不再增长）。

### 12.31 消息去重（Slice AO.1，2026-11-18，`2026.11.18-4`）

**动机**：浏览器自动化重发同一条问题（新 `msg_id`、同文本）时，它被当成补充指令，
把正在执行的查询任务打断重跑。客户端重试/双击也不该有这个副作用。

**规则**（① `ingestInbound`，在入库之后、triage 之前）：

- 仅 `kind='message'` 的纯文本参与；`control` 与卡片动作永不去重；
- 同一线程内，本条文本与**紧邻的上一条用户消息**相同，且距其 `received_at`
  ≤ `DSH_WFXM_DUPLICATE_WINDOW_SECONDS`（默认 `60`，`0` 关闭）→ 判为重复：
  inbox 置 `done`，写 `route_decision(action=ignore, reason=duplicate content…)`，
  `bypassReason='duplicate'`，**不建任务、不投递、不打断、不回执**；
- 文本按 ① 的 `inboundText` 归一（去首尾空白并脱敏），所以空格差异仍算重复；
- 只比较最近两条用户消息，不做全历史去重；窗口过期后的同文本视为新消息。

**验证**：`verify-gateway 119`（同文本 60s 内忽略、不同文本放行、窗口过期后放行、
重复行 `done` + `ignore`）；`verify-host 41`（重复消息不改 `intent`、不产生打断回执）；
`grants` 的 AR37 场景显式 `duplicateWindowMs: 0`，与去重解耦。全量 41 套件通过。
生产实测：同一句「查看一下当前磁盘使用率」在 38 秒内发两次，第二次 `inbox` 直接 `done`、
`route_decision(ignore, duplicate content within 60s)`，无新任务、无第二条回复。

### 12.32 任务执行上下文：同线程已有结果（Slice AP，2026-11-18，`2026.11.18-5`）

**动机**：AO 之后补充指令能进 `intent`，但执行器只拿得到 `intent`——同一线程上一轮写了什么文件、
跑过什么命令，只存在于 ① 的对话里；用户说「在上面基础上再改」时只能重做一遍。

**实现**：

- **`tasks.recentThreadResults(taskId, limit=2)`**：只读 ⑤ 自己的 `task_threads` / `tasks` / `receipts`；
  取与当前任务同线程、`status='succeeded'` 且 `receipts.round = tasks.round` 的回执，
  按 `finished_at DESC` 排，排除自身；`limit` 上限 10；
- **worker** 在执行前组装 `threadContext`（最多 2 条，摘要截断 300 字、折叠空白，带 `taskRef` 与完成时间），
  通过 `ExecutableTask.threadContext` 交给执行器；该读取是非必需的，失败只走 `onError`，不阻塞执行；
- **executor** 把 stdin 从 `intent` 改为 `intent` + 空行 + `threadContext`，**intent 永远在最前**；
  没有上下文时与原先完全一致。

**边界**：只看线程，不跨线程；只取成功任务的回执（失败/取消不注入）；上下文只读、不回写任务、
不改写 `intent`；⑤ 仍不读 ① 的表。

**验证**：`verify-tasks 104`（store 的同线程过滤 / limit / 排除自身与失败、worker 注入上下文）、
`verify-executor 21`（stdin 中 intent 在前、上下文在后且内容正确）；全量 41 套件通过。

### 12.33 重启后的前台 SDK 会话续接（Slice AQ，2026-11-18，`2026.11.18-6`）

### 12.34 等待输入闭环（Slice AR，2026-11-18，`2026.11.18-7`）

**现象**：`waiting_input` 状态、迁移表、事件与提醒文案都在，但没有写入入口——

### 12.36 提醒（Slice AT / J5，2026-11-18，`2026.11.18-9`）

**现象**：没有任何「提醒」实体；future 时间的提醒塞进 ⑤ 会被 worker 立刻领取执行；

**机制**：

- 新增 `@dsh-wfxm/reminder`（`plugins/reminder`）：

### 12.37 邮件只读能力（Slice AU / J1，2026-11-18，`2026.11.18-10`）

**能力**：任务执行器里的三个只读工具 `mail_search` / `mail_read` / `mail_digest`（R0）。
前台（sdk profile）不挂这些工具，查邮件仍由前台建任务、执行器调用（AR25）。
`mail_digest`（Slice BC / J2）按 `hours`（1..168，默认 24）、`unreadOnly`、`limit`（1..50）
只读 INBOX 头部元数据，分 `需要回复 / 需要处理 / 仅供参考`，输出里明确标注

**后端**：`plugins/mail/scripts/mail-query.py`（Python 3 标准库 `imaplib` + `email`），
`select('INBOX', readonly=True)` 只读打开；密码经 **stdin** 传入，不进 argv、不进日志。

**配置**（一次性）：

1. 在邮箱后台开启 IMAP 并生成**授权码**（QQ：设置 → 账号 → 开启「IMAP/SMTP 服务」；
   163：设置 → POP3/SMTP/IMAP → 开启 IMAP/SMTP → 新增授权码）。163 的 IMAP 主机是
   `imap.163.com:993`，且服务端要求客户端发送 IMAP `ID`（本项目已用 `xatom` 处理）。
2. 写 `~/.dsh/integrations/dsh-mail/config.json`：

   ```json
   {"account":{"host":"imap.163.com","port":993,"secure":true,"user":"you@163.com","secretRef":"mail/163"}}
   ```

3. 把授权码写进**邮件专用**的 `~/.dsh/integrations/dsh-mail/credentials.yaml`：

   ```yaml
   refs:
     mail/163: <授权码>
   ```

   **不要**写进 `~/.dsh/.credentials.yaml`：那是 dsh 的凭据库，`refs` 键必须是
   POSIX 环境变量名；`mail/163` 含 `/` 会让整份库解析失败，连带 `DEEPSEEK_API_KEY`
   失效（2026-11-19 真机踩过）。
   生产也可直接用 `DSH_WFXM_MAIL_HOST/PORT/SECURE/USER/PASSWORD` 环境变量
   （推荐写在 `/etc/dsh-wfxm/env`，`0600`），此时不需要 `config.json`。

**挂载**（幂等）：开发机可跑 `node scripts/install-mail-profile.mjs`（默认 `headless` profile）；
**生产必须挂到服务用户的 profile**，并把链接指向 release（`dshwfxm` 无法穿过 `/home/ailearn` 的 0750）：

```bash

chown -h dshwfxm:dshwfxm /var/lib/dsh-wfxm/home/.dsh/profiles/headless/node_modules/@dsh-wfxm/mail
runuser -u dshwfxm -- env HOME=/var/lib/dsh-wfxm/home dsh --profile headless --dump-config | grep mail
```

日历（J4）同理，脚本换成 `node scripts/install-calendar-profile.mjs`，链接指向

**边界**：只读 INBOX、单账号；不发送、不删除、不标记已读、不下载附件；

### 12.38 变更生命周期与半应用回滚（Slice AV，2026-11-18，`2026.11.18-11`）

**是什么**：`@dsh-wfxm/changes` 在 `ops.sqlite` 记录每次 R2/R3 变更走到哪一步
（`applying → applied → verified → kept`、`applying → failed`、`applying|failed → rolled_back`），
并在进程启动时处理上一个进程遗留的**半应用**（docs/11 §5.4、docs/15 §模块 ⑦）。

**接线**：
- ⑤ worker：R2/R3 执行前 `begin`（R3 带 `snapshotId`，按 `task_id` 幂等）；Verifier 通过后 `keep`；
  终态失败 `markFailed`；可重试失败保持 `applying`。`begin` 失败 → 任务 `failed`
  （`reason='change-record-failed'`），**不执行**——不做"改了但不记账"。
- host：`recoverChanges()` 在 `worker.recover()` **之前**执行（`serve` 启动第 6 步）：
  任务已 `succeeded` → 只补账 `kept`；其余 `claimRollback` 后，
  有 `snapshot_id` 走 `restoreWorkspace(snapshotId)`，否则 `rollbackPreimages(taskId)`；
  成功 `rolled_back`，失败 `rollback_status='failed'` + `warn`（不猜、不自动重试）。

**日志**：启动时 `recovery:changes {"kept":n,"rolledBack":n,"failed":n}`；`modules` 行含 `"changes":"on"`。

**边界**：不注册 `svc_start/svc_stop/svc_restart`（headless 审批未统一，避免双闸/绕过），
`kind='service'` 只留表结构；不做运行中巡检；`restic:` 快照不可还原 → 回滚失败留痕。

**真机演练（2026-11-19，维护窗口）**：停服 → 备份 `ops.sqlite` → 在
`/var/lib/dsh-wfxm/workspace/av-recovery/note.txt` 写入 `MUTATED-AV-2026`，并注入
`changes(status='applying', snapshot_id=NULL)` 与对应 `file_preimages(state='present',
content_ref=inline:<原内容>)` → 启动服务。日志：
`recovery:changes {"kept":0,"rolledBack":1,"failed":0}`，文件恢复为 `ORIGINAL-AV-2026`，
台账终态 `status='rolled_back' / rollback_status='done'`。清理演练行与目录后再次启动为
`{"kept":0,"rolledBack":0,"failed":0}`，`listHalfApplied` 为 0。

（与时区/时间格式一起校验），不会静默降级成"没开"。

| 变量 | 默认 | 含义 |
|---|---|---|
| `DSH_WFXM_MAIL_DIGEST_AT` | 不配 = 关闭 | 本地 `HH:MM`，例如 `08:30`；`off` / `0` 也视为关闭 |
| `DSH_WFXM_MAIL_DIGEST_CHANNEL` | `feishu` | 投递渠道（① 的 `channel_id`） |

| `DSH_WFXM_MAIL_DIGEST_HOURS` | `24` | 回看小时数，1–168 |
| `DSH_WFXM_MAIL_DIGEST_LIMIT` | `20` | 最多展示封数，1–50 |
| `DSH_WFXM_MAIL_DIGEST_UNREAD` | `1` | `0` / `false` / `off` = 包含已读 |
| `DSH_WFXM_MAIL_DIGEST_TZ` | `Asia/Shanghai` | 判定时区（不依赖进程 TZ） |
| `DSH_WFXM_MAIL_DIGEST_STATE` | `<数据目录>/mail-digest-state.json` | "今天已发"状态文件 |

- **验证**：`verify-mail` 31 例（新增 7 例调度）、`verify-host` 62 例（新增 5 例）、

  状态文件 `lastDate=2026-11-19`。随后恢复 `AT=08:30` 重启，日志
