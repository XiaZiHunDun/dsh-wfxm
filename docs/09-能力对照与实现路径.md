## 一、四种判定口径

| 判定 | 含义 | 交付形态 |
|---|---|---|
| ✅ **直接可用** | dsh 原生装上有，配置即可 | 改 profile，不写代码 |
| 🔧 **需适配** | dsh 有骨架或接缝，要写胶水/补语义 | 小插件或配置 |
| 🏗 **需自建** | dsh 没有，必须自己实现 | 自建插件 |
| 🔄 **换方案** | 产品目标与 dsh 语义冲突，**必须先做产品决策** | 决策，不是代码 |

> **🔄 不是"实现难"，是"没定就不该动手"。** 这类项与 §五的阻塞决策点一一对应。

## 三、缺口清单与工程量分级

**dsh 覆盖了 L1 大部分、L2 全部、L3 前四种。缺口集中在四块（治理、通道、管家、知识），另有一条工程化工具链。**

| 缺口块 | 含能力项 | 工程量 | 落点 |
|---|---|---|---|
| **L6 治理** | H2 H3 H5 H6 H7(部分) + I3 | **最大**，且是"全域+微信可达"的前提 | 本仓 `plugins/governance/` |
| **L4 通道** | A5 A7 I3(入站去重) + 审批体验 | 中；**协议层 0 行，胶水层几百行** | 本仓 `plugins/wechat-channel/`（仅当 V5/V6 不达标） |
| **L5 管家** | B4 C6 G2 G3 G4 G5 | 中；**技术不难，定义难** | 本仓 `plugins/svcops/` + 巡检插件 |
| **知识层** | B6 F3 F4 F5 F6 + E6 | 中；**先决策后实现** | 本仓 `plugins/knowledge/` |
| **工程化层** | N2 N6 N8 | 小；**是工具链，不是产品功能** | 本仓 CI + `scripts/` |

| `domain` 纯规则 | 4,726 行（不含测试） | 🔧 作**语义参考**，类型体系不同需改写 |
| acceptance 场景库 | `_fixtures.ts` 内 **58 个 fixture 场景**（A/B/C/D 四类）；可执行测试仅 `realistic.test.ts` 的 3 个 `it` | 🔄 场景清单可作验收基准，但深度绑 `runButlerLoop` + `/v1/wechat/inbound`，**必须重写** |

**结论：真实复用率约 3–7%。**

`apps/api`（**18,592 行，不含测试**）—— HTTP 入口 + composition root + 全部微信业务编排 ——
**基本全废**，由 dsh 的 session/event + agent loop + 渠道插件取代。

> **所以：这不是"迁移"，是"换壳重写 + 小面积移植"。**
> 用"迁移"叙述会让 owner 低估工作量、高估"保留了 Butler 资产"。建议全文改称**"重建"**，
> 只有 iLink 与 schema 那部分叫"移植"。

## 四、阻塞开工的决策点与关键路径

08 §七 列了 6 个决策点。**截至 2026-10-28，两条阻塞项已全部落定。**

| # | 决策点 | 阻塞级别 | 结论 |

### 一级风险：版本撕裂（新增）

01–08 把"dsh 是 alpha、会破坏兼容"列为**一条待验证**，但它实际是**架构级风险**：

- dsh `README.md` 明文承诺 breaking changes；`SAFETY.md` 声明未做安全审计；
- dsh-im 钉 `>=0.2.0-rc.2 <0.3.0-0`，本机 dsh 是 `0.2.1-alpha.3`；
- **自有治理插件同样要跟着 dsh 的 breaking change 走**——Step 2 之后每写一层，都会周期性返工。

**必须先定的对策**：锁死 dsh 版本 + 插件仓自带**兼容测试矩阵**（每次升 dsh 前重跑）。
**没有这一条，Step 2 起的每一层都在流沙上。**

### 关键路径（修正 05）

```
Step 0 环境（含版本锁定策略）
   └→ Step 1 零代码验证 ──┬─ V1 多项目不打架  ─┐
                          ├─ V3 对话不再劣化  ─┼─ 全通过 → Step 2 治理 → Step 4/5
                          └─ V2 并发改文件    ─┘  任一不通过 → 停止重估
```

**V1 / V3 才是分叉点。V2 不是。**
dsh 不替你把并发策略接上，这件事**几乎先验成立**——所以 V2 只提供观察、不提供 go/no-go。
应在 Step 1 顺手观察即可，**不要把它当一个会拦住项目的前置条件。**

## 五、逐条实现路径（按建议顺序）

| 序 | 交付 | 覆盖能力 | 前置 |
|---|---|---|---|
| 1 | **审计落库**（消费 session event → `audit_events`，补 actor） | H3 I4 | 无。**先做这个**——没有审计就无法验证授权生效 |
| 2 | **入站准入**（先"小号物理隔离"零代码，再写过滤器） | H2 | 无 |
| 3 | **最小授权形态**：确认 + 路径/命令白名单 + kill switch + 撤销 | H1 H4 H5 | 1、2 |
| 4 | **网络管控**（3 档 profile，dsh out of scope 需自建） | C7 H5 | 3 |
| 5 | **每日摘要**（消费 session event → 微信推送） | G3 A3 | 无。**验证推送链路，最容易见效** |
| 6 | **服务存活巡检** | B4 G2 | 5 |
| 7 | **服务管理**（起停/重启/看日志） | C6 | 6。**"管家"最实的一块** |
| 8 | **中文渠道插件**（复用 iLink 1,228 行；补流式 + 中文审批 + 白名单） | A5 A6 I1 | 仅当 V5/V6 不达标才做 |
| 9 | **跨项目知识** | B6 F3-F6 E6 | **先做决策 #3** |
| 10 | **幂等去重** | I3 | 有渠道后 |

> **顺序原则**：1 必须在 3 之前（先有审计，才能验授权）；5 在 6/7 之前（先验通推送链路，再堆内容）。
> 与 05 的两处差异：① 审计与准入提到最前（05 把两者都放在 Step 2，但 1 是 2 的前提）；
> ② 摘要提到巡检/服务管理之前。

## 八、与 08 的衔接

08 的 MVP 边界（第一版必须有）与本文字段对照：

```
08 的 MVP（36 项）：A1 A2 A3 A4 | B1 B2 B4 | C1 C2 C3 C5 C6 | D1 D2 D3 D6 D7 | E1 E2 E3 | G1 G2 G3 G6 | J1 J5 J6 | H1 H2 H3 H4 H5 H7 | I1 I2 I3
```

| 其中 | 判定分布 |
|---|---|
| ✅ 直接可用 | A1 A2 B1 C1 C2 C3 C5 D1 D2 D3 D6 D7 E2 E3 **G1** **J6** H1 I2 |
| 🔧 需适配 | A3 A4 B2 E1 **J1 J5** H4 H5 H7 I1 |
| 🏗 需自建 | **H2 H3 I3** ← **MVP 的三个硬缺口** |
| 🏗 需自建（管家） | **B4 C6 G2 G3 G6** ← 不是准入性质，但会占用 MVP 工期 |

> **MVP 的三个硬缺口是 H2（入站准入）、H3（审计落库）、I3（幂等）。**
> J1 改由社区插件承接，但仍需验收与版本锁定，不等于零风险。
> 管家 5 项（B4/C6/G2/G3/G6）同样需自建，排在治理之后、按 `05` Step 4 交付。

> **另有六个"上线门槛"不属于 MVP 功能清单，但不能带着缺口接管真实服务器**：
> M1 快照回滚、M2 备份恢复、M3 看门狗自检、M6 审计完整性、M7 注入防护，
> 以及 C8（测试验收）+ M9（评测基线）这一对。
>
> 它们恰好都在 §五建议顺序的**第 1–3 位**——即"先做治理，再做别的"。这不是巧合：
> **P3 全域 + P1 微信可达 的组合，使得治理不是附加项，而是 MVP 的准入条件。**
