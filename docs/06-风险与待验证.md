## 二、外部风险（技术手段无法缓解）

### 腾讯账号风控 —— 最高优先级风险

- **协议合规不等于账号安全。** 四家插件全用官方 iLink，零个用逆向 hook —— 但腾讯侧对"机器人行为"仍有独立的风控判定。
- **实测证据**：dsh-im issue #2 有用户换 5 个新 bot 后 `sendmessage` 返回 `ret:0` 但
  **无 `message_id`、手机端连会话记录都没有**（服务端接受但不投递）。作者无法复现，判为账号侧风控。
- **对策**：
  - 用**小号**，不用主账号
  - 遇到投递问题**不要反复重扫/换 bot** —— 那正是触发风控的动作
  - 不外传 bot 账号
  - 保持备份（`SAFETY.md:22` 建议）

**这是整个方案最可能致命的地方，且与 dsh 的质量无关。** Step 1 就要验证它。

### dsh 是 alpha + 明文承诺破坏性变更

- `README.md:13`：**THERE WILL BE COMPATIBILITY-BREAKING CHANGES**
- `SAFETY.md:7`：未做安全审计，不得视为 production-ready
- 历史先例：dsh-im issue #253 跨版本直接炸 `SessionFormatError`

**对策**：锁插件版本（`dsh-im@5.7.0` 而非 latest）；每次 dsh 升级前重跑插件自检脚本。

## 四、已知的坑（写代码时会遇到）

### dsh 侧

1. **`credentials` 的 scope 语义冲突**
   `packages/credentials/src/types.ts:17-22` —— key 是 `<scope>/<id>`，但这里 scope 是
   **"持有该记录的插件名"，不是权限范围**。与 Butler 的"授权范围"同名不同义，**极易踩**。
   `CredentialInfo` 无 `expiresAt` / TTL。

2. **`experimental/webhook` 无幂等去重**
   README：repeated delivery runs the rules again。若走 webhook 路线，需自己补（Butler 的 D74 有现成能力）。

3. **插件版本锁定是必须的**
   peerDependencies 不匹配时宿主**静默跳过整个 bundle**（stderr 打 `skipping profile bundle`），
   桌面端表现为"插件消失了"。容易误判成安装失败。

4. **没有 in-process 嵌入契约**
   `docs/architecture.md:45` + gate 脚本 `verify-application-entrypoints.ts`。
   自定义走 profile + patch 文件，不要试图 inline 挂 cordis。

5. **不要从 dsh-plugin.org 装**
   issue #124/133/297/298/302/354/356 全是这条路径失败。走 npm 或 github 源。

### Butler 侧

6. **`_analyze.md` 是有意提交的生成物**
   `tests/acceptance/scenarios/_analyze.md` 由 acceptance 测试每次运行重写（换日期 + 随机 temp 路径）。
   D70/D71/D72 都专门 refresh 它 —— 是协议的一部分，不要 untrack。
   但本地先跑测试再跑 `format:check` 会报它未格式化（CI 顺序是先 format-check 后 test，所以 CI 不受影响）。

7. **本机 `~/githubpro/cordis` 与 dsh vendor 的 cordis 不是一对**
   本地是 `4.0.0-rc.11`；dsh 的 `vendor/` pin 的是 rc.7，vendor 包自己标 `4.0.0-alpha.2`，且含本地修改。
   做上游对照时注意这个 gap。
