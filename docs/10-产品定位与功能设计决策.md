# 10 — 产品定位与功能设计决策

> **本文回答一个问题：这个产品到底做什么、长什么样、第一版砍到哪。**
> 依据：`openmuse`（MIT）、`nanoMuse`（GPL-3.0）、本仓 08/09，以及 dsh 源码。
> 本文是**决策建议**，不是已定稿；owner 确认后再回写 08（产品侧 SSOT）。

---

## 〇、结论先行

**一句话定位：一个人的服务器总管 —— 既做开发与运维，也管日常生活；通过企业微信/飞书下达，在服务器全域自主执行，每一步可审计、可撤销。**

**四个闭环（第一版每个闭环各取最小形态）**

| 闭环 | 用户故事 | 完成标志 |
|---|---|---|
| **A 开发闭环** | 微信说"给 X 项目加个接口" → 改代码、跑测试、改到绿 | 回执里能看到 diff、测试输出、commit |
| **B 运维闭环** | 微信问"服务为什么 502" → 查日志、查进程、给诊断 | 回执里能看到证据链和结论 |
| **C 主动闭环** | 定时巡检 → 异常才找你 → 你一句话确认修复 | 告警有分级，修复可回滚 |
| **D 生活闭环** | 微信问"今天有什么要紧的" → 邮件摘要 + 日程 + 提醒 | 一条摘要说清，需要你决定的单独列出 |

**四条不做**（详见 §三）

1. 不做资金类操作（支付/下单/转账）—— 只准备，不执行
2. 不做多设备 mesh / 手机屏幕遥控
3. 不做多租户 SaaS / 账号体系
4. 不做个人微信自动化

## 一、两个参考项目：它们各自验证了什么

| | **OpenMuse** | **nanoMuse** |
|---|---|---|
| 定位 | 跨生活场景的个人 agent（邮件/日历/目标/财务/文档） | 长在你自己的设备上的个人 agent，无中间人 |
| 形态 | Next.js + React Native 原生 App | Web + Android + iOS + 桌面（Electron），**桌面就是 dsh 的插件 bundle** |
| 规模 | 约 37.5k 行 TS/TSX | 约 122k 行 Python + dsh 插件包 |
| 核心机制 | 持久化任务 + 结构化 review + 回执；浏览器 workder + 无网 Linux 沙箱；目标/追踪/通知收件箱 | **Sentinel 治理**（allow/ask/deny + taint + vault + 脱敏 + JSONL 审计）；**三档审批**（once / this chat / always）；执行梯子（skill → API → 浏览器 → 屏幕）；渠道配对码；多设备续跑 |
| 与 dsh 的关系 | 无关（CopilotKit / AG-UI） | **`harness/dsh-nanomuse` 是完整的 dsh 插件 bundle 参考实现** |
| 许可 | MIT —— 代码可借用（保留版权声明） | **GPL-3.0 —— 代码不可抄进本仓**，只能学设计 |

### 最值得拿的四件事（都是设计，不是代码）

1. **任务是一等对象，聊天只是入口。** OpenMuse 的 delegated task 是服务端持久工作，有 review 和 receipt；nanoMuse 的后台 run 结束后回投到"deliver here"的渠道。聊天记录不是交付物，**回执**才是。
2. **审批要带范围，不是 yes/no。** nanoMuse 的卡片给 *once / this conversation / always*，并在 Permissions 页逐条可撤销。更关键的一条安全设计：**从聊天渠道来的审批只算 once，永不记住**（`docs/channels.md:182`）。
3. **执行按梯子降级。** nanoMuse 把手机屏幕放最后一档：能用 skill/CLI 就不开浏览器，能开浏览器就不点屏幕。服务器场景同理：**能 CLI 就不碰 GUI，能 API 就不 SSH 交互**。
4. **准入是配对的，不是白名单硬编码。** 陌生人先拿 6 位配对码，配对数据放在 agent 够不到的地方（`docs/channels.md:121-141`）。

### 不能照搬的

- OpenMuse 的生活域广度（邮件/日历/财务）会把"服务器管家"稀释成"什么都会一点的助手"。
- nanoMuse 的多设备 mesh、屏幕 hands、云 relay —— 我们第一阶段是**单机、单 owner、微信一个入口**。
- **nanoMuse 明确把微信自动化列入 Tier 3 不推荐**（`docs/services.md:43`）：违反 ToS、账号会被限制。这与 06 的判断一致，且由第三方独立佐证。

## 二、定位决策

### D1. 定位：双域总管，深度在服务器，广度在生活

**决策**（owner 已定）：**开发/运维 + 日常生活都要有**。但两者不是平权：
**服务器是深度（差异化），生活是广度（留存）**。

**理由**
- 只做 dev/ops，产品是"一个更好的运维机器人"，天花板低；只做生活，会和 openmuse/nanoMuse 正面撞车。
- 两者的交集正是我们的位置：**生活任务需要一台一直在线的机器**（收邮件、盯网页、定时提醒），而我们已经有一台可执行、可审计的服务器。
- 两域共用同一套记忆、权限、审计 —— 这是"一个总管"而不是"两个 bot"的关键。

**代价与风险**
- 广度会稀释深度：生活域必须**限制在 12 项**（见 08-J），不做社交自动化、不做支付。
- 生活域的输入（邮件/网页）是**不可信内容**，治理成本比 dev/ops 更高，不能因为"只是生活"就放松。

**边界**：不做个人设备 mesh、不做手机屏幕遥控、不做资金操作。

---

### D2. 入口：微信是唯一入口，但微信不是产品形态

**决策**：微信只承担三件事——**下单、审批、收结果**。复杂内容（diff、日志、报告）落成链接或附件，不在聊天里刷屏。

**理由**
- 微信的限制（1800 字分片、无卡片、无流式）不该成为产品设计的约束。
- OpenMuse 的做法值得借鉴：聊天里只放"有意义的状态 + 需要你决定的事"，细节进 review/receipt 页。

**落地**
- 每条任务有**任务号**；进度用阶段式（`已定位 → 改动中 → 测试中 → 待确认`），不做逐字流。
- 超过 ~600 字的内容一律转成附件/链接，微信里只留摘要。
- 审批用纯文本关键词（`允许` / `拒绝`）兼容无卡片渠道。

---

### D3. 渠道：企业微信/飞书为主，个人微信可选过渡（owner 已定）

**决策**：正式形态走**企业微信智能机器人或飞书**；个人微信自动化标为**最高风险路径**，只作可选过渡，产品设计不依赖它。

> **2026-10-28 复核**：`dsh-im@5.7.0` 同一插件已覆盖微信/企微/飞书/钉钉/QQ 等 10+ 渠道，
> 渠道切换是**配置变更**，不需要另写适配器。这降低了 D3 的迁移成本，但**不改变风险判断**：个人微信仍不作主路径。

**理由**
- nanoMuse 把微信自动化列为 Tier 3；两家成熟产品都选择飞书/钉钉/企微/Telegram，不是偶然。
- 06 已把"腾讯账号风控"列为最高风险；这是产品级风险，不是技术风险。

**代价**：企微需要企业主体；个人使用要评估。**这条需要 owner 拍板，不能替答。**

## 三、功能设计决策

### D4. 四个一等对象（取代 9 个域的平铺）

| 对象 | 是什么 | 对应 08 |
|---|---|---|
| **Conversation** | 一次对话，可多轮、可续跑 | A1-A7, F1-F2 |
| **Task** | 一次被委派的持久工作：目标、阶段、产物、状态 | D1-D6, D8 |
| **Receipt** | 任务结束的回执：做了什么、证据、diff/日志、可否回滚 | I2-I4（需新增对象） |
| **Grant** | 一条被授予的权限：范围、过期、来源、撤销 | H1, H6 |

**理由**：用户能理解的只有这四个。9 个域是分析工具，不是产品结构。

---

### D5. 审批：默认问，四档风险，三档范围

**决策**

| 风险档 | 例 | 默认行为 |
|---|---|---|
| **R0 只读** | 读文件、查日志、查状态、搜索 | 自主，不打扰 |
| **R1 工作区内写** | 改项目内代码、跑测试、git commit 到分支 | 自主，记审计 |
| **R2 越界写** | 跨目录写、装包、改配置、重启非生产服务 | **ask** |
| **R3 不可逆/生产** | 删数据、改生产服务、部署、外发消息、读凭证 | **ask + 强确认**（回显具体命令/目标） |

范围三档：**本次 / 本会话 / 永久**。永久授权进"权限中心"，可逐条撤销。
**从微信来的审批只给"本次"**（借 nanoMuse 的安全规则）。

**理由**
- 这直接回答 owner 决策 #1：不是"全自主 vs 全确认"二选一，而是**按风险分档**。
- dsh 的 `approval/request` 是 waterfall，插件可拦截并等外部应答；nanoMuse 已验证"always = 存一条 grant + 本次仍返回 allowed-once"的落地方式（`harness/dsh-nanomuse/src/desk.ts:155,194`）。

**代价**：要做 grant 存储 + 权限中心 + 过期/撤销。这是 09 里 H6 自建面的一部分，但**比完整 ScopedGrant 小**——第一版不需要"绑定 run + 跨重启恢复审批中状态"。

---

### D6. 执行梯子：CLI/API → MCP → 浏览器 → GUI

**决策**：任何任务先走确定性接口；只有没有接口时才用浏览器；GUI/截屏是最后手段。

**理由**
- 服务器上的服务管理天然有 `systemctl` / `docker` / 云厂商 API，没必要模拟点击。
- 梯子决定"服务管理"（09 里最大的空白）**根本不需要 GUI 自动化**，只需要命令白名单 + 输出解析。成本从"造一个 computer-use"降到"写一组工具"。

---

### D7. 网络：默认关，白名单开，按需审批

**决策**：三条网络档位，绑定到工具而不是绑定到进程。

| 档 | 行为 |
|---|---|
| `off` | 文件/进程操作，不出网 |
| `allowlist` | 只允许包源、git 远端、部署目标、监控 API |
| `ask` | 其它出网逐次确认 |

**理由**
- dsh 沙箱**没有网络维度**（已复核），bwrap 参数无 `--unshare-net`，所以只能做工具级管控。
- OpenMuse 的边界设计更彻底：**终端无网，浏览器负责公网访问**。我们照这个思路，把"终端"和"网络"分成两个工具面。

**代价**：要维护域名白名单；误拦会打断部署。第一版白名单宁宽勿窄，但**所有出网都记审计**。

---

### D8. 主动性：三级打扰，默认静默

**决策**

| 级别 | 触发 | 去向 |
|---|---|---|
| **静默** | 成功、例行完成 | 只进审计与日报 |
| **摘要** | 每天一次 | 一条微信摘要（做了什么、花了多少、待办） |
| **告警** | 服务挂、部署失败、磁盘满、需要人决策 | 立即推送，带任务号与一句话结论 |

**铁律：只推异常和需要人的事，不推"成功"。**

**理由**：OpenMuse 的规则是"meaningful completions or requests for input"；nanoMuse 只投递"后台 run 的最终结论、等待的审批、需要回答的问题"。微信推送频率直接关联账号风控与用户耐受度。

---

### D9. 记忆：三层，写入要确认，可遗忘

| 层 | 内容 | 生命周期 | 写入方式 |
|---|---|---|---|
| 身份/偏好 | 称呼、语气、禁区、习惯 | 永久 | 需确认 |
| 项目知识 | 架构、约定、坑、决策 | 随项目 | 任务结束时提议，确认后写入 |
| 会话 | 当前上下文 | 随会话 + 压缩 | 自动 |

**理由**：OpenMuse 明确"editable/forgettable memories"；nanoMuse 的 memory 是"one-line facts，读进每个 chat"。**没有遗忘机制的记忆就是技术债。**

**回答 owner 决策 #3**：跨项目默认**隔离**；知识要跨项目，只能通过显式"晋升"动作，不做自动共享。

---

### D10. 多项目：一项目一 workspace + 一 preset

**决策**：项目注册表 → 每个项目一个 workspace、一套 preset（工具集/权限/模型）、一个默认分支策略。项目间默认不可见。

**理由**：dsh 的隔离单位是 workspace + agent preset，这正好对上。同项目并行写要靠 `withFileLock` 的**策略**（锁粒度 + 冲突退让），不是从零造锁（见 09 §六·修正 1）。

---

### D11. 产品形态：单 owner、单机、自托管、无账号

**决策**：本地部署，数据不出机器；模型用 owner 自己的 key；没有注册、没有云、没有计费。

**理由**：两家参考项目的共同底线都是"自己的 key、自己的数据"。这也是与商业 agent 的差异点。

---

### D12. 第一版只交付五个能力域的最小形态（§〇）

**决策**：MVP 只交付 A/B/C/D/G 五个闭环的**最小形态**（共 36 项，见 09 §八），其余全部推迟。
生活域第一版只做 **邮件读取（J1）+ 提醒（J5）+ 网页检索（J6）**；日历、邮件发送、持久登录浏览器后移。
**管家最小切片 = B4 + C6 + G1 + G2 + G3 + G6**（owner 2026-10-28 决定：进第一版）。

**理由**：08 的 119 项是愿景，不是第一版。09 已指出 MVP 的硬缺口是 **H2 / H3 / I3 三项**——**先把治理做出来，再谈广度。**
管家进 V1 后仍守一条线：**只发现 + 报告，不擅自修复**；修复（C6）一律走 R3 确认。

### D13. 浏览器：持久登录的工作浏览器，不是无状态网页阅读器

**现状（源码核实）**
- dsh 有 `packages/browser-use`：只是一个 **provider 注册位**，一次只能挂一个；现成 provider 是 Playwright MCP / Chrome DevTools MCP / Stagehand（均实验包）。
- DSH 拥有任务循环；浏览器归属**某个 live Agent/Session**，跨 turn 复用，Session 销毁即关闭。
- **浏览器 profile 与登录态不从 session log 恢复**（`docs/subsystems/browser-use.md`）。
- `web_search` / `web_fetch` 可用，但 `web_fetch` **不带登录 cookie**，且抓取内容被标记为 external/untrusted。
- nanoMuse 的做法值得照搬：Playwright headless + **持久 profile（`<workspace>/browser-profile/`）**，登录跨重启保留；动作含 navigate/extract/click/type/key/scroll/back/wait/screenshot/**带 cookie 的 fetch**/profile/close，以及人工接管。

**决策**
1. 用 dsh `browser-use` + Playwright provider；**先不上 Stagehand**（要多一个模型，收益不确定）。
2. **自建持久 profile + 登录态**，放在数据目录、权限 600、agent 的文件工具不可写 —— 这是与 dsh 现状的唯一实质缺口。
3. 补一个 **logged-in fetch** 工具（只读、不渲染），大量场景不需要开页面。
4. 默认 headless；登录、验证码、风控页 **必须能交还给 owner 接管**（hand-over），这是刚需不是可选。
5. 页面内容按不可信处理：页面里出现的"指令"不执行；据此产生的副作用操作重新走审批。
6. 浏览器是**出网域**，与 shell 沙箱分离（见 D15）。

**代价 / 风险**：工程量中；三个 provider 都是实验包，必须纳入版本兼容矩阵。

---

### D14. 邮箱：IMAP/SMTP 优先，Gmail API 可选

**现状（源码核实）**
- dsh **没有任何 mail 包**（`packages/` 下无 mail/imap/smtp）。
- nanoMuse 有 `nanomuse/tools/email_tool.py` 与 `triggers/mail.py`（邮件到达触发），Sentinel 对 `send_email` 有 taint 规则。
- openmuse 用 Gmail/Calendar 连接器 + review 页。

**决策**
1. **协议选 IMAP/SMTP**：QQ/163/Outlook/Gmail 都支持应用专用密码，覆盖面最大；Gmail API/OAuth 作为可选增强。
2. 能力按风险分层：**读/搜/摘要（R0）→ 归档/标签（R2）→ 草稿（R1）→ 发送（R3）**。
3. 发送必须回显**收件人 + 主题 + 正文摘要**；**默认禁止自动回复、自动转发**。
4. 邮件正文是不可信输入；附件落隔离区，不自动执行、不自动打开。
5. 触发：v1 用 schedule 每 5–10 分钟轮询；v2 再上 IMAP IDLE。
6. 凭证进 vault，日志脱敏，正文不进普通日志。

**代价 / 风险**：工程量中；主要成本在 MIME 解析、附件处理与发送审批，不在协议本身。

### D15. 沙箱：四域分离（工作区 / 主机 / 浏览器 / 宿主自身）

**现状（源码核实，含一处重要更正)**
- dsh 三档：`read-only` / `workspace-write` / `danger-full-access`。
- bwrap 参数：`--ro-bind / / --dev /dev --unshare-pid --proc /proc --die-with-parent`；`workspace-write` 只额外加 `--tmpfs /tmp` 和 workspace bind。
- **没有 `--unshare-net` → 网络始终可用。** 所以真相不是"dsh 能管网络"，而是**"dsh 关不掉网络"**。
- Landlock / Seatbelt 两个变体同样只管文件写，不管网络。

**决策**
1. **四域分离**：
   - **A 工作区沙箱**：可写 workspace，**默认断网**（自己做 `unshare -n` 包装）。
   - **B 主机受控域**：`systemctl` / `docker` / 日志 / 部署，R2 审批后进入，全部审计。
   - **C 浏览器出网域**：只有浏览器能自由出网，走白名单与持久 profile。
   - **D 宿主自身域**：升级、改配置、改插件；最高危，必须快照 + 审批 + 回滚点。
     （2026-10-28 补：原"三域"漏掉了这一域，11 §七 已按四域锚定。）
2. 需要装包时走**显式的 network 工具 + 白名单**，不允许"沙箱里随手联网"。
3. 主机域**不得常开** `danger-full-access`；只读日志可以放宽到 R1。
4. 生活任务（邮件/日历/浏览）**不进 shell 沙箱**，避免把两种权限混成一个。
5. 浏览器 profile 是 **owner 级单例**（登录态共享符合预期）；需要隔离时显式开 project profile。

**代价 / 风险**：工程量中；`unshare` 与容器/系统的兼容性必须先实测，否则会误伤正常命令。

### D16. 决策层：采用 System One 的"接口形态"，不绑定 Jev

**先纠正一个常见误读**：Jev / System One **不是协议**，是 TypeSafe 的托管模型 API
（`POST /v1/systemone`）。它不生成文本，而是对"一组带类型的题目"返回
**Choice / Score / Noul + 校准置信度**，70–500ms，输入仅文本。

**它能补什么**
- **风险判级**：一条命令/一次工具调用判 R0–R3（这是 D5 最需要的前置判断）。
- **入站分诊**：一条消息属于开发/运维/生活？要不要追问？急不急？
- **告警/邮件分诊**：P0/P1/P2、是否需要人、是否值得记。
- **记忆候选**：这句话值不值得写进长期记忆。

**它不能补什么**
- 代码理解、复杂诊断 —— 仍归主模型。
- 不可逆操作 —— **置信度高不等于判断对**，R3 永远要人确认。
- 敏感正文外发 —— 邮件正文、日志、源码默认不出域，只送标签/命令串/元数据。

**决策**
1. 定义 `DecisionProvider` 接口：`decide(问题, 选项, 上下文) → {choice, confidence, reason}`。
2. 默认实现是**规则 + 主模型**，Jev 只作可选 provider；**停服必须能降级**。
3. 所有自动判级写进审计（choice + confidence + reason）——否则无法解释"它为什么自己批了"。

**代价**：多一层抽象；但不引入它，风险判级就会散落在各处 prompt 里，无法测试。

### D17. MCP：接进来，但先装阀门

**现状**：dsh 有完整 MCP **客户端**（stdio + Streamable HTTP），外部工具会走 permission check 与结果记录；
**没有服务端**。MCP 规范已是 AAIF 标准（`2026-07-28`，转向无状态架构）。

**决策**
1. **用 MCP 吸收长尾集成**（日历、智能家居、监控、云 API），不逐个自建。
2. **核心能力不走 MCP**：治理、审计、svcops、项目注册必须自建，保持可控。
3. **先有 K2 再谈接入**：服务白名单、版本锁定、凭据隔离、逐工具风险映射、首用审批。
4. **工具描述视为不可信**（tool poisoning）：描述里的指令不执行，工具能力以实测为准。
5. **MVP 的邮件不走 MCP**，先自建 IMAP 工具，避免把供应链风险塞进第一个闭环。
6. 对外 MCP Server（K4）放 P2，且必须复用 H2 准入。

**代价**：每个 MCP server 都是一个要审计的第三方依赖；数量要克制，优先"一个有维护者的"。

### D18. A2A：先对齐数据模型，不接协议

**现状**：A2A 已是 AAIF Growth Stage 项目、150+ 组织；dsh **完全没有** A2A。

**关键判断**
- **内部子代理不需要 A2A**：dsh 的 subagent 是进程内、共享治理，比跨进程协议便宜得多。
- **真正的场景只有两个**：
  1. 笔记本上的编码 agent 把"部署/重启/查日志"委托给服务器管家；
  2. 管家把细分任务（研究、比价、票务）委托给外部专用 agent。

**决策**
1. **P0 只做 K8**：Task / Receipt 的字段与状态对齐 A2A Task（submitted / working / input-required /
   completed / failed / canceled + artifacts）。**这一层现在做，几乎零成本；以后接协议才便宜。**
2. **P2 才实现 K9 出站**；先只连可信对端，逐对端授权。
3. **P2 之后才考虑 K10 入站**，且必须过 H2/H3/H4 + 鉴权 + 限流。
   **入站 A2A = 一个新的公网攻击面**，治理没成熟前不开放。

**代价**：现在不做协议，只多写几个字段；代价是以后接入时要补鉴权与错误语义。

### D19. 可替换性：只在高退出成本处做 seam，内核保持不可替换

**判据**：`供应商风险高 × 迁移成本高` 才值得做 seam。两条都高的是模型、渠道、沙箱、凭据、审计；
只有一条高的用适配层；都不高的直接调用。

**dsh 已经把 6 个 seam 免费给了我们**：模型、沙箱（含**远端 SSH 后端**）、浏览器/屏幕、搜索、凭据、MCP。
**不要重造这六个。**

**我们必须自己定义的 seam**：渠道（含兜底通知）、决策、邮件、日历、运行环境操作、存储、审计落点、记忆存储、调度策略
（宿主只给定时器，不给投递与重试语义）。
其中**审计与沙箱必须 fail closed**（不可用就停止执行），模型/搜索/记忆可以 fail soft。

**必须固定、不许可替换的内核**：PolicyGate 与 approval 语义、Task/Receipt、审计 schema、
项目/workspace 语义、配对与准入、数据目录布局。这些一换，产品就不是同一个产品，审计链也会断。
（**判级实现**可经 DecisionPort 切换 S1 规则 / S2 模型 / 外部 Jev，但**语义与所在模块不可换**；见 11 §三·决策层。）

**两条经验**
1. **可替换 ≠ 同时支持。** 默认只装一个 provider，备选"支持但不随版本发布"，避免维护四套渠道。
2. **没有契约测试的可替换是假的。** 同一个 seam 的两个 provider 行为不一致，换过去就是静默变形；
   L1 是其他 14 项的前提。

**一处修正**：D15 说"断网要自己用 `unshare -n` 包装"——更准确的做法是**实现一个 sandbox provider**
（`packages/sandbox/sandbox` 就是 provider seam，`sandbox-ssh` 已示范远端后端）。
这样断网策略与执行策略在同一个 seam 上，不用在命令层做字符串包装。

### D20. 上线门槛：有些能力不是功能，是"允许它碰真实服务器"的前提

08 的 MVP 解决"首版能演示什么"，但没有回答"凭什么敢让它接管一台真实服务器"。
单人、单机、自托管意味着**没有第二个运维兜底**，所以下面六项是准入门槛，不是加分项：

| 门槛 | 缺了会怎样 |
|---|---|
| **M1 快照回滚** | 一次误改就没有退路 |
| **M2 备份恢复** | 机器坏了，记忆与审计一起没 |
| **M3 看门狗自检** | agent 挂了没人知道，任务静默消失 |
| **M6 审计完整性** | 审计可被篡改，等于没有审计 |
| **M7 注入防护** | 一封邮件就能让它执行任意指令 |
| **C8 + M9 测试与评测** | "改好了"和"没变差"都无法证明 |

**决策**
1. 这六项**不进 MVP 功能清单**，但作为**发布门槛**单列，未过门槛不允许接真实服务。
2. 它们的判定几乎全是 🏗 —— 这是自托管路线的真实成本，不是可以"以后再说"的优化项。
3. 其中 M1/M2/M3 必须在 Step 1（冒烟测试）通过后立刻做，因为它们决定"敢不敢让它动手"。

**代价**：首版看起来"功能少"，但这是唯一能让单机自托管可持续的顺序。

### D21. 任务执行模型：显式委派 + 持久队列 + 租约执行（借鉴 openmuse）

openmuse 的任务段设计值得直接借鉴的是**"创建与执行解耦"**，而不是它的领域建模。

**它的机制（源码实测）**

| 环节 | 做法 |
|---|---|
| 创建 | 对话模型调用 `delegate_task` → `AgentService.createTask` 写入 tasks（`queued`） |
| 幂等 | `idempotencyKey` 哈希成任务 id + `insertIfAbsent`；重复调用返回同一条 |
| 抢占 | `compareAndSwap` 期望 `status + leaseId` → 置 `running`、`leaseUntil = now + 60s`、`attempts+1` |
| 心跳 | 每 `leaseMs/3` 续租；续不上 → abort 执行 |
| 防脏写 | 每次 checkpoint 都带 `leaseId` CAS；失去租约抛 `LostLeaseError` |
| 回收 | 租约过期 → 其他 worker 可抢占；丢失租约 → 回到 `queued` |
| 状态 | `queued / running / waiting_approval / waiting_input / scheduled / paused / succeeded / failed / cancelled` |
| 回执 | `plan[] + evidence[] + artifactIds[] + run-events` |
| 控制 | pause / resume / cancel / retry |
| 限额 | 并发 3；单 owner 非终态任务上限 100 |

**我们要采纳的（对应能力）**

- **D9**：任务对象、计划、证据、产物、回执。
- **D10**：CAS 租约 + 心跳 + `attempts` + 崩溃回收。**这是"进程挂了任务不丢"的唯一可靠做法。**
- **D11**：暂停/恢复/取消/重试；`waiting_approval` / `waiting_input` 是正式状态，不是特例分支。
- **I3**：幂等键 = `hash(sessionId + turnId + 参数)`；**必须带 turnId**，否则两次相同的请求会被错误合并。
- **E2**：并发上限（单机建议 3），以及非终态任务总量上限。

**必须改造的三处**

1. **结果投递方式不同。** openmuse 有 Activity 视图，任务结果落在通知中心；
   我们**只有微信**，所以完成/失败都必须**主动推回执**，并用 `task-done:<id>` 去重，绝不能"静默完成"。
2. **委派阈值要明说。** 不能让模型把所有事都丢给任务队列。规则：
   - 预计 > 60s、需要审批、必须跨断线存活、跨项目 → **委派**；
   - 一次问答、单步只读 → **当场做完**。
   没有这条阈值，模型会过度委派，聊天变成"已受理"复读机。
3. **单写者原则。** 只有持租约的 worker 能写任务体；聊天侧只能发控制指令（pause/cancel/retry）。
   两边都能改状态，租约就失去意义。

**不建议照搬的**

| 不搬 | 原因 |
|---|---|
| Goals / milestones 两级模型 | 单人单机场景过度建模；v1 用"任务组"即可 |
| 按 kind 预置固定计划步骤 | 我们的 dev/ops/life 差异太大，计划应由模型生成 |
| 独立 worker 进程 | 先做**进程内单 worker**；租约仍然保留，用于重启恢复与将来多进程 |
| 1 秒轮询 | 用事件唤醒 + 2–5s 兜底轮询，减少空转 |
| monitor 的领域字段（price_below 等） | 抽象成"条件 + 阈值"，供巡检/J8 复用 |

**dsh 侧的缺口**：没有持久任务表与 worker；jobs 是 owning-session 作用域；
`schedule` 只能投递原 session；**同一 session 能否被多 worker 并发 resume 未验证**（见 09 §七·11）。
落地时 `Task.sessionId` 必须显式，执行 = 创建或 resume 一个 dsh session。

## 七、与两份参考的关系（以及许可）

- **设计可以学，代码要分清许可**：OpenMuse MIT，可借鉴甚至移植；**nanoMuse GPL-3.0，代码不可抄进本仓**，否则整个仓库要 GPL。
- **nanoMuse 的 `harness/dsh-nanomuse` 是 dsh 插件 bundle 的现成范本**（bundle patch、preset、client 注入、`approval/request` 拦截）。它钉的是 dsh `0.2.0-rc.2`，我们用的是 `0.2.1-alpha.3`——**再次说明版本锁定与兼容测试矩阵是必需品**（09 §四）。
- 两者都证明了一件事：**dsh 之上做产品是可行的**，但都必须自带治理层。这不是我们的特殊困难，是这条路线的共性成本。
